# Проверки 1.3.5

Дата подготовки: 26 сентября 2026 года.

## Выполнено в среде разработки

Команда из корня архива:

```bash
python3 -m unittest discover -s tests -v
```

**31 тест, все пройдены, без пропусков.** Сохранённый полный вывод: `tests/RESULTS.txt`.

Среда: Python 3.13.5, Node.js 22.16.0, OpenSSL 3.5.5, cryptography 46.0.4, Bash.

Проверены:

- Синтаксис Bash, встроенного Python и JavaScript; `--help`; совпадение встроенных диагностик с исходниками `tools/`.
- SNI: независимая реализация HKDF в Python совпадает с Node.js crypto; различия переноса строк не меняют результат.
- Локальный TLS 1.3 стенд требует правильный SNI, доверенный клиентский сертификат и подписанный JWT. Старый Selfsteal-SNI отклоняется; правильный служебный SNI проходит серверную проверку.
- Фрагментированный ClientHello больше 1500 байт; проверка точного server leaf и отклонение несовпадения.
- Реальный HTTPS-запрос Node.js к локальному стенду: успешные mTLS + RS256 JWT; отказ при чужом CA, неверном JWT, попытке использовать сертификат ноды как сертификат панели.
- HTTP 200 без ожидаемого JSON-поля не объявляется успехом; TCP connection refused остаётся ошибкой стадии TCP.
- Дополнительный X25519-запрос; запуск JavaScript через stdin, как в `docker exec -i ... node -`.
- Удаление устаревших переопределений ключа/порта/часового пояса из Compose, сохранение явного SNI_VERIFICATION, host networking, restart policy, env_file, сохранение литерального `$` в дополнительных environment-переменных.
- Защита от чужого образа, дополнительных сервисов, неизвестного `/dev/shm` mount и незакреплённого digest.
- Выявление расхождения ключа и порта между ожидаемой конфигурацией и данными runtime; атомарная запись файла с правами 0600.
- Статические ограничения: repair не вызывает переустановку ОС, сброс firewall, изменение MTU/sysctl или reboot; содержит резервирование/попытку отката и проверку неизменности ключевого файла. Панельный код обращается только к healthcheck и использует read-only транзакцию.

Синтетические ключи тестового стенда генерируются заново во временном каталоге и удаляются после тестов. Реальные ключи пользователя не использовались и в архив не включены.

## Не проверено здесь

В среде разработки нет Docker daemon, systemd VPS, backend/БД пользователя, внешнего firewall и доступа к его серверам. Поэтому **не выполнялись** полная установка, применение Compose через настоящий Docker, обновление реального образа, реальный rollback сервисов, запросы Prisma к работающей БД Remnawave, reboot и проверка рабочего VPN-трафика.

Протокольный стенд проверяет поведение клиентского кода, но не заменяет запуск против настоящей RemnaNode. Панельная SQL-диагностика сверена с опубликованной схемой; при другой схеме или отсутствии доступной Prisma сообщает `INCOMPLETE`, а не ложный `PASS`.

`CONNECTION_REPAIR=APPLIED` и `NODE_MANAGEMENT_LOCAL=PASS` относятся к применению ремонта и локальному API. Только отдельная панельная проверка может вывести `PANEL_NODE_API=PASS`; и даже она не подтверждает все worker-контейнеры, применение Xray-профиля и пользовательский трафик.

## Повторить тесты

На отдельной машине разработки с Bash, Node.js 18+ и Python 3.10+ создайте venv и установите `cryptography`. Не требуется запускать установщик от root, иметь рабочую панель или открывать порты наружу: стенд слушает только `127.0.0.1` на временном порту.

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install cryptography
python -m unittest discover -s tests -v
```

Тесты Node.js при его отсутствии явно пропускаются. Для полного результата нужно отсутствие пропусков.
