# Node Plugins contract — 2.5.0

## Scope

`Node_Install 2.5.0` remains **node-only**. It prepares and checks the host/container prerequisites for stable Remnawave Node Plugins; it does **not** authenticate to the Panel, create Shared Lists, assign Plugin Config, mutate users/Hosts/Nodes or claim that a client-side feature works merely because the VPS is healthy.

The reviewed local prerequisites are:

- Linux kernel `>= 5.7`, checked before APT/firewall/GRUB/SSH mutation;
- distro `nftables` userspace CLI present and runnable; `nftables.service` is not enabled or started and `/etc/nftables.conf` is not managed;
- RemnaNode remains `network_mode: host`, with exactly the existing `NET_ADMIN` addition, `NET_RAW` drop and `no-new-privileges:true` contract;
- Xray functional floor `>= 26.3.27` for Torrent Blocker readiness;
- reviewed Xray security floor `>= 26.7.11`;
- VLESS RAW+REALITY+Vision profile with public TCP/443, own-domain `serverNames`, Selfsteal target `/dev/shm/nginx.sock`, `xver=1`, and sniffing `{enabled:true, routeOnly:true, destOverride:[http,tls,quic]}`.

No custom Xray binary is downloaded or installed. Core comes from the reviewed official Remnawave image/digest selected by the existing installer transaction.

## Runtime acceptance

`vkarmani-node-check` reports the prerequisite layers separately. Xray version is obtained read-only from `docker exec remnanode rw-core version`. Node Plugin runtime is inspected with bounded `nft -j list table ip remnanode` and structured JSON parsing. The reviewed runtime structure contains the table `ip remnanode`, sets `ingress-filter-ip`, `torrent-blocker`, `egress-filter-ip`, `egress-filter-port`, and chains `input`, `forward`, `output`.

Empty sets and zero counters are valid. No active DROP is generated by acceptance. The installer never adds/deletes/flushes RemnaNode nft objects.

Fresh install preboot may occur before Panel Plugin Config is assigned. Therefore absence of the RemnaNode runtime table in normal/preboot/local/postboot mode is `NOTE NOT_VERIFIED`, not a false PASS and not a premature failure. `sudo vkarmani-node-check --require-xray` is the strict canary check after Panel profile/plugin assignment; there missing/malformed plugin runtime is a failure.

`NODE_PLUGINS_PANEL_CONFIG` and `TORRENT_DETECTION` stay `NOT_VERIFIED`: the installer deliberately has no Panel API token and a local nft/Xray prerequisite check does not prove that Panel configuration is assigned or that a real BitTorrent flow will be detected. Xray sniffing only recognizes part of real-world BitTorrent traffic; do not turn installation acceptance into a torrent-generation test.

## Manual Panel baseline

Reference-only JSON: [`NODE_PLUGINS_REFERENCE_2.5.0.json`](NODE_PLUGINS_REFERENCE_2.5.0.json). It is documentation, not runtime source of truth.

Recommended manual baseline:

- Ingress Filter enabled; `blockedIps=["ext:vkarmani_ingress_blocklist"]`;
- Egress Filter enabled; `blockedIps=[]`; blocked ports exactly `25,137,138,139,445,465,587,2525`;
- Torrent Blocker enabled; `ignoreLists.ip=[]`; `blockDuration=3600`;
- Connection Drop enabled; `whitelistIps=[]`;
- `vkarmani_ingress_blocklist` is an empty `ipList` initially.

`vkarmani_nonpublic_ipv4` is reference-only and is **not** wired into Egress Filter by default. Egress filtering operates in host OUTPUT; blindly blocking `127/8`, link-local or provider-private ranges can break local DNS, metadata or private routes.

## Intentionally unchanged

Pre-Start/Cleanup Sockets remain disabled; the live Selfsteal socket pathname must not be broadly deleted. Abuse Blocker is not copied from draft/unreleased upstream behavior. `NFTABLES_LOGGING`, `NFTABLES_ACCEPT_REPLY_TRAFFIC` and `SNI_VERIFICATION` defaults are not silently changed. In Node 3.4.x nftables logging may be enabled upstream; if it causes a log storm, handle that as an explicit reviewed configuration task, not an installer side effect.

No third-party threat lists, RST-derived lists, `ipset`, provider hopping, SNI/ShortID/key rotation, random fingerprints, packet fragmentation/noise, alternate transports or high/random public ports are introduced.

## Canary and rollback

Before rollout, use a disposable Ubuntu 24.04 amd64 VPS with provider snapshot/console. After fresh installation and manual Panel assignment:

```bash
sudo vkarmani-node-check --require-xray
sudo nft list table ip remnanode
sudo docker logs --since 10m remnanode
sudo ss -4 -lntp
sudo ufw status verbose
sudo systemctl --failed --no-pager
```

Then verify Panel→Node `NODE_PORT`, client→443, REALITY/Selfsteal, one real client and sustained transfer. A manual TCP/25 egress canary may be done only after Plugin Config sync, with DNS/HTTPS rechecked afterward. Roll back Panel Plugin Config independently if needed; never `nft flush ruleset` and never manually delete RemnaNode tables. Image rollback continues to use the existing transactional image workflow.

This repository build cannot perform that real VPS canary by itself; release records must say `NOT_PERFORMED` until an operator does it.
