## Завершено в исходниках

- Предыдущие этапы r54–r57 и 120 сайтов без изменений серверной логики.
- Устранён дефект актов приёмки: раньше `--evaluate` принимал записанный оператором SHA в качестве строки, не сверяя его с конкретным архивом. Теперь для `ACCEPTED` обязателен `--archive` и совпадение SHA-256 его реальных байтов с `source_zip_sha256` в JSON. Символьные ссылки в аргументе архива отклоняются.

## Фактическая staging-приёмка (обязательна до production)

**Порядок:** подготовить только отдельную тестовую VPS, полный проверенный снимок и подтверждённую возможность восстановления через панель провайдера. Никогда не применять staging-приёмку на работающем production-узле без отдельного согласования.

1. Сверить SHA-256 ZIP по независимому каналу и выполнить из распакованного архива `python3 scripts/verify_release.py --root .` и `bash tests/run.sh`.
2. Сохранить snapshot и внешний backup, проделать контрольное восстановление на изолированной VPS (не на действующем сервере).
3. До и после установки проверить SSH-вход **по паролю** в новой независимой сессии и доступность консоли хостера. **Не включать SSH-ключи**.
4. Проверить `nginx -t`, статус Nginx, сертификаты TLS, публичный HTTPS/404, A/AAAA/DNS и локальные ресурсы сайта; сохранить конфигурацию до/после.
5. Проверить `docker compose config`, systemd-сервисы, firewall, избирательный доступ Panel к Node API, реальные клиентские подключения, маршрут IPv4/IPv6 и счётчики nftables; не считать `drop`-policing точным тарифицируемым объёмом.
6. Выполнить проверенный reboot на тестовом узле, отказоустойчивость, восстановление сети и снапшота, журналы; отдельно проверить каскадные сценарии, если применяется каскад.
7. Проверить 120 тематик человеком: достоверность публикаций, оригинальность, доступность и внешний вид. Автоматическое `OFFLINE_PASS` не подтверждает качество материалов или готовность публичной площадки.
8. Задокументировать evidence каждой реально выполненной проверки, время UTC и оператора, исключив пароли, UUID и токены. Следующий этап — экспертное подтверждение результатов.

## Инструмент акта приёмки

Шаблон для ordinary VPS (вне папки проекта, в закрытом рабочем каталоге):

```bash
sha256sum Node_Install_2.5.18-docs-menu_20261113-r58-final-acceptance-pass5-staging.zip
python3 scripts/staging_acceptance.py --create-template ordinary \
  --zip-sha256 ИСТИННЫЙ_SHA256_АРХИВА > /защищённый/каталог/evidence.json
```

Незаполненный шаблон содержит `BLOCKED` во всех пунктах; **не редактировать его как `ACCEPTED` до настоящих испытаний**. После верификации на тестовой инфраструктуре и подшивки реальных доказательств:

```bash
python3 scripts/staging_acceptance.py --evaluate /защищённый/каталог/evidence.json \
  --archive /путь/к/Node_Install_2.5.18-docs-menu_20261113-r58-final-acceptance-pass5-staging.zip
```

Exit 0 свидетельствует **только** о полном операторском чек-листе, проверенном SHA архива и совпадении схемы. Он не доказывает подлинность ссылок и факт подключения к Remnawave/серверу, которые требуют независимой проверки. `--archive` обязателен для принятого акта, без него успешный результат невозможен.

## Backup и rollback

**Серверных изменений этап 5 не делает, поэтому серверный rollback для него не требуется.** На staging: сохранить текущие SSH/Nginx/UFW/Docker-конфигурации, данные Panel/Node API и внешний snapshot, подтвердить восстановление на *отдельном* инстансе. Перед любой правкой Nginx выполнить `nginx -t`; при ошибке не перезагружать. При потере сетевого доступа использовать консоль провайдера и проверенный snapshot, не пытаться вслепую очистить firewall. Исходную r57 хранить отдельно для сравнения исходников; обратная установка файлов сама по себе не восстанавливает состояние VPS/БД/доступы.

## Ограничения

Доступа к действующей отдельной VPS и Panel в рамках подготовки архива нет. Нет свидетельств проведения реального первого install/reboot/restore, живых клиентских проверок, DNS/ASN/TLS или 24-часового soak. **Нельзя писать «production готов» или «вся система испытана» на основании ZIP и офлайн-тестов.**
