# Node Install 2.5.18 r48 — навигация по статьям и проверка реального 404 (STAGING)

**Дата:** 2026-11-07. **Источник:** полный проверенный ZIP r47. **Статус:** `INCOMPLETE_STAGING_ONLY`.

## Цель и границы

Обновить **только** статические тематические сайты и контроль их публикации; не изменять действующие подключения, REALITY/XHTTP, ключи, TLS, SSH, Nginx, маршруты, Docker и firewall. Хороший веб-сайт улучшает качество обычного HTTPS-ответа, но **не доказывает и не гарантирует** стойкость VPN к ТСПУ/РКН или сокрытие его сетевого профиля.

## Реальные изменения

1. **96 каталожных сайтов:** на `journal.html` перед четырьмя статьями создано навигационное оглавление из названий их тем. `#story-1` … `#story-4` — те же уже существующие, проверенные идентификаторы; ссылки не ведут на новые URL. Язык заголовка оглавления соответствует `lang` сайта. CSS использует локальные цвета темы, медиа-правило для смартфонов и стандартный фокус клавиатуры. Остальные страницы и 24 не-каталожные темы сохраняют дизайн и маршруты.
2. **Транзакционная публикация:** после активации Nginx `scripts/staging_web_deploy.py` проверяет по реальному HTTPS не только три внутренних страницы, `robots.txt` и `sitemap.xml`, но и favicon. Дополнительно выполняет один GET на гарантированно несуществующий путь своего домена. Проверяются одновременно статус **404** и точное тело опубликованной `404.html` с новым CSS href. Если ответ 200, редирект, чужая дефолтная страница Nginx, повреждённый favicon или ошибка curl — публикация откатывается текущим механизмом.
3. **Тесты:** позитивные проверки контента всех 96 журналов и существующих якорей, негативный обрыв якоря, ошибка favicon, ошибка 404 и восстановление исходных файлов/конфига при неудачной публикации.
4. **Сохранность:** `install.sh` побайтово прежний, существующие 120 тем и 9 файлов каждой сохранены, изменения CSS/HTML ограничены 96 темами каталога. Никаких API, браузерных скриптов, серверных плагинов, внешних ресурсов или новых URL нет.

## Приёмка

В каталоге полного ZIP:

```bash
sha256sum --check SHA256SUMS
python3 -B scripts/verify_release.py --root .
python3 -B scripts/site_audit.py --rich
python3 -B -m unittest discover -s tests -p test_r48_site_navigation_live_404.py -v
bash -n install.sh
bash tests/run.sh
```

Реальный ответ 404 и favicon **не тестировались на действующей VPS**: новый тестовый набор моделирует эти ответы для проверки успешного и аварийного сценария. Фактический HTTP/2, сертификаты, доступность клиента и реакцию DPI необходимо проверять на собственной staging VPS.

## Безопасное применение на готовой staging VPS

1. Заранее подтвердить backup/snapshot, доступность консоли провайдера, домен, публичный IPv4, сертификат и исправную ноду; **не запускать повторную первичную установку ради смены сайта**.
2. Из новой отдельной распаковки выполнить целостностные проверки выше. Для смены сайта использовать существующий `python3 -B scripts/site_manager.py menu` и разрешённое им изменение темы с явным подтверждением `STAGING` и домена.
3. После изменения проверить `nginx -t`, `vkarmani-selfsteal-check`, HTTP/2, статус GET/HEAD главной страницы, четыре публичные ссылки/og:metadata/robots/sitemap, favicon и путь без файла (404). Проверить реальный VPN-клиент и повторить после reboot.
4. Откат сайта: штатная команда/пункт `site-rollback` через `site_manager.py`, работающая с журналом транзакции. При системном сбое использовать проверенный snapshot VPS; не менять ключи/порты/правила firewall ради отката HTML.

## Важные ограничения

- Поскольку публичный сайт и VPN используют разное поведение TLS/REALITY, их нельзя считать одним и тем же HTTPS-протоколом только потому, что HTML доступен.
- Нельзя подтвердить снижение обнаружимости VPN, не сравнив поведение клиентских подключений с контролируемым baseline в разных сетях.
- GitHub-ветка `main` не проверена на наличие r48; используйте только ZIP и доверенную контрольную сумму. Честная маркировка: **STAGING ONLY**.
