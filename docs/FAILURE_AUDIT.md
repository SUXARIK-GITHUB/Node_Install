# 🔎 Отказные сценарии и узкие места — 2.0.1

Дата: **30 сентября 2026**. База: предоставленный полный `Node_Install_2.0.0.zip`. Исследовался именно код архива, а не предполагаемое состояние GitHub. Продакшен, реальные узлы, панель, DNS и учётные записи не изменялись.

**Вывод:** исходные 74 теста проходили, но это не исключало дефектов в аварийных сценариях. Четыре проблемы воспроизведены непосредственно на старом коде/изолированном Nginx; дополнительные риски найдены при разборе состояний и закрыты отдельными тестами. В 2.0.1 — 178 отдельных тестов. Подробная граница реальных/имитированных проверок: [TEST_REPORT](TEST_REPORT.md).

## 1. Воспроизведено на исходной 2.0.0

| Дефект | Как проверен | Что происходило | Исправление и подтверждение |
|---|---|---|---|
| Ложный успех firewall check | Старый фактический Python payload, имитация `iptables -S`: сохранён только panel/API allow, удалены SSH/80/443 allow | Exit code **0**; пропажа доступа не замечалась | Новый parser требует весь ожидаемый набор разрешений и INPUT-топологию, отклоняет лишние/двусмысленные правила. Пропажа каждого порта покрыта тестом. Это не запуск реального UFW |
| Зависание Selfsteal на увеличенной странице | Реальный Nginx 1.26.3, временный Unix socket/CA, собственный шаблон, `index.html` 96 KiB | Старый checker завершался `TimeoutError` примерно через **5,02 с**, хотя Nginx был исправен | Добавлены HTTP/2 WINDOW_UPDATE для connection и stream. Страницы 96 и 128 KiB проходят; 128 KiB + 1 байт отклоняется явным лимитом проверяющего кода |
| Потомок продолжает работу после таймаута | Старый maintenance `run`, реальный `/bin/sh` с фоновым потомком, который пишет временный маркер после задержки | Helper сообщал `COMMAND_TIMEOUT`, но потомок позже **создавал файл** | Popen с отдельной process group, TERM → ограниченное ожидание → KILL. После отмены позднего файла нет; отдельно проверены SIGTERM и игнорирование TERM |
| Nginx не стартует после аварии со старым socket | Изолированный реальный Nginx принудительно завершён SIGKILL | Socket-файл оставался; повторный старт без очистки получал `Address already in use`, connect — отказ | Новый ExecStartPre-helper проверяет тип, владельца, liveness, повторный inode. Три последовательных crash → stale detection → cleanup → restart → HTTP/1.1+HTTP/2 цикла проходят |

HTTP/2 flow control относится **к проверке сайта Selfsteal**, не к смене VPN-транспорта. В проекте по-прежнему VLESS RAW REALITY. Нормативная основа WINDOW_UPDATE: [RFC 9113](https://datatracker.ietf.org/doc/html/rfc9113), в частности управление окном и DATA.

## 2. Найдено анализом и проверено дополнительными сценариями

### Неопределённый результат Docker apply

Таймаут CLI не доказывает, что daemon отменил уже принятую операцию. Автоматически запускать обратный Compose во время возможного продолжающегося recreate — риск гонки. Теперь **только при timeout/сигнале внутри compose_up** остаётся `IMAGE_APPLY=UNKNOWN` и pending marker; встречный rollback не запускается. Нужны проверка Docker и явное решение оператора.

Если Compose вернулся, но локальное здоровье кандидата не подтверждено, автоматическая попытка возврата сохранена. Если сам откат не подтверждён, pending не удаляется. Registry failure/некорректный JSON/нехватка места до применения не меняют работающий Compose. Эти переходы тестируются с **имитированным Docker boundary**, реальными временными transaction files и инъекцией ошибок; реальный daemon не запускался.

### Общий, а не только отдельный timeout

У старого readiness loop отдельные Docker inspect/cover/sleep могли выходить за номинальное время ожидания. В 2.0.1 все этапы получают оставшийся бюджет. Selfsteal использует monotonic deadline, который не продлевается потоком медленных маленьких чтений. Общая локальная проверка ограничена GNU timeout; ожидание Selfsteal в renewal — отдельным общим бюджетом.

| Проверка | Заданный бюджет | Граница |
|---|---|---|
| Selfsteal HTTP/1.1 + HTTP/2 | 20 секунд суммарно | До 5 секунд на отдельное чтение/запись, не дольше оставшегося общего времени |
| `vkarmani-wait-selfsteal` | 60 секунд | До 2 секунд дополнительно на принудительное завершение текущей попытки |
| Acceptance `vkarmani-node-check` | 600 секунд | До 5 секунд kill-after; timeout — ошибка, не PASS |
| Maintenance health | 180 секунд, pre-update 60 секунд | Inspect/probes/stability sleep делят бюджет; завершение процессов может добавить короткое ограниченное ожидание |

Это ограничения управляющих проверок, **не SLA восстановления VPS**. Kernel tasks в непрерываемом I/O, сломанный host storage, внешний daemon и гипервизор не становятся управляемыми Python-таймаутом.

### Сертификат записан на диск, но Nginx ещё отдаёт старый

Теперь checker сравнивает проверенный TLS leaf с сертификатом на диске. Несовпадение выдаёт `SELFSTEAL_CERTIFICATE_NOT_RELOADED`; TLS/hostname validation не отключается. Renewal hook ждёт фактический Selfsteal после `nginx -t` и reload. Неправильный pin проверен на настоящем Nginx; **реальный выпуск/renewal Let's Encrypt не выполнялся**.

### Повторные запуски и долговечность состояния

При pending SSH/UFW rollback установка останавливается до перезаписи единственного backup. Повторная проверка выполняется и после получения installer lock. Сохранённый digest перед записью Compose повторно проверяется. JSON/text atomic write синхронизирует файл и родительский каталог; archive backup синхронизируется до публикации checksum.

ENOSPC на rename и EIO на fsync до замены сохраняют предыдущий файл; временные файлы убираются. Ошибка fsync каталога **после** rename означает, что новая версия могла уже появиться — это не обещание возврата старого состояния при любой ошибке. Физическое отключение питания и гарантии storage-cache гипервизора не тестировались.

### Ограничение маскировки своим доменом

`profile-check` проверяет один VLESS inbound/443, RAW+REALITY, свой `serverNames`, локальный `/dev/shm/nginx.sock` в `target`/`dest`, PROXY v1 и допустимый шаблон outbounds. Отдельно проверяются оба transport aliases `network`/`method`: запись второго поля не должна скрытно включать XHTTP. Flow клиентов не меняется.

Неправильный профиль останавливается, не исправляется тихо. Это **не полный валидатор Xray**, не аудит любого произвольного JSON, не проверка Host override/живой панели и не доказательство права собственности. Для фактически назначенного профиля нужна проверка экспорта панели и выбранного бинарника. Подробности: [HOSTING_AND_INCIDENTS](HOSTING_AND_INCIDENTS.md).

### Повторные старты Nginx

Убрано исчерпание StartLimit для managed Nginx, задан интервал 5 секунд. После появления адреса или исправления конфигурации попытки запуска продолжаются. Само по себе это не лечит синтаксическую ошибку/просроченный cert; бесконечная ошибка требует оператора, а журналы и диск требуют контроля. Конфигурация unit проверена offline вместе с distro unit; systemd boot/restart на настоящей VPS здесь не проверен.

## 3. Что именно не решено установщиком

| Узкое место | Почему локальный скрипт не устраняет его | Что требуется |
|---|---|---|
| Фильтрация/blackhole IP по внешнему маршруту | Пакет может вообще не доходить до VPS; Nginx, MTU и ключи не меняют решение удалённой сети | Сопоставить разрешённые пробы своих адресов из нескольких сетей, console evidence и ответ хостера; не диагностировать CIDR по цвету карты |
| Нет подтверждённой работоспособности всей цепочки | Нет реального RemnaNode/Xray/Docker/панели/клиента в текущей среде | Canary с точным image digest, своей версией панели и реальным пользователем |
| Перезапуск контейнера при offline панели | Image rollback не является восстановлением профиля/users/клиентских sessions | Доступная панель и проверка повторной доставки профиля; не обновлять ноду во время инцидента панели |
| Одна VPS, один IPv4, один контейнер | Нет второй ноды и автоматического переключения клиентов | Проектирование резервирования отдельно; оно не добавлялось без запроса |
| VPS CPU steal, ограниченная полоса, потери, большой RTT | Локальный Unix-socket тест не воспроизводит сеть и гипервизор | Измерения upload/download, loss/retransmits, p95 задержки, steal/RAM/I/O на каждом классе хостинга |
| Root SSH по паролю | Компрометация пароля и распределённый перебор не устраняются Fail2ban | Уникальные сильные пароли, журнал, проверенная консоль; исходное требование доступа без allowlist сохранено |
| Накопление backups/images | Автоматический prune нарушил бы возможность rollback | Off-host копия и проверенный restore, наблюдение за свободным диском; удаление только выбранных копий после проверки |
| `latest` при первом install | Новый upstream может изменить поведение/схему и совместимость с панелью | Выбранный и проверенный digest; одинаковый digest при раскатке, а не вера в тег |
| Firewall вне двух проверяемых цепочек | Нет модели всех nft/raw/mangle/UFW before/after hooks и provider firewall | Внешняя проверка API/SSH/443 и аудит ручных изменений; не смешивать firewall managers |
| Power loss и GRUB | Нет гипервизора/boot-cycle в контейнере подготовки | Snapshot + restore rehearsal + power-cycle только на одноразовой canary |
| Старые уже установленные helpers 2.0.0 | Копирование архива не изменяет host runtime; plain install намеренно только проверяет | Не считать новый архив миграцией. Отдельная canary или специально проверенный план in-place перехода |

## 4. Что не менялось

Три обязательных ответа; парольный SSH и существующие порты; отсутствие SSH allowlist; VLESS RAW REALITY; Nginx вне Docker; свой сайт/домен; один RemnaNode; API только с IP панели; отсутствие нового транспорта/прокси/моста/очереди/БД. Не менялись MTU интерфейса, маршруты, sysctl-профиль ради «обхода блокировки», DNS/адреса реальных нод и объекты панели.

Изменены `install.sh`, README/SECURITY/CHANGELOG, аудит/регламент/источники/отчёт, два существующих тестовых файла и добавлены отдельные regression tests. Сохранены все исходные файлы 2.0.0 и Git metadata; отчёт предыдущего этапа перенесён без изменения текста в `docs/history/TEST_REPORT_2.0.0.md`.

## 5. Безопасная приёмка перед production

Проверенный snapshot/консоль → чистая canary **того же хостера и класса VM** → install с известным digest → новая парольная SSH-сессия → ручной reboot → локальная и строгая диагностика → профиль/Host/пользователь в панели → реальный RAW REALITY клиент из нужной сети → наблюдение под нагрузкой → update/rollback в согласованное окно → повторная проверка.

Отрицательные испытания с отключением сети, заполнением диска, SIGKILL, остановкой панели или power cycle — **только на отдельном стенде**. Не запускайте хаос-тесты в production, не сканируйте соседние чужие IP и не «лечите» отказ удалением UFW/Fail2ban/секретов.
