# ⛓️ Каскад VLESS/REALITY — справочные профили 2.5.10

**Статус: STAGING_ROLE_INSTALLER / LIVE_NOT_TESTED.** В r5 добавлена отдельная установка двух ролей на новых VPS, подготовка раздельных ключей и fail-closed проверка профилей. **Эти примеры остаются только справочными**; для установки и привязки Panel используйте [инструкцию r5](CASCADE_R5_ROLE_INSTALL_AND_PANEL.md). Нет автоматического создания Node/Squad/Host/bridge user или подтверждённых реальных двухсерверных испытаний.


## Изменения r4 (без включения live-узлов)

Добавлен [offline-генератор](../integrations/cascade_profiles.py), создающий из закрытого файла две **настраиваемые** профильные заготовки с проверяемым анти-DIRECT policy. Справочный `cascade-entry-profile.reference.json` теперь имеет `routing.domainStrategy=AsIs` и **не имеет** `dns`: сервер не должен разрешать пользовательские имена для IP-match перед передачей на выход. Это не гарантирует отсутствие системных DNS-запросов; внешние `tcpdump`/E2E gate обязательны. Выходной профиль оставляет `IPOnDemand` и собственные DNS и DIRECT с `finalRules` на exit. Полные команды и правила секретов — [R4 инженерный план](R4_8_POINT_ENGINEERING_20261015.md).

**Исторически в r4** меню `2` завершалось до мутаций. **В r5** оно позволяет выбрать Entry или Exit и приватный bundle для установки на **новой staging VPS**. Связь с Remnawave и live-проверки остаются отдельными release-gates.

## Архитектура: реализована генерация ролевых профилей, но не E2E подтверждение

```text
Клиент → ВХОД:443 (VLESS+REALITY+Vision) → TO_EXIT_VLESS (VLESS/REALITY) → ВЫХОД:443 → DIRECT/интернет
```

Планируется независимый Selfsteal/сертификат на обоих серверах: внешние браузеры видят *собственный* сайт входа/выхода через Xray REALITY fallback → Nginx Unix socket; VPN-пакеты не становятся HTTP-запросами. Входная нода не должна иметь запасного пользовательского DIRECT, когда peer недоступен. Управляющий Node API и обновления отделяются от клиентской маршрутизации. Для обоих серверов нужны своя область RKN/IP-панели, SSH, TLS, firewall и контрольный клиент.

## Два полных JSON-примера (НЕ активные)

- [Входная нода](../examples/cascade-entry-profile.reference.json): `VK_CASCADE_ENTRY_REALITY_REPLACE_WITH_REAL_TAG` на 443; при авторизованном клиенте правилом inboundTag направляется в `TO_EXIT_VLESS`. Первым outbound является BLOCK для отсутствия неявного пользовательского DIRECT. Документ нельзя импортировать, пока не подставлены настоящие параметры и не валидировано **весь активный Config Profile** с дополнительными правилами панели.
- [Выходная нода](../examples/cascade-exit-profile.reference.json): отдельный VLESS/REALITY inbound, собственный `target=/dev/shm/nginx.sock`, отдельные ключи и SNI. DIRECT присутствует **только на выходе** в демонстрационной модели.

**Placeholder-значения не реальные адреса и не секреты:** `198.51.100.20` — тестовый адрес, `entry.example.com`/`exit.example.com` — примеры FQDN, `REPLACE_WITH_*` должны быть заменены пользователем/панелью. Нельзя вставлять шаблон в production без валидации и сквозной приёмки.

## Почему недостаточно одного inbound

По [официальной документации Remnawave о серверной маршрутизации](https://docs.rw/learn-en/server-routing/) панель очищает статический массив `clients` и управляет назначениями пользователей сама. Для входа нужна связка user → inboundTag → межнодовый outbound, для выхода — **отдельный служебный пользователь**, которому панель через Internal Squad разрешает именно bridge inbound. Ни JSON-файл на диске, ни SECRET_KEY ноды сами не создают service-user в панели.

[Вопросы, которые нужно проверить до внедрения](https://github.com/XTLS/Xray-core): версия `rw-core` и поддержка Vision в outbound; Node API, routing overrides от панели, DNS на двух узлах, адрес источника через REALITY/PROXY, правила RKN и firewall, отсутствие циклов и прямого обхода. Сервисная учётная запись не должна быть административным токеном панели.

## Критерии, которые нельзя закрыть без настоящих VPS и Panel

1. Реальный прогон интерактивной установки обеих ролей с сохранённым state, своим доменом и сертификатом (**код r5 создан; live запуск не выполнялся**).
2. Подтверждённая безопасная **ротация** peer-данных двух действующих узлов; r5 разделяет исходные пакеты по ролям, но не автоматизирует ротацию.
3. Реальная привязка двух Node и Config Profiles в Remnawave, без переписывания чужих пользователей/Hosts.
4. Тест правильного внешнего IPv4 через выход и отказа соединения при недоступном выходе — **без DIRECT fallback**.
5. Own Selfsteal, RKN, UFW, обновление, rollback, timer, certificate renewal и reboot на каждом сервере.
6. Две независимые VPS и настоящий клиент, включая отрицательные тесты неправильных credentials и RKN/Node Port ACL.

До исполнения этих live-gates релиз остаётся staging-only; r5 добавляет изолированные установочные роли, но ни JSON-примеры, ни сухой тест не доказывают работающий production-каскад.
