# Node_Install 2.5.18 r26 — FinalMask, анализ измерений и усиленные проверки транспорта

**Дата:** 2026-11-05. **Статус:** `INCOMPLETE_STAGING_ONLY`. **База:** точный архив r25, GitHub `main` не изменяется.

## Что добавлено

1. **Опциональный FinalMask TCP/fragment для исходящего VLESS клиента**: выбор **включить / выключить / статус**, ручной ввод размерных диапазонов, полный экспорт нового приватного Xray JSON с сохранением других outbound и routing, альтернативно — приватный JSON-фрагмент для ручной интеграции. Встроенное меню доступно командой `--finalmask menu`. **По умолчанию отключено**; никакие существующие профили не меняются. При выключении удаляется только проверенный одиночный `tcp.fragment`, другие типы FinalMask не перезаписываются.
2. **Числовые параметры FinalMask (не «оптимальные» значения):**

   | Флаг CLI | Поле Xray JSON | Значение в примере | Значение / допустимый диапазон инструмента |
   |---|---|---|---|
   | `--lengths` | `settings.lengths` | `80-160` | Длина TCP-фрагмента в байтах; `1..1400`; поддерживаются списки `80-160,160-240` |
   | `--delays` | `settings.delays` | `0-5` | Пауза между фрагментами, **миллисекунды**, `0..200`; список значений |
   | `--max-split` | `settings.maxSplit` | `2-4` | Число разбиений, `1..16`; только один диапазон |
   | фиксировано | `settings.packets` | `tlshello` | Только TLS ClientHello, не все пользовательские TCP-пакеты |

   **Все числа — лишь ограниченные начальные параметры для разрешённого staging-эксперимента; они не дают гарантий скорости или незаметности и могут ухудшать соединение.** Значения Xray представлены строками Int32Range, `lengths` и `delays` — массивами строк, `maxSplit` — строкой.

3. **Read-only проверка Xray runtime для опциональных bundles:** `--transport-readiness xhttp-tls|hysteria2 --bundle ... --expected-domain ... --xray-bin /absolute/path/xray`. Запускает локальное `xray run -test -config`, не стартуя службу, не изменяя файрвол и не раскрывая stderr/stdout потенциально секретного Xray. Бинарник должен быть доверенным, исполненным без групповой/мировой записи. Результат `PASS` означает только прохождение конфигурационного теста указанным ядром, а не соединение клиента. Из-за неактивированной службы итоговый статус продолжает оставаться `REVIEW`.
4. **Анализ уже сделанных замеров:** `--measure-compare before.json after.json`. Поддерживает только отчёты `--quality-probe` (прямой HTTPS) или `--throughput-probe` (прямой TCP к разрешённому iperf3). Сравнивает совпадающий тип измерения/направление, показывает изменения p50/p95 или Mbps, не рекомендует бессистемную смену BBR/CUBIC и **не называет это измерением скорости VPN или устойчивости против DPI**. Никаких запросов в сеть не делает.
5. Дополнены offline-тесты на значения, обходы путей, приватность файлов, повторное отключение, порядок `outbound`, незнакомые маски, ошибочный Core и несовпадающие измерения.

## Как включить/выключить FinalMask

Здесь **настройка располагается на клиентском Xray outbound**, а не на RemnaNode inbound. Фрагментация `tlshello` воздействует на исходящий ClientHello: Xray-сервер не может «за клиента» разбить ClientHello, который уже пришёл по сети. Если пользователь подключается через Remnawave-приложение, настройки клиентского Xray должны поддерживать FinalMask; возможности приложения и Panel **не** подменяются сервером.

**Исходный файл:** полный приватный Xray JSON клиента, содержащий исходящий `protocol: vless` и уникальный `tag`, с `streamSettings.security` = `reality` или `tls` и TCP транспортом `raw`/`tcp` или `xhttp`. Права исходного файла `0600`, владелец — вызывающий пользователь. Создай приватный каталог с `0700` *вне* репозитория, например `/root/private`, и не размещай ключи в ZIP/Git. `--output` должен указывать на новый файл и никогда не перезаписывает существующий.

```bash
# Пример выбора параметров / выключено по умолчанию, без исходного JSON
bash install.sh --finalmask defaults

# ТОЛЬКО фрагмент для ручной вставки в streamSettings клиентского outbound
sudo bash install.sh --finalmask snippet \
  --output /root/private/finalmask-snippet.json \
  --lengths 80-160 --delays 0-5 --max-split 2-4

# Просмотр статуса конкретного приватного клиентского JSON (без вывода секретов)
sudo bash install.sh --finalmask status \
  --input /root/private/client.json --outbound-tag proxy

# Интерактивное меню (выбрать 1 ВКЛ / 2 ВЫКЛ и ввести числа)
sudo bash install.sh --finalmask menu \
  --input /root/private/client.json \
  --output /root/private/client-updated.json \
  --outbound-tag proxy

# Неинтерактивная явная активация в НОВОМ приватном клиентском JSON
sudo bash install.sh --finalmask enable \
  --input /root/private/client.json \
  --output /root/private/client-enabled.json \
  --outbound-tag proxy \
  --lengths 80-160 --delays 0-5 --max-split 2-4

# Выключить: экспорт без единственной управляемой маски (старый файл не изменён)
sudo bash install.sh --finalmask disable \
  --input /root/private/client-enabled.json \
  --output /root/private/client-disabled.json \
  --outbound-tag proxy
```

**Никакого запуска Xray и автоматического переключения активных подписок здесь нет.** Программа сначала проверяет тип транспорта, шифрование и отсутствие посторонних FinalMask-слоёв. На неподходящем режиме, при попытке перезаписать файл, на символьной ссылке, в общедоступной директории или при некорректных цифрах программа останавливается. На каскадных профилях не запускайте прямые экспериментальные транспорты; неизменность fail-closed Entry/Exit остаётся обязательной.

### Пример получаемого элемента `streamSettings`

```json
{
  "finalmask": {
    "tcp": [
      {
        "type": "fragment",
        "settings": {
          "packets": "tlshello",
          "lengths": ["80-160"],
          "delays": ["0-5"],
          "maxSplit": "2-4"
        }
      }
    ]
  }
}
```

**Пример — только часть `streamSettings`**, его нельзя загружать в Panel как полноценный серверный профиль, клиентскую подписку или готовую полную Xray-конфигурацию. Не добавляй FinalMask автоматически на inbound ноды.

Официальный источник формата: https://xtls.github.io/en/config/transports/finalmask.html (проверен 2026-11-05). Для новой версии Core/клиента заново проверяй схему через `xray run -test -config ...`; конечный handshake/доступность без клиента не подтверждаются.

## Опциональные режимы: что всё ещё не является проверенным runtime

| Функция | Стадия | Необходимые внешние условия для полноценного включения |
|---|---|---|
| RAW + REALITY + Vision + Selfsteal | Исходная архитектура проекта, сохранена | Для production ещё нужна собственная приёмка хоста |
| XHTTP + REALITY | Существующий импортируемый шаблон, без смены работающего профиля | Совместимость Remnawave и клиентского транспорта |
| XHTTP + TLS + HTTP/2 | Reference Xray loopback + управляемая Nginx grpc_pass staging-транзакция | Настоящий Xray inbound и тестовая авторизация; совпадение с Panel; тест H2 и откат |
| Hysteria2 | Приватный генератор и строгий статический/read-only runtime syntax gate | Xray бинарник версии с Hysteria, доверенный TLS-cert, отдельный UDP listener/firewall/служба и E2E |
| AmneziaWG2 | Приватные peer-конфиги + криптографическая проверка | Совместимый AWG2 runtime или module, TUN, маршруты, IPv4 forwarding/NAT/UFW, обнаружение пересекающихся подсетей и E2E |
| FinalMask TCP fragment | Реальный CLI «вкл/выкл/числа» для **экспорта клиентского JSON** | Xray клиент с поддержкой FinalMask, совместимость handshake и измерения; не управление подпиской в Panel |
| BBR/CUBIC и qdisc | Диагностика и read-only сравнение; измеренный backlog отдельно | Одинаковые разрешённые сетевые условия для сравнения; никакого автопереключения ядра |

**Почему runtime не включён «автоматом»:** Node_Install не владеет клиентскими профилями Remnawave, системой сертификации других демонов или NAT/файрволом стороннего AWG2. Нельзя превращать reference JSON с `clients: []` в якобы работающий транспорt без аутентификации. Устанавливать сторонние пакеты/службы/модули ядра и менять действующие UFW/NAT ради демонстрации готовности опасно. Пользователь ранее исключил проверки настоящих Panel+Client на VPS, поэтому результат таких функций не может быть **доказан E2E**.

## Безопасность, проверки и откат

- `--finalmask` **не трогает** действующий JSON или VPS. Отмена — продолжать использовать исходный клиентский файл. Для варианта, созданного с `--finalmask enable`, применить `--finalmask disable` к нему в новый файл или не устанавливать экспорт в клиент. Никаких сетевых rollback для этого не требуется.
- `--transport-readiness --xray-bin` только запускает команду `run -test` на **локально доверенном** Xray. Она не изменяет unit, Docker, firewall или Panel. Если Core недоступен, состояние `NOT_VERIFIED`; ошибочный синтаксис — `FAIL`, не `PASS`.
- Старые узкие операции `--site-manager rollback`, `--network-tuning rollback` и `scripts/staging_web_deploy.py xhttp-tls-rollback` сохраняются. Действующие права Selfsteal `root:www-data 0750` не изменены.
- SSH продолжает использовать пароль — это требование владельца, хотя модель root/password остаётся повышенным риском. Каскад Entry/Exit, UFW, Grub и IPv4 остаются без изменений.
- В текущей сборке не выполнены на реальной VPS тесты Remnawave/клиентов, QUIC/AWG, корректности сертификатов/доступа, фактического DPI, скорости и каскадных маршрутов. Не объявлять release production-ready.
