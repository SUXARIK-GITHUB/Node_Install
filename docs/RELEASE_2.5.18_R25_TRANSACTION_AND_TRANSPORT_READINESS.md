# Node_Install 2.5.18 r25 — исправления по независимому аудиту и безопасный второй этап

**Срез:** 2026-11-05. **Статус:** `INCOMPLETE_STAGING_ONLY` — офлайн-кандидат, не production-релиз.
**Исходник:** полный переданный архив r24 (1407 файлов). Исторический GitHub/main по данным предыдущего аудита содержит r19, **не** является исходником r25. Никакие файлы на действующей VPS, в Panel или GitHub не изменялись.

## 1. Что исправлено по подтверждённым воспроизведениям

### 1.1. Прерванный site rollback

В r24 при смене сайта A → B `site_rollback` мог физически вернуть A и записать receipt B со стадией `rolled_back`, но не успеть восстановить активную запись A. Повторная команда отказывала с `NO_SITE_ROLLBACK`.

В `scripts/staging_web_deploy.py` добавлено продолжение такой транзакции: оно проверяет предыдущий подтверждённый receipt, SHA-256 каждого восстановленного файла, запускает уже существующую проверку Nginx/сайта и только затем восстанавливает журнал A. При несоответствии файлов отказывается продолжать; чужие изменения не перезаписывает.

**Если восстановление прервано**, на этой же staging VPS после анализа журнала повторить штатный `sudo bash install.sh --site-manager rollback --confirm-staging`. **Не** удалять журналы вручную. При неподтверждённом состоянии — восстановить проверенный snapshot.

### 1.2. Прерванный сетевой rollback

В r24 `network_tuning.py` мог восстановить ядро и удалить управляемый sysctl-файл до фиксации `rolled_back` в receipt, после чего повторный откат не срабатывал.

Теперь журнал фиксирует `rolling_back` до внесения изменений; восстановление проверяет текущие значения, разрешает только своё старое или утверждённое новое значение, повторяемо возвращает параметры, проверяет readback, удаляет только собственный файл с совпавшим SHA-256, fsync каталога и записывает `rolled_back`. Учитывается также известное прерванное старое состояние r24 (`active` + удалённый конфигурационный файл + исходные значения).

**Изменения сети** остаются прежними по области действия: только `somaxconn` и `tcp_max_syn_backlog` по зарегистрированным ошибкам backlog; BBR, qdisc, маршруты, IPv6, MTU, NAT и firewall не меняются.

### 1.3. Конкуренция транзакций

Операции изменения сети теперь используют общий `/run/lock/vkarmani-node-installer.lock` ДО собственной блокировки; после захвата повторно проверяют `INSTALL_COMPLETE`, системные маркеры и финализационный checkpoint. При чужой/незавершённой операции — `STOP`, без sysctl-изменений. Для offline-тестов блокировка находится в изолированной fixture, а не на реальном хосте.

### 1.4. Частичный результат установки выбранной темы

Если необязательная тема `--site-theme` не публикуется после успешно завершённой базовой установки, теперь выводится `INSTALL_RESULT=PARTIAL CORE=PASS OPTIONAL_SITE=FAILED AUTO_REBOOT=DISABLED` и код возврата **20**. `INSTALL_FAILED` не записывается: базовая нода уже имеет `INSTALL_COMPLETE`. Требуются разбор site-journal и явное повторное развёртывание или rollback сайта. **Не** запускать повторно полный install поверх законченной ноды.

Исправлена документация: чтение `--site-manager status` требует `sudo`, потому что открывает закрытое состояние установленной ноды.

## 2. Optional Transport Readiness Gate

Новый файл `integrations/transport_readiness.py`, CLI `--transport-readiness MODE --bundle DIR --expected-domain FQDN [--role ordinary] [--strict]`.

* **XHTTP + TLS + HTTP/2:** JSON на локальном 127.0.0.1, порт, транспортный path и hostname должны совпадать с конфигурацией `nginx-location.conf`/`grpc_pass`. Отдельно указаны ненастроенный runtime Xray, отсутствие обязательных пользователей/Panel и неиспытанный HTTPS/H2.
* **Hysteria2:** проверяются version=2, транспорт и inbound, пароль сервера/клиента, TLS-сертификат домена, UDP порт, тип outbound. Не настраиваются UDP/UFW/сервис и не проверяется QUIC-клиент.
* **AmneziaWG2:** проверки формата закрытых и публичных ключей X25519, соответствия публичных ключей приватным через OpenSSL, общего PSK, серверного адреса/peer /32, allowed IP, endpoint, MTU, значений Jc/Jmin/Jmax/S1–S4/H1–H4. Не создаются интерфейсы, NAT или системные туннели.
* Приватный bundle не должен содержать symlink/лишние файлы; каталог 0700, файлы 0600; выполнение от root дополнительно проверяет владение. Никакие приватные данные не печатаются.
* Cascade Entry/Exit отказываются принимать прямые optional transport bundles, чтобы не создать незапланированный прямой выход через Entry в обход Exit.

**Пример:**

```bash
# Только на доверенной офлайн/dev-машине: генерация приватного шаблона вне репозитория
umask 077
python3 integrations/optional_transports.py xhttp-tls --domain node.example.com --output /root/xhttp-private
# Проверка без изменений ОС (не требует root, если файлы принадлежат вызывающему пользователю)
bash install.sh --transport-readiness xhttp-tls --bundle /root/xhttp-private --expected-domain node.example.com
# Для автоматизации: пока не подтверждён runtime, всегда REVIEW, exit=2
bash install.sh --transport-readiness xhttp-tls --bundle /root/xhttp-private --expected-domain node.example.com --strict
```

**Важно:** пути, режимы и поддерживаемые аргументы генератора сверять с `python3 integrations/optional_transports.py --help`; пример выше имеет пояснительный характер и должен выполняться в соответствующей тестовой среде. `REVIEW` означает *шаблон статически согласован, но транспорт не развёрнут*; **ни одно поле отчёта не означает доступность VPN**.

## 3. Что из первоначального второго этапа остаётся невыполненным

- Нет подтверждённого автоматического запуска полного **XHTTP/TLS/H2** backend и совмещённого Xray+Panel+Nginx жизненного цикла. Существует генератор, staged-конфиг Nginx с откатом и read-only readiness; это всё ещё не работающий отдельный transport на реальном сервисе.
- Нет безопасной полной установки **Hysteria2** (управление бинарником/версией, сертификатами, UDP/UFW, изолированной службой, обновлением и откатом).
- Нет безопасной полной установки **AmneziaWG2** (соответствующий реальный kernel/userspace, TUN, маршрутизация/NAT, firewall, systemd, конфликты подсетей и откат).
- **FinalMask** не активирован: сервер/клиент и Core compatibility, качество и поведение с REALITY/XHTTP на настоящем потоке не подтверждены.
- Сравнение **BBR/CUBIC**, TCP/UDP и транспортых режимов под идентичной внешней нагрузкой; полноценный MTU blackhole E2E; эффективность против DPI — нет измерений, выводы делать нельзя.
- **Полная Panel+Client проверка VPS сознательно исключена** по пожеланию владельца, поэтому готовность к production заявить нельзя.
- Полного переноса чужих каталогов сайтов нет: 120 тем присутствуют, но 96 основаны на одном тематическом генераторе с 16 семействами оформления. Художественная уникальность 120 самостоятельных проектов не заявляется.

Новые сетевые службы не включены скрытно, сетевые параметры вне двух backlog sysctl не меняются, новые зависимости по умолчанию не добавляются. При последующем согласовании внедрения соблюдать backup/snapshot → тест на staging → readback → журнал → проверка отказа → rollback. SSH-политика остаётся парольной, **SSH keys не внедряются**.

## 4. Безопасные локальные проверки до staging

```bash
bash -n install.sh
python3 -B -m py_compile integrations/transport_readiness.py integrations/network_tuning.py scripts/staging_web_deploy.py
sha256sum --check SHA256SUMS
python3 scripts/verify_release.py --root .
bash tests/run.sh
```

В offline-контейнере команды для реального конфигурационного Nginx, действующих сертификатов, Xray, гипервизора, UFW и клиентского UDP не заменяются заглушками и не выдаются за прошедшие. При отсутствии отдельной тестовой VPS никаких правок production не выполнять.

## 5. Восстановление и обязательные условия

1. До живой установки: проверенный snapshot VPS, внешний консольный доступ, второй действующий парольный SSH-вход, оригинальные конфиги и собственный домен.
2. Перед применением изменить только явно выбранный компонент, не выполнять повторный `install.sh` для ремонта неизвестной незавершённой установки.
3. При откате сети **не** удалять `r23-network-tuning.json` или `98-vkarmani-measured.conf` вручную, иначе потеряется защищённая процедура.
4. При отказе отката сайта повторить только соответствующий `--site-manager rollback`, оценить `NO_VERIFIED_PREVIOUS_SITE_RECOVERY` и сверить файлы; при чужом изменении — остановиться.
5. После сетевых изменений проверять SSH, Nginx, Node API, sysctl readback, tcp counters, journal и внешнюю доступность; при отказе использовать проверенный snapshot.

Разработчику на следующем этапе: `docs/MAINTAINER_HANDOFF_R25.md` содержит карту каталогов, контракты и приоритеты.
