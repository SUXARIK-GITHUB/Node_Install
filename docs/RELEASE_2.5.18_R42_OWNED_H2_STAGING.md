# Node Install 2.5.18 r42 — проверяемое HTTPS-прикрытие и staging-контур

**7 ноября 2026** · `INCOMPLETE_STAGING_ONLY` · основа — полный проверенный архив r41.

Это изменение **только** проверяемости/маскировки. **Не** изменены рабочие настройки Xray/REALITY, TLS/Nginx, Remnawave, Docker, UFW/SSH, ключи, каскад и пользователи. Новые TCP/TLS-запросы выполняются **только по запросу оператора**, из внешнего диагностического скрипта на указанный **собственный публичный IPv4**.

## Что изменилось

1. **Новые Ordinary-ноды из полного проверенного архива больше не получают одну и ту же тему.** `scripts/site_default.py` детерминированно выбирает один из 120 существующих проверенных сайтов по публичному FQDN. Это не случайная смена сайтов во время работы, не защита от всех методов идентификации и не гарантирует уникальности между двумя доменами. Выбор выполняется **после основного commit**, до прежнего `site-deploy`, который атомарно публикует сайт и откатывает изменения при ошибке. В лог пишется ID темы, а не секреты. Явный `--site-theme` всегда имеет приоритет. При повторной установке, для Entry/Exit и standalone `install.sh` работа не меняется. Если полный каталог повреждён — fail closed до изменения ОС; если выбор/публикация не удались после commit — отдельная ошибка необязательного сайта, без автоматического reboot.
2. **Настоящий HTTP/2-запрос, а не только ALPN.** `scripts/stealth_external_audit.py --http2-actual` использует установленный *внешне*, у оператора, `curl` с проверкой публичного CA, TLS 1.3, `--http2`, жёсткой привязкой DNS `--resolve domain:443:OWN_IP`, без редиректов/системных прокси/.curlrc, с ограничением времени и без сохранения тела/заголовков. Успех означает, что получен HTTP/2 `200` с собственного сайта — **не означает** отсутствие DPI-отпечатков. Если curl не установлен или не собран с HTTP/2, итог `UNVERIFIED`, а не ложный `PASS`.
3. **Проверка управляющего Node API.** `--node-api-port N` создаёт **одно** TCP-подключение к явно названному порту того же собственного IPv4. Никакого перебора портов и API-запросов. Доступность — `REVIEW`, явный TCP refusal — `PASS` только с текущей точки наблюдения, таймаут/фильтрация — `UNVERIFIED`. Проверку выполнять **с внешнего хоста, который не добавлен в allowlist панели**; иначе результат не доказывает ошибку firewall.
4. **Тест через работающий клиентский SOCKS5.** `--client-socks5-port 10808` выполняет один HTTPS/2-запрос через **уже работающий** локальный SOCKS5, только `127.0.0.1:PORT`, к собственному домену/IP; пароли, Xray-конфиги и client URI в диагностический инструмент не передаются. Если оператор запустил тестовый Xray с REALITY outbound и указанным локальным SOCKS5 inbound, запрос способен проверить живую связку. Но **сам SOCKS5-ответ не доказывает**, что клиент действительно использовал REALITY или не обошёл туннель через direct. Проверить это отдельно в клиентской маршрутизации и (при необходимости) собственной сетевой трассировке. В отчёте `reality_transport_proven=NO`.
5. Расширен `scripts/stealth_report_compare.py` для сравнения необязательных проверок r42. Проверки предыдущих r30–r41 **сохранены** и применяются в `scripts/verify_release.py` также для r42. Добавлены регрессионные тесты на безопасные параметры curl, валидацию целей, ошибки сертификатов, недоступность инструмента, однократный TCP-dial и жизненный цикл выбора темы.

## Порядок испытаний на **собственном** staging

1. Создать **snapshot** VPS, убедиться, что есть аварийная консоль, записать версию Xray/RemnaNode/клиента. Не менять работающие профили или ключи.
2. На новой тестовой Ordinary-нoде развернуть **полный проверенный архив**. Убедиться, что в журнале установки `SITE_DEFAULT=VERIFIED_CATALOG; theme=DOMAIN_DERIVED_AFTER_COMMIT`, а затем `SITE_THEME=PASS theme=...`. Повторный запуск не должен менять тему. При необходимости задать явную тему `--site-theme` перед первой установкой.
3. Из **другой собственной машины** (не в allowlist панели) выполнить:

   ```bash
   umask 077
   python3 scripts/stealth_external_audit.py \
     --domain node.example.com --ip YOUR_OWN_PUBLIC_IPV4 \
     --confirm-owned-endpoint --http2-actual --parallel 4 \
     --node-api-port YOUR_NODE_PORT > own-stage-r42.json
   ```

   В примере **заменить** имена/адреса/порт. Не направлять на сторонние серверы. Не запускать аудит на самой ноде для оценки внешней доступности API: точка наблюдения и firewall-правила могут отличаться.
4. Запустить **отдельно**, на собственном тестовом компьютере, заранее проверенный Xray-клиент с REALITY outbound и локальным SOCKS5 inbound (`127.0.0.1:10808`). Затем выполнить тот же аудит с флагом `--client-socks5-port 10808`. Должен получиться действительный HTTPS/2-запрос. В клиентской конфигурации отдельно убедиться, что этот домен не уходит через `direct` или системный bypass. Сравнить с клиентом, у которого outbound отключён. Не помещать живые `privateKey`, `pbk`, UUID, ShortID, ссылки и токены в команды, документы или отчёты.
5. Сравнить обезличенные результаты до/после: `python3 scripts/stealth_report_compare.py before.json after.json --strict`. Не делать выводов о DPI по обычному HTTPS/2. Для настоящей проверки TLS 1.3 post-handshake и fingerprint нужен ограниченный пакетный захват **только собственного staging-трафика**, с отдельными тестовыми учётными данными, без публикации PCAP с чужими соединениями.
6. Проверить HTTPS после перезагрузки, продления сертификата, недоступности Nginx/socket, нескольких соединений и отказа сети. Отдельно проверить DNS/IPv6/UDP/direct и Entry/Exit с собственным тестовым клиентом.

## Границы безопасности и откат

- Скрипт не сканирует диапазоны адресов, не делает перебор портов, не использует HTTP redirect, не выполняет активные протокольные атаки и не собирает закрытые данные сервера. Аргументы `--domain`/`--ip` обязаны пройти валидацию; `--confirm-owned-endpoint` обязательно. Без необязательных флагов осталась диагностика r41.
- Обновление *существующей* ноды автоматическим выбором сайта **не предусмотрено**. Если новая установка завершилась частичным отказом при публикации, сайт восстанавливается существующим rollback-журналом; проверьте `--site-manager rollback --confirm-staging` **только после изучения receipt и сохранения snapshot**.
- В случае аварии ОС/SSH/GRUB — восстановить snapshot хостера через аварийную консоль. Отдельные диагностические инструменты не меняют сетевые правила, поэтому сами не требуют server rollback.
- **Недоказано без реальной среды:** ClientHello REALITY, session tickets/post-handshake, устойчивость к DPI и активному сканированию, отсутствие direct/DNS/IPv6-утечек, корректность подписок XHTTP, безопасность конкретной клиентской конфигурации. `PASS` диагностического HTTP/2 не равен «незаметен».

## Инженерные проверки релиза

`bash -n install.sh`, компиляция Python, `scripts/verify_release.py --root .`, `scripts/site_audit.py --rich`, изолированные r42 и все регрессионные тесты, сравнение состава с r41, чистая распаковка итогового ZIP и `sha256sum --check`. Итоги полного прогона находятся в отдельном отчёте QA и **не** являются E2E тестированием на реальной VPS.
