## Что уже было полезным и сохранено

Исходник не был пустой заготовкой: уже существовали проверки входов, выбор IPv4 по DNS на multi-IP VPS, схема RAW/REALITY с локальным Nginx Selfsteal, image digest, проверка API TLS, фрагментированный ClientHello, postboot-диагностика, закрытое хранение и repair-команды. Эти механизмы не заменялись сторонним «универсальным установщиком».

Сохранён один самостоятельный `install.sh`, который содержит собственные helper payload и конфигурации. Нет нового backend, БД, панели, reverse proxy контейнера, очереди, Watchtower, CrowdSec или зависимостей от внешних shell-скриптов. Nginx остаётся на хосте; RemnaNode — один официальный контейнер. Тестовые зависимости не становятся дополнительными runtime-сервисами.

## Найдено → риск → решение

| Область | Исходная проблема/ограничение | Что изменено в 2.0.0 | Что осталось проверить/учесть |
|---|---|---|---|
| Три входа | Неочевидный порядок и смешение ожиданий «нода готова»/«панель настроена» | Ключ → домен → egress IPv4 технички; шаблон/guide отдельно | Панель не настраивается без административного токена |
| SSH | Сохранение старой политики не гарантировало требуемый парольный вход | First-value-wins managed block, password yes, existing ports, refusal чужих Match/Allow/Deny | Live sshd/PAM/socket switching и внешний вход не проверены здесь |
| Reboot | Для полного IPv6-off нужен reboot, но бесконтрольная перезагрузка опасна | 2.1.2: один reboot после успешной установки включён по прямому требованию оператора, задержка 30 сек через systemd; `--no-reboot` — явный opt-out; weekly reboot остаётся opt-in | Нужны snapshot и console/recovery; ошибка scheduler требует ручного `sudo reboot` |
| Пакеты | Смешение установки ноды и обслуживания/массового обновления ОС | Только нужные пакеты, no-remove, без full-upgrade/autoremove | APT install может обновлять необходимые зависимости; это не «ОС вообще не меняется» |
| Повторный запуск | Полный установочный путь не подходил как безрисковая кнопка проверки/обновления | Complete → diagnostics only; same-generation incomplete resume | Не общая миграция 1.3.x → 2.0.0 |
| Firewall | Нельзя безопасно сбрасывать произвольный existing stack | Refusal чужих UFW/nftables/iptables/сервисов/конфигов | Provider firewall вне контроля; IPv4 source панели нужно знать правильно |
| SSH/UFW guard | Требовалось более явное состояние и исключение гонки таймера/disarm | Lock, armed/running/done, сохранение marker при fail | Не полный rollback и не доказательство внешнего входа |
| Fail2ban | UFW profile/action не должен случайно банить все порты источника | Собственное действие с обязательными SSH port/proto, no постоянного bypass IP технички | Реальное событие ban/unban на supported distro ещё требует стенда |
| Docker privileges | NET_ADMIN и весь host `/dev/shm` давали лишние полномочия | Отдельный read-only socket directory, NET_ADMIN opt-in, NET_RAW drop | Некоторые IP-management функции upstream требуют capability; root/host net остаются риском |
| Socket lifecycle | Bind отдельного inode или общего shm не соответствовал минимальному доступу/перезапуску | Bind каталога, tmpfiles создание, отдельные host/container paths | Реальный Docker bind после boot/recreate не запускался здесь |
| Nginx | Нужно учитывать разные поколения HTTP/2-директив | Version gate старого `listen … http2` и нового `http2 on` | Реальный тест выполнен на Nginx 1.26.3, не всех distro builds |
| API TLS/SNI | Более новые Node могут проверять не публичный домен, а derived SNI | Upstream-compatible HKDF SNI, CA+leaf pin, не ослаблен mTLS | Это локальная проверка server side TLS, не авторизация панели |
| Сеть | Жёсткое требование BBR/fq не подходит каждому provider kernel | Write/readback, безопасный fallback и DEGRADED, без обязательной загрузки отсутствующих модулей | Скорость/справедливость очередей нужно измерять по реальному пути |
| MTU | Нет универсальной MTU-цифры для разных хостеров | `tcp_mtu_probing=1`, без ручной смены MTU/MSS/offload/routes | Не решает любые UDP/MTU/ICMP/маршрутные проблемы |
| Профиль | Защита internal destinations и сохранность пары ключей требуют проверки | Routing блокирует внутренние и management IP; X25519 pair validation, ключи не ротируются молча | Профиль импортируется/назначается панелью, не становится live сам |
| Image update | Изменение image не должно повторно трогать систему | Отдельный transaction helper, backup, digest, health, rollback attempt | Нет гарантии writable-layer/data rollback или работы при offline panel |
| Очистка | Удаление образов/пакетов может разрушить rollback или чужие данные | Только APT cache/ограниченные старые журналы, общий lock | Backups растут, нужен контроль свободного диска |
| Документация | Краткого README недостаточно для разных провайдеров и восстановления | Install вверху, checksum, traffic map, port matrix, регламенты, источники/тесты | README не заменяет проверку конкретного VPS и версии панели |

## Неочевидные архитектурные решения

### Нет автоматического управления панелью

Запрошенный секрет RemnaNode — bundle служебной криптографии. Административные действия над панелью потребовали бы иного credential и дополнительного API-контракта. Добавлять скрытый способ авторизации, извлекать чужие сессии или обещать создание Host/Squad по трём данным было бы неверно. Вместо этого генерируются готовый JSON и адресная инструкция.

### Не расширена поддержка загрузчиков «наугад»

Пользователь требует полностью не использовать IPv6. Простого sysctl недостаточно для утверждения, что AF_INET6 недоступен. Сохранён явный контракт GRUB + kernel parameter + reboot verification. Наличие `/etc/default/grub` не является абсолютным доказательством загрузки именно через этот файл у любого хостера, поэтому важна фактическая проверка после reboot. Прямое вмешательство в неизвестный EFI/systemd-boot/kexec без стенда не добавлялось.

### Не обещается отсутствие downtime при обновлении

Compose recreates контейнер при смене image; существующие клиентские сессии могут оборваться. Современный RemnaNode и панель должны согласованно восстановить profile/users. Сохранение Compose/image не равно сохранению текущего writable layer контейнера. Поэтому pending/rollback статусы отделены от подтверждения VPN.

### Диагностика не выдаёт partial success за полную приёмку

`NODE_LOCAL_CHECKS=PASS` — только проверенные локальные условия. `PANEL_CONNECTION=NOT_VERIFIED` выводится намеренно. `--require-xray` отдельно требует слушающий 443 и точный cover body, но всё ещё не проверяет аутентификацию реального клиента, его Host/Squad и международную доступность.

## Остаточные риски, требующие решения оператором

Парольный root SSH без allowlist — осознанное требование, не «максимально безопасный SSH». Сильный пароль и Fail2ban снижают часть рисков, но не устраняют credential theft и distributed brute force. Наличие NET_ADMIN при opt-in увеличивает blast radius upstream-багов. Host networking сохраняет доступ к сетевому пространству VPS.

`latest` — источник первой установки, не обещание совместимости с любой панелью. В эксплуатации нужен проверенный image digest и canary. Supply-chain компрометацию namespace один digest не исключает. Обновления Docker/ОС/RemnaNode должны проходить отдельный review.

VPS с NAT, IPv6-only DNS/egress, внешним ACL, нестандартным boot, ограниченным ядром или изменяемым egress IP панели требуют другого согласованного проекта, а не обхода preflight. Высокая загрузка CPU/диска, packet loss, overselling и ограничения международного маршрута установщиком не устраняются.

Backups закрыты по правам, но не шифруются и не уходят off-host автоматически. Их проверка checksum/readability не равна restore drill. Массовая production-раскатка до успешного canary install/reboot/backup-restore/panel/client теста не рекомендована.
