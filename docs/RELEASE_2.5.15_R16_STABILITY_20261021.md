# VKARMANI Node Install 2.5.15 r16 — анализ стабильности 50+ клиентов на ноду

**Дата:** 2026-10-21. **Статус:** `INCOMPLETE_STAGING_ONLY`. Этот документ относится к архиву r16, не к GitHub `main` и не к действующим VPS. Ни один production-сервер не менялся. Предыдущая база: полный архив 2.5.14 r15. Протоколы REALITY/RAW/XHTTP, Nginx Stream Selfsteal и каскад не изменены.

## Что реально выявлено в исходниках

1. На новой Ordinary-ноде 2.5.14 ранее **автоматически включался** `vkarmani-node-nightly.timer`. В 03:00–04:00 Europe/Moscow он запускает сервис, перезапускающий `remnanode`. Даже без ошибки ядра это обрывает активные TCP/UDP соединения, игры и потоки. На r16 для **НОВЫХ Ordinary** таймер установлен, но по умолчанию выключен (`install-only`); ручной `--maintenance-enable` остаётся. Если реальная жалоба не приходится на это время, причиной могут быть другие факторы. Старые ноды **не мигрируются**.
2. Основные параметры Linux в r15 уже включали `net.core.default_qdisc=fq`, `net.ipv4.tcp_congestion_control=bbr`, `net.ipv4.tcp_mtu_probing=1`. Это не доказательство правильного active qdisc для каждого реального интерфейса и не гарантия стабильности. Без данных менять sysctl опасно.
3. Авторизованные клиентские потоки обрабатываются Xray; Nginx Stream/HTTP Selfsteal обрабатывает TLS fallback на локальном Unix socket, а не основной клиентский upstream. Следовательно, диагностику нагрузки клиентов следует начинать с CPU, Xray, Docker, соединений, интерфейса и внешнего пути, а не с повышения Nginx `worker_connections` или `proxy_read_timeout`.
4. Обычный RAW-профиль продолжает блокировать `bittorrent` через routing; разрешить торренты — **отдельное изменение политики**, а не ускорение. Учитывать правила клиента, панельные правила, лимиты и реальный upstream.
5. На CPU с 1–2 vCPU и RAM около 1 GiB нельзя гарантировать высокую нагрузку ~50 активных клиентов, многопоточное 8K, игры и P2P одновременно. Состав пользователей (100 зарегистрированных ≠ 100 одновременно активных), скорость порта хостера, steal CPU, swap, NIC drops, потери у ISP определяют ёмкость.

## Новые read-only измерения

Команда после установки на **локальной ноде** (если используем установленную сборку, не запускайте установщик r16 поверх старой ноды):

```bash
sudo bash ./install.sh --diagnose-resources --seconds 15
```

Она снимает два набора счётчиков; не меняет sysctl, Docker, маршруты, UFW, Nginx, файлы конфигурации или секреты. Вывод JSON:

- `tcp_delta`, `tcp_ext_delta`: перепередачи, тайм-ауты, потери listen backlog, reset, SYN; счётчики **всего хоста**. Значения могут не существовать на некоторых ядрах.
- `udp_delta`: `InErrors`, `RcvbufErrors`, `SndbufErrors`, `NoPorts` за интервал. Рост указывает на локальную проблему UDP или политику приложений, но не является доказательством DPI.
- `softnet_delta`: обработанные пакеты, drops и `time_squeeze` по CPU (/proc/net/softnet_stat). Рост под нагрузкой может означать нехватку времени CPU/сетевого softirq. Он не равен потерям конкретного клиента.
- `netdev_delta`: изменения счётчиков `/proc/net/dev` по non-loopback интерфейсам; rx/tx bytes, packets, errors, drops и рассчитанные Mbps **отдельно по интерфейсам**. Виртуальные интерфейсы могут отражать повторный учёт одних пакетов. Нельзя суммировать Mbps на всех интерфейсах как «реальная WAN пропускная способность».
- `cpu`, `memory`, `pressure`, `daemon_fds`, `container`, `conntrack`, `root_disk`, `selfsteal_socket_queue`: уже имевшиеся диагностические срезы.

Нулевая дельта не гарантирует отсутствие клиентских потерь. При смене интерфейса/топологии или сбросе счётчика возвращается `verified=false`/`null`, а не выдуманное «0». `--strict` может вернуть ненулевой код при неполных данных; это сигнал для анализа, а не разрешение изменять настройки.

## План сравнения исправных и проблемных клиентов

**Контрольная группа:** на одной и той же ноде собрать профили клиентов (без UUID и приватных ключей): версия приложения и встроенного Xray, Android/iOS/Windows, RAW vs XHTTP, `flow`, протокол TUN vs system proxy, Wi-Fi vs LTE, оператор/ASN, дата-время с часовым поясом, наличие проблем именно в TCP/UDP, время после последнего смены сети.

**Сервер:** измерить одновременно при простое и под нагрузкой: `--diagnose-resources --seconds 15`, реальный CPU steal, активные docker restart count, OOM, память, FD, conntrack, ошибку интерфейса, доступную WAN-скорость, RTT к нескольким направлениям. Проверить включён ли `vkarmani-node-nightly.timer`; сопоставить журнал service с точным временем обрыва.

**Сеть:** три независимых теста на одной VPS и у одного провайдера: (1) контролируемый однопоточный TCP, (2) многопоточный TCP + параллельная игровая UDP-нагрузка, (3) клиент с VPN и без VPN до сопоставимого узла. Соблюдать нагрузочные лимиты хостера. Сравнивать p50/p95 RTT, jitter, packet loss, long stalls, Gbit/s и загрузку CPU; не запускать агрессивную нагрузку на production без разрешения.

**Диагноз по симптомам:**

| Наблюдение | Что проверять |
| --- | --- |
| Обрывы в 03:00–04:00 МСК | Nightly timer, контейнерный restart, журнал systemd |
| Только XHTTP, особенно при переключении Wi-Fi/LTE | Версия Xray клиента/серверной стороны, Go HTTP/2/dial pooling, переподключения, фактическая версия core; не обещать автоматический fix у приложений |
| Только игра/голос, TCP загрузки в порядке | UDP ошибки, MTU/path, мобильный оператор, режим TUN, очередь softnet |
| На всех устройствах одной ноды одновременно | CPU steal, OOM, upstream link saturation, NIC drops/errors, коннтрак, провайдер VPS |
| Только один оператор/ASN/сеть | маршрут/фильтрация/связь у данного провайдера; смена сайта-прикрытия не устраняет блокировку IP |
| Длительное 8K и P2P при высокой загрузке | транзитная скорость сервера, fairness между потоками, bufferbloat/latency под нагрузкой |

## Xray и признаки проблем (не считать доказанным на наших нодах)

- 2026-09-21–10-18, XHTTP `xmux.maxConnections` на Go 1.27: https://github.com/XTLS/Xray-core/issues/6797 . Автор подтвердил восстановление соединительного coalescing в официальном Xray v26.10.17. Нужно проверить **точный Xray у проблемных клиентов**, серверный образ и историю его сборки до обновлений. Без теста откаты/переходы не выполнять.
- 2026-10-15, Vision лишняя padding-CPU-нагрузка в частном случае: https://github.com/XTLS/Xray-core/issues/7164 . Это открытое сообщение исследователя о воспроизводимом сценарии, не диагноз каждой VLESS-ноды.
- 2026-10-15–17, отдельный SIGSEGV для Vision/REALITY на определённой Go-сборке: https://github.com/XTLS/Xray-core/issues/7162 (закрыто после fix). Проверить версии, не выбирать «последний» контейнер по одному имени тега.
- 2026-10-08, UDP burst path конкретного tunnel/dokodemo: https://github.com/XTLS/Xray-core/issues/7106 . Не экстраполировать автоматически на наш inbound.

## Скрытность / SNI / TLS — реалистичные ожидания

- REALITY и внешняя SNI-цель не делают IP VPS IP-адресом чужого крупного сайта. При сравнении сетей видны IP/ASN, тайминги, TCP handshake, отдельные шаблоны запросов; абсолютной невидимости нет.
- Не добавлять случайное MTU/TCP-фрагментирование, искусственные задержки, padding или включение UDP-over-TCP как «усиление защиты»: это может ухудшить игровой ping, потери и загрузки, а эффект против DPI не подтверждён.
- TLS uTLS fingerprint зависит в том числе от клиентского приложения/ядра; серверное изменение Nginx fallback не меняет автоматически отпечатки авторизованных клиентов.
- Актуальная проверка у разных операторов нужна отдельно от замеров качества. Проверять настоящую доступность, а не только показания Nginx локально.

## Rollback и развёртывание

- r16 **не предназначен для запуска на уже установленной production-ноде**. Не пересоздавать VPS ради смены nightly timer. Для существующих нод сначала сделать backup и провести **read-only** проверку состояния таймеров и сервисов. Изменение их режима — отдельное согласованное действие.
- Для staging перед инсталляцией snapshot VPS, проверка восстановления из snapshot, запасная консоль хостера. Повторный запуск только через официально поддержанный `--finish-install` после диагностики; не обходить fail-closed проверки.
- После staging проверить инсталляцию, полную перезагрузку, API панели, RAW/XHTTP реальные TCP/UDP, Selfsteal TLS, аварийное восстановление, отключённый timer, диагностику в простое и под синтетической нагрузкой, а также `systemctl list-timers`.
- Rollback **новой тестовой ноды** при системной проблеме — восстановление полного снимка VPS. Старые ноды не затронуты новой ZIP.

**Итог:** единственная подтверждённая кодом причина неизбежных плановых разрывов — ежедневный рестарт. Для всех остальных жалоб необходимы наблюдения на VPS и у клиентских групп; автоматическая универсальная настройка сетевого ядра не обоснована.
