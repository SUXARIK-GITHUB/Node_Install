# 🚀 Установка ноды — VKarmani Node Install 2.1.0

**Запускать на отдельной чистой VPS-ноде, не на сервере панели.** До запуска сделайте снимок VPS, проверьте консоль хостера и действующий пароль администратора. Скрипт меняет SSH, UFW, системные настройки и GRUB. По умолчанию **не перезагружает** сервер.

### Установка с GitHub

Команда скачивает **сначала весь файл**, сверяет SHA256 именно этой версии, проверяет Bash-синтаксис и только затем запускает. Нужен установленный `curl`. Три ответа считываются из терминала, поэтому heredoc не мешает вводу.

```bash
sudo bash <<'INSTALL'
set -Eeuo pipefail
set +x
umask 077
command -v curl >/dev/null || { echo 'Нужен curl; другой вариант — install.sh из полного архива.' >&2; exit 1; }
work=$(mktemp -d /root/vkarmani-install.XXXXXXXX)
cd "$work"
curl --fail --show-error --silent --location \
  --proto '=https' --proto-redir '=https' --tlsv1.2 \
  --connect-timeout 15 --max-time 180 --retry 3 \
  'https://raw.githubusercontent.com/SUXARIK-GITHUB/Node_Install/main/install.sh' \
  --output install.sh
if ! printf '%s  install.sh\n' \
  '9420c5a76749fd0ae52c26279e78069fca42b40d8a7bae9d80b950a89b3f976c' \
  | sha256sum --check; then
    echo 'STOP: файл GitHub не совпадает с выпуском 2.1.0. Не запускаю; нужен новый install.sh в main либо файл из архива 2.1.0.' >&2
    exit 1
fi
bash -n install.sh
[[ $(bash install.sh --version) == 2.1.0 ]] || { echo 'STOP: неверная версия установщика.' >&2; exit 1; }
exec bash install.sh
INSTALL
```

**Этот способ начнёт устанавливать 2.1.0 только после публикации её `install.sh` в `main`.** Пока в GitHub другой файл, проверка остановится — не отключайте проверку хеша ради обхода. При выпуске следующей версии обновите файл, README и контрольные суммы вместе. SHA256 защищает от несовпадения файла с полученным README, но не заменяет доверие к источнику самого README.

Репозиторий: [SUXARIK-GITHUB/Node_Install](https://github.com/SUXARIK-GITHUB/Node_Install). Сам файл: [install.sh](https://raw.githubusercontent.com/SUXARIK-GITHUB/Node_Install/main/install.sh).

### Установка из полного архива

Распакуйте архив в отдельную папку и перейдите в `Node_Install`. Ничего не копируйте поверх `/etc`, `/opt` или работающего проекта ноды вручную.

**GitHub Desktop / существующий clone:** новый архив содержит полный рабочий проект, но намеренно **без `.git`**, чтобы не перезаписать вашу актуальную историю старой копией. Обновляйте файлы внутри существующего clone, сохраняя его `.git`; не удаляйте папку подключённого репозитория целиком. Метаданные `.git` из исходного архива 2.0.2 сохранены отдельно в `Node_Install_2.0.2_git_metadata_backup.zip` как резервная копия, не как способ обновления репозитория. Не используйте force push или `reset --hard` для согласования истории.

```bash
sha256sum --check SHA256SUMS
bash -n install.sh
sudo bash install.sh
```

> **Первый запуск спрашивает ровно три значения:** `SECRET_KEY` → **домен ноды** → **исходящий публичный IPv4 технички**. Пароль SSH, адрес ноды, email, SSH-ключ, API-токен панели и Cloudflare-токен не запрашиваются. Пароль для `sudo`, если он требуется вашей системой, не является вопросом установщика.

После установки **не закрывайте старую SSH-сессию**: сначала откройте вторую по IPv4 и проверьте вход по паролю. Затем выполните запланированную ручную перезагрузку:

```bash
sudo reboot
# После повторного подключения:
sudo vkarmani-node-check
```

Для работающего VPN нужно также назначить профиль/Host/доступ пользователя в панели. Порядок ниже: [действия в Remnawave](#-что-остаётся-сделать-в-панели).

## ✨ Сайт и диагностика без переустановки работающей ноды

После проверки полного архива и `install.sh` новой версии:

```bash
# Только одностраничник; отдельная проверенная копия и локальная приёмка.
sudo bash install.sh --update-cover

# При необходимости — только возврат страницы из сохранённой копии.

sudo bash install.sh --diagnose-resources --seconds 5
```

Сначала snapshot и сохранённый проверенный файл установщика. После обновления страницы проверьте сайт извне и действующий VPN. Нулевой риск не обещается. ## 🛡️ Условия версии 2.1.0

**Новое в 2.1.0:** адаптация Ubuntu 26.04 / Resolute; сохранение Chrony sources/NTS; необязательная APT-очистка с отдельным статусом; новый статический одностраничник; отдельные `--update-cover` / `--rollback-cover` для работающей **2.0.3 или 2.1.0**; read-only `--diagnose-resources`. Ровно три вопроса сохранены. [Обоснование и источники](docs/IMPROVEMENTS_2.1.0.md).

**26.04: код адаптирован, полная приёмка на VPS ещё не выполнена.** Docker официально поддерживает этот выпуск, но это не заменяет тест install → панель/клиент → reboot → renew → rollback нашего проекта. [Матрица, требования и проверки](docs/UBUNTU_26_04.md).

**Работающую 2.0.3 не переустанавливайте.** Для одного сайта используйте проверенный новый файл с `--update-cover`, а не полный запуск. Откат: `--rollback-cover`. Это не обновление системы, образа или всех установленных helpers. [Порядок, backup и границы](docs/COVER_SITE.md).


**Сохранено исправление 2.0.3:** установка больше не требует заменить уже установленный `systemd-timesyncd` на `chrony`. Установленный поддерживаемый NTP-клиент сохраняется; если нет обоих — выбирается Chrony. Общий запрет удаления пакетов сохранён: сначала проверяется APT-план, затем установка выполняется с тем же `--no-remove`. Проверка времени, backup и postboot учитывают выбранную службу. [Причина, продолжение и ограничения](docs/TIME_SYNC_FIX.md).

**Точное раннее прерывание 2.0.2 с `rc=100 line=2761`** может быть продолжено 2.1.0 автоматически, но только после проверки private state, контрольной суммы старого helper и отсутствия поздних стадий. Сначала создаётся и проверяется новая закрытая копия, затем меняется маркер версии. Сохранённые три значения и ключ повторно не спрашиваются. Это исключение для конкретной стадии, не общий `--force` и не миграция работающих нод.

**Исправление 2.0.2:** устранён ложный STOP на выключенном UFW без добавленных правил, когда `user.rules` содержит только стандартные `ufw-user-limit*`. Проверяются оба файла `user.rules` / `user6.rules`, причём IPv6 не включается. Допускаются только пустые поддерживаемые шаблоны и точные служебные правила; настоящие правила, ручные изменения и неизвестный формат по-прежнему останавливают установку. Никакого `ufw reset` для обхода ошибки. [Причина, тесты и продолжение после STOP](docs/UFW_PREFLIGHT_FIX.md).

**Только VLESS RAW REALITY + Selfsteal на своём домене.** XHTTP, WebSocket, Trojan, сторонние сайты для SNI/target и российский мост не добавлены. Проверка локального JSON не означает, что панель уже передала именно его в Xray. Домен, сертификат, SNI в профиле/Host/клиенте и адрес ноды должны быть согласованы; владение доменом подтверждает оператор.

В этой версии исправлены зависание HTTP/2-проверки на странице более 65535 байт, восстановление Nginx после оставшегося Unix socket, незавершённые дочерние процессы maintenance и пропуск отсутствующих UFW-разрешений в диагностике. Добавлены проверка загруженного сертификата и ограничения общего времени проверок. Обзор причин и тестов: [FAILURE_AUDIT](docs/FAILURE_AUDIT.md).

**Замена папки репозитория не обновляет уже установленные helpers на VPS 2.0.0/2.0.1/2.0.2/2.0.3.** Обычный повторный запуск на завершённой ноде по-прежнему только запускает установленную диагностику. `refresh-image` обновляет образ, а не установщик. Автоматическая миграция действующей 2.0.0/2.0.1/2.0.2/2.0.3 в этом выпуске не реализована; не подменяйте version markers и не удаляйте конфиги ради её обхода. Новая установка — на чистой тестовой VPS, затем приёмка и тиражирование. Детали: [совместимость](docs/OPERATIONS.md#обновление-исходников-и-уже-установленная-200).

Совет «оставить только 443» **не применяется**: существующие SSH-порты остаются доступными по паролю со всех адресов, кроме временных SSH-блокировок Fail2ban; HTTP/80 нужен текущему ACME HTTP-01. API ноды разрешён только с IPv4 панели. Автоматической смены IP/DNS или перезапусков «при подозрении на блокировку» нет.

## 🔑 Три значения и откуда их взять

| Вопрос | Что вводить | Что не подходит |
|---|---|---|
| `SECRET_KEY` | Полное значение `SECRET_KEY` из конфигурации RemnaNode, которую выдаёт ваша панель | API-токен панели, пароль, случайная строка, ключ от другой панели |
| Домен ноды | Например, `ee1.example.com`: одна DNS A-запись на публичный адрес этой VPS | `https://…`, путь, порт, домен панели, проксируемая Cloudflare-запись |
| IPv4 технички | Публичный **исходящий адрес backend панели**, с которого она подключается к API ноды | Адрес администратора, DNS-IP Cloudflare, частный IP Docker, IPv4 самой ноды |

Ввод ключа скрыт. Допустимы значение без обёртки и скопированная форма `SECRET_KEY=…`; всё равно нужен именно полный секрет одной строкой. Установщик проверяет структуру base64/JSON, сертификаты, подпись CA, соответствие сертификата приватному ключу и публичный JWT-ключ. Сроки сертификатов повторно проверяются после синхронизации времени.

**Адрес ноды определяется автоматически:** публичные DNS A/AAAA проверяются через системный резолвер и доступные публичные резолверы, затем A сопоставляется со всеми публичными IPv4, реально назначенными интерфейсам. На VPS с несколькими адресами выбирается адрес домена, а не случайный адрес внешнего запроса. При противоречии DNS, нескольких A, AAAA, NAT или чужом IP установка останавливается.

DNS домена панели **не используется** как способ узнать IP технички: при Cloudflare он часто указывает не на backend. Для исходящего NAT нужен его стабильный внешний адрес. Если backend работает через IPv6-only egress или его IPv4 регулярно меняется, эта схема из трёх значений без отдельной настройки не подходит.

## ✅ Требования к VPS и DNS

| Параметр | Условие |
|---|---|
| ОС | Чистая Ubuntu **22.04 / 24.04 / 26.04** (26.04 требует отдельной VPS-приёмки) или Debian **12 / 13** |
| Архитектура | `amd64` или `arm64`; архитектура образа RemnaNode должна существовать в выбранном реестре |
| Виртуализация | Полноценная VM/выделенный сервер со своим управляемым ядром; не LXC/OpenVZ/Docker |
| Загрузка | `systemd`, действующий GRUB, `update-grub`, `/boot/grub/grub.cfg` и `/etc/default/grub` |
| RAM | >=900 MiB MemTotal; для Ubuntu 26.04 >=1536 MiB. Пилот 26.04 лучше на VPS от 2 GiB RAM; это не оценка пользовательской ёмкости |
| Диск | >=6 GiB свободного места перед установкой; backups/образы требуют дополнительного места |
| Сеть | Публичный IPv4 назначен интерфейсу VPS непосредственно; стабильный IPv4-доступ к DNS, NTP, APT, Docker Registry и ACME |
| SSH | Текущая сессия по IPv4; действующий локальный пароль root либо пользователя, запускающего через sudo |
| DNS ноды | Ровно одна публичная A-запись на локальный IPv4 VPS; нет AAAA; Cloudflare **DNS only**, серое облако |
| Чистота сервера | Нет чужих контейнеров, активного web/firewall-стека, пользовательских правил UFW/nftables/iptables и конфликтующих Docker-пакетов |
| Восстановление | Доступна проверенная консоль/recovery хостера и снимок VPS до изменений |

**Это проверяемые ограничения, а не обещание совместимости со всеми тарифами и провайдерами.** Например, systemd-boot, NAT VPS и IPv6-only хостинг автоматически не адаптируются. Скрипт не переустанавливает загрузчик, не меняет netplan, не переназначает IP и не удаляет чужие настройки ради продолжения.

Если нет `curl`, можно установить только средство скачивания из репозитория ОС либо передать архив по SFTP:

```bash
sudo apt-get update
sudo apt-get install --no-install-recommends curl ca-certificates
```

### Порты на UFW и во внешнем firewall хостера

| Порт | Назначение | Источник | Адрес назначения |
|---|---|---|---|
| Существующие SSH TCP-порты | Парольный SSH | Любой IPv4, кроме временно заблокированных Fail2ban | SSH-адреса VPS |
| `80/tcp` | ACME HTTP-01 и redirect | Любой IPv4 | Только выбранный IPv4 домена ноды |
| `443/tcp` | VLESS RAW REALITY / Selfsteal | Любой IPv4 | Только выбранный IPv4 домена ноды |
| `2222/tcp` | Служебный API RemnaNode | Только введённый IPv4 технички | Все локальные IPv4 ноды |

API доступен на всех локальных адресах именно для multi-IP VPS: адрес Node в панели может отличаться от адреса домена клиентов. **Ограничение по IP относится к API, не к SSH.** `2222` нельзя путать с клиентским `443`.

UFW разрешает исходящие соединения и запрещает прочий входящий/маршрутизируемый трафик. Пользовательские UDP-порты отдельным правилом не открываются: здесь выбран транспорт TCP/RAW. Правила security group, ACL, upstream firewall, DNS и Cloudflare на стороне провайдера скрипт без соответствующих доступов не меняет. HTTP-01 требует доступного снаружи TCP/80, в том числе при продлении сертификата; после установки его не закрывают [R7](docs/RESEARCH.md#r7-acme-и-certbot).

## 🗺️ Как устроена нода

```text
                           ОТДЕЛЬНАЯ VPS НОДЫ

Администратор ── IPv4 / пароль ──► sshd на сохранённых TCP-портах
                                  └─ Fail2ban: временные баны только SSH

Backend панели ── свой IPv4 ──► UFW allowlist ──► RemnaNode API :2222
                                                 └─ mTLS / управление Xray

VPN-клиент ──► домен ноды :443 ──► Xray: VLESS + RAW + REALITY
                                      │
Обычный HTTPS / Selfsteal ──────────────┤
                                      └─ PROXY v1, xver=1
                                         /dev/shm/nginx.sock внутри контейнера
                                                   │
                                         read-only bind КАТАЛОГА
                                                   │
                                         /run/vkarmani-selfsteal/nginx.sock
                                                   │
                                         Nginx НА ХОСТЕ + TLS-сертификат
                                                   └─ локальный cover-сайт

Let's Encrypt ──► домен :80 ──► Nginx ──► webroot HTTP-01
```

Один контейнер RemnaNode с `network_mode: host`, без `ports:` и без второго контейнера Nginx. У host networking контейнер использует сетевое пространство хоста — это сознательная схема RemnaNode, **не полная сетевая изоляция** [R1](docs/RESEARCH.md#r1-remnawave-node), [R3](docs/RESEARCH.md#r3-docker).

На хосте Nginx **не занимает TCP/443**: этот порт принадлежит Xray. Nginx принимает Selfsteal на Unix socket, ожидает PROXY v1 и отдаёт собственный локальный сайт. Сайт не загружается с чужого домена, не содержит внешних скриптов и сохраняет свои параметры при продолжении установки.

В контейнер монтируется только отдельный каталог сокета, а не весь host `/dev/shm`. Каталог монтируется read-only; это не мешает соединению с Unix socket. Монтирование каталога, а не одного inode сокета, позволяет увидеть новый socket после перезапуска Nginx. Сертификаты Let's Encrypt и приватные ключи Nginx в контейнер не монтируются.

**NET_ADMIN по умолчанию не выдаётся.** `NET_RAW` убран; включён `no-new-privileges`. Если конкретные функции IP/connection management вашей версии RemnaNode требуют `NET_ADMIN`, при первой установке доступен явный флаг `--allow-net-admin`. В host network эта capability позволяет контейнеру менять сеть хоста: включать её без понимания конкретной функции не следует. Без неё такие дополнительные функции могут не работать — это не скрывается [R2](docs/RESEARCH.md#r2-актуальный-исходный-код-remnanode).

## ⚙️ Что скрипт делает по порядку

| Этап | Действие | Защитная проверка |
|---|---|---|
| 1. Preflight | ОС, архитектура, GRUB, RAM/disk, systemd, dpkg, SSH, существующие сервисы | Остановка на неподдержанном/чужом состоянии, блокировка параллельного запуска |
| 2. Три значения | Скрытый ключ, домен, IPv4 технички | Формат, закрытый временный файл для продолжения |
| 3. Backup | Сохраняет исходные системные конфиги | SHA256 manifest; закрытые каталоги; это не снимок всей VPS |
| 4. Базовые зависимости | Подписанный APT, Python, crypto, DNS, curl | IPv4, retries/timeouts, ожидание dpkg lock; без массового обновления ОС |
| 5. Валидация | Проверяет секрет/DNS, выбирает IPv4 ноды, сохраняет SSH-порты | Не подменяет старые адреса и чужой ключ автоматически |
| 6. Службы и время | OpenSSH, UFW, Fail2ban, Nginx, Certbot, сохранённый NTP-клиент, logrotate | APT simulation + `--no-remove`, MSK, проверка синхронизации; журналы и security updates без auto-reboot |
| 7. Ядро и IPv6 | Консервативные sysctl, BBR/fq при поддержке, GRUB IPv4-only | Readback значений, проверка grub.cfg, явный fallback для ускорения |
| 8. SSH/UFW | Парольный SSH, сохранение портов, API allowlist | Backup фазы; временный 180-секундный аварийный откат; `sshd -t/-T` и listeners |
| 9. Защита/ресурсы | Fail2ban и при необходимости swap | Бан только SSH; существующий swap сохраняется |
| 10. Docker | Официальный репозиторий Docker, Engine и Compose plugin | Fingerprint ключа, `dockerd --validate`, отсутствие конфликта пакетов |
| 11. Selfsteal/TLS | Nginx на хосте, ACME, socket, renewal hook | `nginx -t`, реальный TLS 1.3 / HTTP/1.1 / HTTP/2 и renew dry-run |
| 12. RemnaNode | Загрузка официального образа и закрепление digest | Закрытый env, Compose validation, API TLS, видимость socket, стабильность процесса |
| 13. Профиль | Постоянная пара X25519, ShortID, RAW/REALITY JSON | Проверка пары ключей; `rw-core`/`xray run -test` внутри выбранного образа |
| 14. Завершение | Команды диагностики, maintenance, postboot, инструкции панели | Только после preboot-проверок — `INSTALL_COMPLETE`; reboot только по явному флагу |

Таймер отката SSH/UFW — страховка **конкретной фазы**, а не подтверждение входа из интернета и не откат APT/GRUB. После локальной проверки он снимается. Новая парольная сессия и консоль провайдера всё равно обязательны.

Повторный запуск **незавершённой 2.1.0** использует сохранённые значения, ключи и уже выбранный image digest. Повторный запуск **завершённой установки** выполняет только диагностику: не повторяет APT, UFW, SSH, выпуск сертификата или скачивание нового образа. Межверсионное продолжение по умолчанию запрещено. Единственное новое исключение — проверенный ранний package-stage STOP 2.0.2, описанный в [TIME_SYNC_FIX](docs/TIME_SYNC_FIX.md). Маркеры, ключи и firewall для обхода проверки не удаляют.

## 🔐 SSH по паролю и Fail2ban

Парольный вход разрешается явно, включая root при наличии у него действующего локального пароля. Пустые пароли запрещены. Создание аккаунтов, назначение паролей и разблокировка root не выполняются. Если используется sudo-пользователь, проверяется его локальный пароль; заблокированный root не становится доступным только от `PermitRootLogin yes`.

Существующие SSH-порты сохраняются, включая порт текущей сессии и порты `ssh.socket`; новые IP-ограничения не вводятся. Активный `ssh.socket` переводится на IPv4 `ssh.service`, перед переключением проверяется `KillMode=process`. Существующие ключи не создаются, не требуются и не удаляются. Пользовательские `Match`, `Allow/Deny` и нестандартные Include не переписываются вслепую: нужна чистая конфигурация или отдельный аудит [R4](docs/RESEARCH.md#r4-openssh).

Fail2ban использует журнал systemd: **5 неудачных попыток за 10 минут → бан на 1 час**, при повторении срок растёт до 24 часов. Исключён только loopback `127.0.0.1/8`. Введённый IP технички не становится бессрочным SSH-исключением. Собственное UFW-действие всегда указывает SSH-порты и не блокирует этому адресу весь трафик ноды.

Парольный SSH, особенно root с любого IP, сохраняет риск перебора, утечки и повторного использования пароля. Нужен длинный уникальный случайный пароль, защищённый менеджер паролей и контроль входов. Fail2ban не является заменой сильному паролю и не гарантирует защиту от распределённого перебора. Разбор и безопасный unban: [OPERATIONS](docs/OPERATIONS.md#ssh-и-fail2ban).

## 🌐 Сеть, ядро, BBR и MTU

Запрашиваются `tcp_congestion_control=bbr` и `default_qdisc=fq`. Проверяется не только `modprobe`, но и возможность записи/readback sysctl: модуль может быть встроен в ядро. Если ядро не поддерживает ускорение, сохраняется прежний действующий алгоритм/дисциплина, а диагностика показывает **DEGRADED**, не выдавая fallback за BBR.

Установщик **не заменяет ядро**, не ставит сторонний «BBR plus», не меняет MTU/MSS интерфейсов, netplan, маршруты, TSO/GRO/GSO и структуру `mq`/root qdisc. `default_qdisc=fq` не означает, что существующие очереди всех NIC немедленно стали `fq`.

Для проблем Path MTU включается `net.ipv4.tcp_mtu_probing=1`: пробование после обнаружения TCP black hole, а не принудительное уменьшение MTU всего сервера. Это не исправляет любую фильтрацию, UDP, потери, перегрузку или плохой международный маршрут [R5](docs/RESEARCH.md#r5-ядро-и-mtu).

Остальные настройки: SYN cookies; запрет ICMP redirects и source routes; loose reverse-path filtering `rp_filter=2`; `swappiness=10`. Не устанавливаются универсальные гигантские TCP-буферы «на скорость». При RAM меньше 2 GiB и отсутствии swap может создаваться 1 GiB swap на ext4/xfs; другие ФС и нехватка диска приводят к явному пропуску. Swap — аварийный запас, не дополнительная производительность.

IPv6 отключается runtime и параметром GRUB `ipv6.disable=1`. **Полное отключение возможности создавать IPv6 socket подтверждается только после reboot.** IPv4 DNS должен остаться работоспособным: установщик не исправляет за провайдера IPv6-only DNS. Часовой пояс сервера и расписаний — `Europe/Moscow`, независимо от страны VPS.

## 🧩 Что остаётся сделать в панели

**`SECRET_KEY` не является административным API-токеном панели.** Установщик с тремя значениями не может создать/назначить Node, Profile, Host, Squad или пользователя без дополнительных полномочий. Он подготавливает локальную ноду и готовые файлы, но не заявляет, что сделал действия в панели [R1](docs/RESEARCH.md#r1-remnawave-node).

Откройте `/etc/vkarmani-node/PANEL-SETUP.txt` **только у себя**. Там уже подставлены домен, IPv4, порт API, имя профиля, inbound tag, публичный REALITY-ключ и ShortID. Сам `/etc/vkarmani-node/profile.json` содержит приватный REALITY-ключ: не прикладывайте его к публичному issue.

1. В **Config Profiles** создайте профиль и импортируйте JSON из `profile.json`. Это шаблон с пустым `clients`; пользователей добавляет панель, не нужно вручную выдумывать UUID в файле установщика.
2. В карточке **Node** укажите адрес ноды и служебный порт `2222`, назначьте профиль и нужный inbound. Секрет должен соответствовать вашей панели. Не подставляйте сюда клиентский порт `443`.
3. Создайте/проверьте **Host**: домен ноды, порт `443`, соответствующий inbound и REALITY-параметры из инструкции. Обеспечьте доступ пользователя через подходящий Squad/права вашей версии панели и обновите подписку клиента.
4. Проверьте подключение ноды в панели, затем на VPS `sudo vkarmani-node-check --require-xray` и реальный клиент извне. Названия разделов панели могут отличаться между версиями.

Профиль использует **VLESS + RAW + REALITY**, target `/dev/shm/nginx.sock`, `xver=1`. Vision flow не навязывается автоматически. Маршрутизация блокирует private/link-local/loopback, собственные публичные IP ноды, IP панели и IPv6; это снижает возможность обратиться через proxy к metadata/внутренним сервисам. Не удаляйте эти ограничения без отдельного анализа.

## 🛠️ Основные команды

```bash
# Версия/справка — не меняют сервер:
bash install.sh --version
bash install.sh --help

# Локальная готовность; до первого reboot допустим специальный preboot:
sudo vkarmani-node-check
sudo vkarmani-node-check --preboot

# Строго: Xray :443 + ожидаемый Selfsteal; не заменяет VPN-клиент:
sudo vkarmani-node-check --require-xray

# Не перепроверять внешний DNS; остальные локальные проверки сохраняются:
sudo vkarmani-node-check --local

# Разделить диагностику API и Selfsteal:
sudo vkarmani-node-tls-check
sudo vkarmani-selfsteal-check

# Закрытый backup конфигурации:
sudo vkarmani-node-maintain backup

# Эти вызовы через файл установщика эквивалентны:
sudo bash install.sh --check --require-xray
sudo bash install.sh --backup
```

Код выхода диагностики: `0` — её локальные условия выполнены; `1` — локальная ошибка; `2` — неверные аргументы либо `--require-xray` ещё не подтвердил Xray/Selfsteal. **Код 0 не означает «панель авторизовалась» или «пользовательский VPN работает».**

Первоначальные необязательные флаги, **не дополнительные вопросы**:

| Флаг | Эффект |
|---|---|
| `--image remnawave/node:TAG` или `…@sha256:DIGEST` | Явный официальный образ для новой/незавершённой установки; после pull закрепляется digest |
| `--allow-net-admin` | Явно выдать сетевую capability для нужных upstream-функций; повышает риск |
| `--reboot` | Разрешить одну перезагрузку после успешной установки; SSH отключится |
| `--weekly-reboot` | Включить reboot по понедельникам в 04:00 МСК; по умолчанию выключен |
| `--no-reboot` | Явный запрет одноразового reboot; это поведение по умолчанию |

Флаги первой установки не меняют уже завершённую ноду при обычном повторном запуске. Для изменения эксплуатационной политики нужен регламент, а не надежда, что `bash install.sh --allow-net-admin` молча перепишет рабочий Compose.

## 🔄 Обновление образа и откат

По умолчанию первая установка берёт `remnawave/node:latest`, затем записывает **точный digest** в Compose и state. Это делает последующие запуски закреплёнными, но **не доказывает совместимость latest с вашей панелью**. Для нескольких стран/хостеров сначала проверьте один конкретный образ с вашей панелью на canary-ноде и используйте одинаковый digest при тиражировании.

Автоматического ежедневного обновления образа, Watchtower и Docker prune нет. Обновление — отдельное явное действие в согласованное окно обслуживания:

```bash
sudo vkarmani-node-maintain backup
sudo vkarmani-node-maintain refresh-image
# Для конкретного образа замените TAG на проверенный существующий тег:
# sudo vkarmani-node-maintain refresh-image --image remnawave/node:TAG

sudo vkarmani-node-check --require-xray
# Затем — состояние в панели и настоящий VPN-клиент.
```

Maintenance не запускает установку заново: **без APT, перенастройки SSH/UFW/Nginx/ядра**. Проверяются принадлежность контейнера проекту, совпадение текущего образа с Compose/state, место на диске и локальное здоровье. Затем сохраняется закрытый backup, скачивается новый образ, фиксируются старая/новая конфигурации и хеши транзакции. Если digest не изменился, контейнер не пересоздаётся.

При обновлении изменяется только строка image и пересоздаётся только `remnanode`. Предыдущий образ дополнительно удерживается локальным rollback-тегом. Если кандидат не проходит локальные проверки, выполняется попытка возврата прежнего Compose и образа. Неуспешный/прерванный откат оставляет pending marker и блокирует следующее обновление. **Таймаут/сигнал во время Compose apply — отдельный случай:** Docker daemon мог уже принять запрос. Устанавливается `IMAGE_APPLY=UNKNOWN`; встречный автоматический rollback не запускается. Сначала проверьте Docker и завершение его операций через консоль, затем выполняйте явный откат. Не удаляйте pending marker.

```bash
sudo vkarmani-node-maintain rollback-image
sudo vkarmani-node-check --require-xray
```

**Откат образа не равен откату всех данных.** Он не восстанавливает writable layer пересозданного контейнера, сессии клиентов, пакеты ОС, объекты/БД панели или её изменения. Панель должна быть работоспособна и повторно передать профиль. При недоступной панели возврат образа сам по себе не гарантирует возвращение TCP/443. Старый image не входит в конфигурационный tar-backup: не удаляйте его через `prune`.

Разовый `refresh-image --image …` не меняет сохранённый источник `config.json:image`; следующий вызов без `--image` снова использует сохранённый источник. Для фиксированного эксплуатационного тега/digest указывайте нужный образ явно либо меняйте источник отдельным проверяемым изменением.

Для работающих нод **1.3.x** сохранены только узкие `--repair-network` и `--repair-node`, с собственными ограничениями и backup. Это **не миграция на 2.1.0**. Новая схема socket, политика SSH/capabilities и maintenance не устанавливаются на старую ноду вслепую. Незавершённую 1.3.x продолжайте её исходной версией либо восстанавливайте снимок. Детали: [OPERATIONS](docs/OPERATIONS.md#совместимость-с-13x).

## ⏱️ Синхронизация времени без замены системной службы

На VPS с установленным `systemd-timesyncd` он сохраняется вместе с настройками NTP-серверов ОС/хостера. Установщик задаёт отдельный systemd drop-in с `AF_UNIX AF_INET`, проверяет фактически принятую политику и успешную IPv4-синхронизацию. `timesyncd.conf`, DHCP и netplan не переписываются. При уже установленном Chrony теперь сохраняются также `chrony.conf`, источники/включения и NTS-настройки ОС/хостера; добавляются `-4` и client-only `port 0` / `cmdport 0`, конфигурация проверяется до и после правки; при отсутствии обоих поддерживаемых клиентов устанавливается Chrony. Другой time-daemon, неполная установка пакета или противоречивое состояние вызывают STOP, а не автоматическое удаление.

`active` службы недостаточно: для timesyncd проверяются `NTPSynchronized=yes`, IPv4 источника и штатный runtime-маркер успешной синхронизации; для Chrony — `waitsync` с порогом коррекции 0.1 секунды и `Leap status: Normal`. Ожидание установки ограничено общим бюджетом 120 секунд. При недоступном исходящем NTP или источнике только по IPv6 будет ошибка с причиной, не ложное «всё готово». Timesyncd — SNTP-клиент; одинаковая с Chrony точность или полный NTP-функционал не заявляются. Источники: [R12](docs/RESEARCH.md#r12-apt-и-выбор-службы-времени-203); диагностика: [OPERATIONS](docs/OPERATIONS.md#синхронизация-времени-в-203).

## 🕒 Автозапуск и регулярное обслуживание

Автозапуск контейнера принадлежит **Docker `restart: always`**. `vkarmani-node.service` оставлен как ручная обёртка и не включён в boot target. Он не конкурирует с Docker как второй supervisor. API ноды не удерживается обязательной зависимостью от Nginx, обновления сертификата или BBR [R3](docs/RESEARCH.md#r3-docker).

Каталог socket создаётся через `systemd-tmpfiles` при загрузке до обычных сервисов. Перед стартом Nginx проверяется старый Unix socket: активный, чужой, подменённый или неоднозначный объект не удаляется. После подтверждённого отказа соединения собственный старый socket очищается. Nginx запускается как host service; после загрузки отдельный postboot unit собирает диагностику. Успех postboot всё ещё не является подтверждением панели.

Проверка Selfsteal ограничена 20 секундами на HTTP/1.1 и HTTP/2 вместе; `index.html` — до 128 KiB. Это ограничение локального проверяющего кода, не ограничение полезного VLESS-трафика. `vkarmani-wait-selfsteal` ждёт до 60 секунд плюс короткое завершение зависших процессов.

Сертификат обслуживает `certbot.timer`; deploy hook сначала проверяет Nginx, затем reload и Selfsteal. Аккаунт ACME регистрируется **без email**: запуск предполагает согласие с условиями CA; не рассчитывайте на email-напоминание об истечении. Важны timer, журнал и `TLS_VALID_7DAYS` в диагностике.

Журналы Docker: local driver, 10 MiB × 3 на контейнер; journald: до 200 MiB на диске, runtime 50 MiB и retention 14 дней. Логи установщика/postboot ротируются. В воскресенье 03:10 МСК очистка ограничивается APT-cache и старыми журналами; использует общий lock с установкой/maintenance. **Backups, volumes, образы, контейнеры и пакеты автоматически не удаляются.** Диск под backups всё равно нужно контролировать.

## 🧪 Что проверено и чего не обещает установщик

**2.1.0 / ci-fix2: 371 отдельный тест; локально пройдены от root и UID 1000, без пропусков.** Все 356 тестов ci-fix1 сохранены, добавлено 15 регрессий. Исправлены две причины из присланных журналов: отсутствие `crypto.hkdfSync` в Node 12 тестового Ubuntu 22.04 и Git `dubious ownership` в контейнере 26.04. JavaScript-эталон использует native HKDF при наличии API, иначе RFC 5869 через встроенный `createHmac`; серверная криптография не меняется. В 26.04 только текущий `$GITHUB_WORKSPACE` добавляется в protected global Git config shell-процесса до проверки worktree. Нет `safe.directory=*`, `chown`, новых зависимостей, sudo для VM-тестов или подавления ошибок. [Разбор и применение ci-fix2](docs/CI_FIX2_2.1.0.md), [точная матрица испытаний](docs/TEST_REPORT.md).

Исправления ci-fix1 — изоляция APT, пять временных каталогов тестового Nginx, установка Git до checkout — сохранены. Сам `install.sh`, сайт, версия установщика и его SHA256 не изменены. [История ci-fix1](docs/CI_FIX_2.1.0.md). Прежняя визуальная проверка девяти размеров описана в [историческом отчёте 2.1.0](docs/history/TEST_REPORT_2.1.0.md); в CI-исправлениях она повторно не выполнялась.

В поставке есть воспроизводимые тесты **реальных встроенных payload**, а не отдельно переписанных копий: валидация, DNS-сценарии, SSH-rendering, sysctl/fallback, шаблоны, изолированный Nginx, реальный TLS 1.3, HTTP/2 и транзакции обновления с имитацией Docker. Запуск не устанавливает ноду:

```bash
bash tests/run.sh
```

Нужны Python 3.10+, `cryptography`, PyYAML; для интеграционных тестов Nginx/OpenSSL, APT и Git; для независимой JS-проверки HKDF — Node.js. Отсутствующие внешние инструменты отмечаются как skip; результаты ci-fix2 получены без пропусков. В режиме без native HKDF весь набор также прошёл на Node 22 с искусственно отключённым API. Это **не запуск настоящего Node 12**; его бинарный дистрибутив в среду подготовки получить не удалось.

По присланным данным запуска GitHub Actions **#36679239665** ci-fix1: Ubuntu 24.04 успешна; Ubuntu 22.04 завершила 356 тестов с одной ошибкой JavaScript HKDF; 26.04 остановилась **до тестов**, на `git rev-parse`, код 128. Это не доказательство несовместимости VPS-установщика с Ubuntu 26.04. Исправленный ci-fix2 workflow **ещё не опубликован и не выполнен в GitHub**: нужен новый commit/push и новый run, а не повтор старого commit. Матрица Ubuntu 22.04/24.04 и userspace 26.04, read-only token и action commit сохранены. Полные тесты трёх Ubuntu-окружений в этой локальной среде не выполнялись.

Полный install/reboot/restore на настоящей VPS, Docker Compose runtime, доступ из панели, выпуск Let's Encrypt, SSH/UFW/Fail2ban на реальной ОС и скорость на международных маршрутах **не были проверены в среде подготовки архива**. Актуальный перечень и результаты: [TEST_REPORT](docs/TEST_REPORT.md).

Первая раскатка: **snapshot → одна тестовая нода → локальные проверки → новый парольный SSH → reboot → панель → реальный VPN-клиент → наблюдение под вашей нагрузкой → остальные хостеры**. География сама по себе не определяет правильный MTU и не гарантирует полосу. Установщик не обещает максимальную скорость на любом VPS, абсолютную неотличимость Selfsteal, отсутствие блокировок или защиту от всех атак.
