# Node_Install 2.5.13 r12 · двенадцать тематических сайтов и безопасная публикация

**Дата:** 2026-10-18. **Статус:** `INCOMPLETE_STAGING_ONLY`. Это не подтверждённый production-релиз. Источник — полный архив `2.5.12 r11`. Его структура и предыдущие подсистемы сохранены.

## 1. Что сделано

- В каталоге `cover-variants` **12 разных тематик**: 01 керамика/дизайн, 02 городской архив, 03 астрономия, 04 пешие маршруты, 05 чтение и эссе, 06 индустриальная мастерская, 07 ботаника, 08 музыкальные ландшафты, 09 домашняя кухня, 10 городские прогулки, 11 море и экология, 12 кинематограф.
- У каждой темы собственные тексты, разделы навигации, авторские SVG-иллюстрации, favicon, оформление карточек, раскрывающиеся FAQ, адаптивная типографика, содержательная тематическая 404-страница с возвратом на главную. **Настоящий HTTP 404 сохраняется**. Фальшивые формы, платежи, сбор персональных данных, рекламные трекеры не добавлялись.
- `scripts/cover_variants.py --name ... --domain FQDN --output NEW_DIR` строит четыре готовых статических файла без сервера, сети, сторонних пакетов и JavaScript. Тот же код вызывается при подтверждённом оператором `site-deploy`. Разные домены приводят к разным вариантам заголовков, авторского выпуска, цветов, порядка материалов, геометрии иллюстрации и сетки. Это не обещание абсолютной неразличимости или полного отсутствия сходства.
- Доставляются только HTML, CSS и статический SVG. CSP в HTTP Nginx и в HTML запрещает сторонний JavaScript, внешние скрипты, формы и встраиваемые фреймы. Не добавлены external URLs/remote fonts/CDN, скрытая аналитика, закодированные payload. Публичные страницы не содержат служебных комментариев и упоминаний внутренних механизмов ноды.
- Публикация и rollback расширены с двух файлов (`index.html`, content-addressed CSS) до четырёх (плюс `404.html`, `favicon.svg`). Журнал с SHA-256 и исходными правами ограничивает операцию; файлы публикуются атомарно, Nginx не переписывается; после проверки сервиса и содержимого CSS завершается транзакция. При падении доступен recovery, сторонние изменения не затираются. Откат старых двухфайловых записей сохранён.
- Исправлена несовместимость `install-version` и `INSTALL_COMPLETE`: теперь сравниваются реальные одинаковые версии 2.5.11/2.5.12/2.5.13, вместо жёсткого требования `2.5.11`. Поддержка версии не означает разрешение на изменение чужой ноды.
- Базовая 404-страница установщика также привязана к уже созданному локальному CSS, а не является голым текстом. Сохранена строка `error_page 404 /404.html` и `location = /404.html { internal; ... }` в Nginx.

## 2. Границы и эксплуатация

Публичный сайт — статическая страница на Nginx. Разметка доступна посетителю через браузер, DevTools и обычные HTTP-запросы; скрыть сам факт используемого протокола или технологии таким способом нельзя. Цель изменений — нормальный контент, корректные коды ответа, защита файлов, отсутствие секретов и отказоустойчивость. Нет обфускации, антиотладчика, обмана статуса ответа, имитации реальных организаций или обхода контроля безопасности.

**Preview (без прав root)**:

```bash
python3 scripts/cover_variants.py --list
python3 scripts/cover_variants.py --name 08-nocturne --domain preview.example.test --output /tmp/nocturne-preview-new
```

Папка для `--output` обязана не существовать. Изменение `--domain` возвращает устойчиво воспроизводимый вариант этого же шаблона. `index.html`, `style.css`, `404.html`, `favicon.svg` можно изучать локально.

**Публикация только на выделенном staging-хосте с проверенным snapshot**:

```bash
# Сначала check state, чужие ресурсы и версию; затем выберите тему и укажите именно свой FQDN.
python3 scripts/staging_web_deploy.py --help
sudo python3 scripts/staging_web_deploy.py status
sudo python3 scripts/staging_web_deploy.py site-deploy --theme 08-nocturne --expected-domain YOUR_STAGING_FQDN --confirm-staging
# Восстановление только при журнале именно этого деплоя:
sudo python3 scripts/staging_web_deploy.py site-rollback --confirm-staging
```

Сам `site-deploy` не выполняется автоматически при `bash install.sh`: чтобы не менять без запроса профиль ранее установленной страницы. Также нельзя смешивать новый R7/R12 journal и `install.sh --update-cover` (старый режим обновления). Для разделения сценариев нужны отдельные тесты и snapshot до операций.

**Проверить после изменения (на своей staging VPS)**: `nginx -t`, ответ 200 на `/`, ответ 200 на CSS/favicon, ответ именно **404** на `/not-a-real-page`, отсутствие внешних запросов, работа ссылок и FAQ, сертификат с внешнего клиента, содержимое `index.html` и `404.html` совпадают с развернутыми вариантами. Любая ошибка — не запускать `--update-cover`; сначала проверьте журнал и откат через `site-rollback`.

## 3. Совместимость

Нет изменений в каскадных ключах, Remnawave API, Xray RAW/XHTTP, секретных файлах, systemd timers, UFW/RKN, хранилище Docker, правах на PostgreSQL, Nginx TLS listen, fallback Unix socket, сертификатах и ACME. Не добавлены новые сервисы и зависимости; основная VPS с 1 vCPU / 1 GiB остаётся под ограничением тестового статуса: браузерные проверки шаблонов не доказывают работу реального TLS, прокси или трафика.

## 4. Приёмочные критерии

- `bash -n install.sh`, AST компиляция Python, JSON parsing всех файлов.
- Проверка SHA256SUMS и BUILD_MANIFEST на **чистой распаковке**.
- Раздельные тесты генератора и 12 шаблонов, всех 4 файлов, устойчивости повторного рендера, доменной уникальности, XSS/URL/secret hygiene, rollback при ошибках.
- Браузерные тесты 12 тем на мобильном / планшете / десктопе, проверка FAQ, ссылок и отсутствия горизонтального переполнения.
- Изолированный Nginx с HTTP 404 и asset allowlist, без работы с действующими конфигурациями.
- Полный регрессионный набор тестов под root и непривилегированным пользователем, для финального ZIP отдельно от рабочей папки.
- **Нельзя заменить офлайн-проверками**: реальную staging VPS, `nginx -t` на ней, публичный TLS, Remnawave, клиентский RAW/XHTTP, нагрузку 1 ГБ и reboot.

Результаты проведённых тестов необходимо фиксировать по фактическим логам; не считать ссылки на тесты доказательством их успешного запуска.
