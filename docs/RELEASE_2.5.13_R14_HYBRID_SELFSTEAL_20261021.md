## 2. Двухветочная схема без двойного публичного 443

В каждой Ordinary RAW/VLESS/REALITY клиентской конфигурации:

- `streamSettings.network=raw`, `security=reality`, `flow=xtls-rprx-vision`;
- `realitySettings.target=/dev/shm/nginx.sock` (socket внутри контейнера), `xver=1`, `shortIds` и приватный ключ именно этой VPS;
- в режиме `local` — REALITY `serverNames=[FQDN_НОДЫ]`;
- во внешнем режиме — REALITY `serverNames=[ВЫБРАННЫЙ_ДОМЕН]`, **не** домен собственного сайта.

XHTTP использует ту же локальную REALITY-цель, ключи и SNI, но `network=xhttp`, `flow=''`, собственные `xhttpSettings.host` и `path`. **RAW и XHTTP — два альтернативных JSON, а не два одновременных сервиса TCP/443**. Remnawave Panel должна применить только один профиль/inbound на этот порт.

```
          TCP/443 on VPS: RemnaNode/Xray
                    |
       REALITY: authenticated?  -- YES --> VLESS user handling (no Nginx)
                    |
                   NO
                    |
        PROXY v1 + original TLS ClientHello
                    |
     /dev/shm/nginx.sock (container bind -> /run/vkarmani-selfsteal/nginx.sock on host)
                    |
       Nginx Stream, proxy_protocol listener, ssl_preread
           /                          \
    own VPS FQDN                chosen external SNI
           |                          |
    unix:cover.sock            selected domain:443
           |                    TLS passthrough
      Nginx HTTPS               no PROXY v1 to upstream
      own certificate           real external TLS certificate
      HSTS and site             no certificate interception
```

Для обычного (`local`) варианта промежуточного Nginx Stream **нет**: HTTPS слушает основной Unix socket напрямую, сохраняя прежний PROXY-protocol интерфейс. Для внешнего — подписанный пакет `libnginx-mod-stream`; разрешённый домен закреплён в `map`, неизвестный SNI не получает произвольный TCP-прокси к сторонним хостам. IPv6 резолвинг Stream отключён; UDP/QUIC отдельным маршрутом не маскируется. Для `max.ru` / `ya.ru` / `rutube.ru` / `mail.ru` назначается **ровно один** выбранный внешний upstream.

`xver=1` означает передачу PROXY v1 **в локальный Nginx**. Он читает заголовок на входе; наружу в интернет PROXY protocol **не** передаётся. Нельзя заменить локальный target на `max.ru:443` без отдельного изменения `xver` и архитектуры, иначе чужой сервер получит неподдерживаемый заголовок. Собственный HTTPS-сертификат выпускает Certbot по HTTP-01; HTTP/80 собственного FQDN отдаёт ACME и делает фиксированный 301 на собственный HTTPS/443. Публичный HTTPS трафик VPS проходит через Xray REALITY fallback, а не второй socket на `0.0.0.0:443`.

### Примечание о безопасности и наблюдаемости

Этот режим **не** превращает VPS в чужой сайт и **не** гарантирует обход ТСПУ/DPI/белых списков IP, TLS/JA3/JA4 или ограничений операторов. При REALITY клиенте внешний SNI не означает, что реально установлен сквозной туннель к внешнему сайту. Проверка внешнего TLS fallback **не равна** проверке авторизованного VPN-трафика. Смена upstream или его антибот/антипрокси политики может прервать работу внешней ветки даже при работоспособности собственного HTTPS.

## 3. Порты

| Назначение | По умолчанию r14 | Допустимые настройки | Что вручную согласовать |
|---|---|---|---|
| Управляющий RemnaNode `NODE_PORT` | `2222/tcp` | Для **новой Ordinary**: `bash ./install.sh --node-port 32443` (целое 1024..65535, кроме `61001`) | Поле **Node Port** в Remnawave Panel = конфигурация Node, разрешённые IPv4 панели и UFW, свобода сокета |
| Клиент VLESS/REALITY RAW либо XHTTP | `443/tcp` | В r14 **не настраивается** | Отдельная миграция и проверка реально применённого inbound, Hosts, URL и UFW нужны до любого изменения |
| ACME HTTP-01 | `80/tcp` | В r14 не меняется | DNS A = собственный IPv4; доступ с Let's Encrypt |
| SSH | сохраняет порты хоста, отдельный механизм защиты | Не использовать занятые `80/443/NODE_PORT` | Консоль и внешний SSH canary обязательны |

`--node-port` **не является переносом** уже установленной ноды и **не** разрешён для роли Cascade. На существующей VPS изменять 2222 вручную, не согласовав конфигурацию Remnawave, состояние контейнера, правила UFW и rollback, нельзя. `61001` зарезервирован проектом. Клиентский `443` можно проектировать как изменяемый в отдельной версии, но на нестандартном порту доступность со стороны операторов может отличаться; смена номера TCP-порта обычно не повышает вычислительную пропускную способность и не гарантирует стабильность.

## 4. Проверки изоляции и остаточные риски

В исходнике до установки выполняется IPv4+TLS1.3 preflight к выбранному внешнему домену (проверка публичности и CA). При установке Nginx использует пакет из штатного подписанного дистрибутивного репозитория. Если уже существует несогласованный верхнеуровневый `stream`, новая ветка **откажется** переписывать Nginx. Выполняется `nginx -t`, прежде чем `reload`. При перезапуске сокетный preparer отказывается удалять живые, не принадлежащие root, изменившиеся или symlink-сокеты; удаляет только доказанно осиротевшие **свои** Unix socket. Завершающая диагностика отдельно проверяет собственный TLS Selfsteal и внешний TLS 1.3 fallback.

**Не закрыто никакими офлайн-тестами:** корректная сборка `libnginx-mod-stream` для конкретного дистрибутива, реальный запуск stream с Xray, фактическое PROXY v1 ClientHello от используемого образа RemnaNode, внешний fallback сертификат, обрыв upstream, функциональность XHTTP в активной панели, DNS TTL после смены внешних адресов, TCP/443/80 из отдельных ISP, UDP, throughput/latency, 1 GiB RAM, reboot, 24h soak и полный диск rollback. Статус останется `INCOMPLETE_STAGING_ONLY`, даже если все автономные проверки успешны.

## 5. Обязательная staging-приёмка (отдельная VPS под каждый режим)

1. Получить проверяемый snapshot VPS, доступ к консоли провайдера **до** исполнения любых root-команд. Проверить исходный SHA-256 архива внешним доверенным способом; `scripts/verify_release.py`, `SHA256SUMS` и `bash -n install.sh` — лишь локальные проверки.
2. На новой VPS с действующим DNS A проверить публичный IPv4, свободные TCP `80/443/2222` (либо выбранный NODE_PORT) и отсутствие действующего неизвестного Nginx. Не ставить поверх production и cascade.
3. Проверить все пять пунктов меню на **чистых** снимках (не менять реальный режим на установленной VPS). Для внешнего режима проверить `nginx -V`, загруженный stream module, `nginx -t`, `ss -xlpn`, что ожидаемые Unix socket реально существуют, а на публичном 443 только один слушатель Xray.
4. Перед активацией профиля в Remnawave подтвердить `curl --resolve OWN_FQDN:443:NODE_IP https://OWN_FQDN/` с валидным собственным сертификатом и содержимым сайта. Убедиться, что HTTP/80 обслуживает ACME и выдаёт фиксированный HTTPS redirect. Проверить отвергнутый чужой Host, чужой SNI и недопустимые методы/пути.
5. Проверить `curl --resolve max.ru:443:NODE_IP https://max.ru/` (для соответствующего выбранного домена): валидный настоящий внешний сертификат, ожидаемый SNI и HTTP-ответ; отсутствие PROXY v1 в upstream. Важно отличать локальную ошибку Xray/Nginx от отказа внешнего сайта. Не слать неподписанные сторонние сертификаты.
6. Проверить REALITY RAW+Vision на реальном клиенте из нескольких операторов. Затем сохранить предыдущий профиль в Panel, **вместо**, а не вместе с ним активировать XHTTP без Vision; после запуска клиента проверить DNS IPv4/TCP/UDP, задержку, длительные соединения, повторные подключения и ограничения скорости. Откатиться к сохранённому RAW при любой регрессии.
7. Для кастомного NODE_PORT вручную поставить тот же порт в Panel, проверить соединение Node API **только** с IPv4 панели, закрытие извне и отсутствие конфликта с SSH. Сохранить аварийную консоль и независимый внешний SSH сеанс при смене UFW.
8. Перезагрузить VPS, проверить `nginx -t`, `vkarmani-node-check --postboot`, systemd status, Certbot renewal dry-run, Docker image digest, панель и клиент, затем минимум 24 часа наблюдения. Проверить реакцию на отказ удалённого TLS сервера или DNS до объявления релиза пригодным для production.

## 6. Backup / rollback / deployment

Для испытаний r14 достаточная стратегия отказа — восстановление **полного снимка чистой VPS**, сделанного у провайдера до начала установки, с независимой консолью. Частичный rollback Nginx/SSH/UFW не эквивалентен восстановлению после изменения OS packages, GRUB и Docker. При неуспешной установке нельзя запускать поверх неё другую ветку скрипта, менять роль или вручную «чинить» firewall без сохранения полного состояния. Для production нужна отдельная процедура миграции с проверенным удалённым backup и планом возврата Node/Panel, а не обновление ZIP поверх рабочей папки.

Секреты `SECRET_KEY`, REALITY private keys, `/root/*profile.json`, role-bundles, конфиг `.env` и материалы журнала/файлов `/etc/vkarmani-node` **не публиковать**. Вывод `vkarmani-node-check` может содержать имя домена/IP/режим; перед отправкой редактировать чувствительные поля. Установщик по-прежнему меняет SSH policy и систему; нельзя принимать наличие статического теста за гарантию внешнего доступа.
