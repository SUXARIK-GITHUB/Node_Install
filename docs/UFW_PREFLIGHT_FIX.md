# 🛠️ UFW preflight: исправление 2.0.2

Дата: 2026-09-30. База: предоставленный полный архив 2.0.1, а не предположение о текущем содержимом GitHub.

## Что доказано присланным выводом

ОС сообщила Ubuntu 24.04.4 (`VERSION_ID=24.04`), пакет `ufw 0.36.2-6`. `ufw status verbose` вернул `inactive`, `ufw show added` — `(None)`. `nft list ruleset`, `iptables-save`, `iptables-legacy-save` не вывели правил. Это не проверка firewall в панели хостера, но в показанном локальном состоянии нет основания очищать UFW.

`user.rules` содержал пять объявлений ufw-user-цепочек и только три limit-helper строки; `user6.rules` — три объявления, без `-A`. Их точные текстовые копии лежат в `tests/fixtures/ufw/ubuntu-24.04-0.36.2-6/`. Чтение IPv6-конфига не активирует IPv6.

## Причина и пробел прежних тестов

В 2.0.1 строки 1873–1875 искали все `^-A ufw-user-`. Стандартные `-A ufw-user-limit ...` и `-A ufw-user-limit-accept ...` удовлетворяли этому условию, хотя в файле не было правил input/output/forward. Старый predicate воспроизведён на точном fixture и действительно принимает служебные строки за повод для STOP.

Прежние 178 тестов снова прошли до изменений. `test_firewall.py` проверял **послеустановочную** Python-диагностику разрешений, а не Bash preflight первой установки. Поэтому его PASS не исключал этот дефект. Новый набор исполняет действительные Bash-функции и условие вызова внутри preflight; он не подменяет установщик улучшенной копией алгоритма.

## Что изменено

Перед вводом данных выполняется `vk_check_saved_ufw_rules`. Для обоих saved-файлов допускается лишь известный пустой `*filter ... COMMIT` с правильными chain declarations; при наличии limit helpers — точные три стандартные строки и их объявления. Допустимы комментарии, секционные заголовки, пустые строки, внешние пробелы и счётчики. Отсутствующий файл допустим, например до установки UFW; существующий пустой/повреждённый файл не считается доказанно чистым.

Пользовательские input/output/forward-правила (в том числе настоящий `ufw limit` с переходом из input), custom chains/tables/policies, изменённые limit helpers, tuple metadata без packet-rule, неизвестные директивы, обрезанные/дублированные структуры, symlink/FIFO/каталог и ошибка awk вызывают отказ. Это намеренно узкий допуск, а не общий парсер всех вариантов iptables-restore. Незнакомый шаблон требует анализа.

Функция только читает; не вызывает `ufw`, `nft`, `iptables`, `systemctl`, не пишет `/etc/ufw`, не включает IPv6. Использует уже необходимый установщику awk, без новых пакетов до ввода данных. Остальные guards активного UFW, nftables/iptables, чужих сервисов, портов, SSH, ОС и загрузчика сохранены.

Не изменены: три обязательных вопроса, парольный SSH и существующие порты, Fail2ban, правила API, Docker/Compose, Nginx/Selfsteal, RAW REALITY, настройки сети, reboot-политика и панельные действия. Встроенные версии/проверки markers согласованно обновлены на 2.0.2; прошлые установки не мигрируются.

## Что проверено и что нет

48 новых тестов + прежние 178 = 226. Покрыты точный инцидент, положительные минимальные шаблоны обеих семей, отрицательные ручные правила, modified helpers, неверная структура и тип файла, отказ awk, сохранность байтов/mode/mtime/inode и отсутствие вызовов firewall/service-команд. Gate успешно переходит дальше только на принятом fixture; при сохранённом правиле — STOP до следующего этапа.

Полное развёртывание на присланной VPS, живые UFW/SSH/Docker/Xray/ACME и reboot **не выполнялись**. Успех fixture означает устранение этого конкретного препятствия, не обещание, что все следующие проверки и внешние сервисы обязательно сработают.

## Как продолжить именно после этого STOP

Проверка 2.0.1 срабатывала до запроса трёх значений, записи `owned-installation`/`install-version`, APT и конфигурации firewall/SSH. Ранее уже могли быть созданы каталог загрузки, lock-файл установщика и `/run/sshd`; это не установленная нода и не изменение правил доступа.

На этой стадии можно использовать полный новый `install.sh` 2.0.2 без очистки ОС. Сначала snapshot и проверенная консоль, затем hash и `bash -n`, затем обычный запуск. Если на VPS уже есть markers начатой установки, не удаляйте их: новый файл откажется смешивать версии. Отдельный rollback UFW не требуется, потому что исправление не применяет firewall-изменений; после начала полной установки действует обычный регламент backup/аварийного восстановления.

Установка с GitHub требует сначала разместить новый `install.sh`, README и manifest в репозитории. Старая SHA256 относится к 2.0.1; повторение старого блока не устанавливает исправление. Новый README выводит ясное сообщение при несовпадении файла. Для запуска без публикации используйте установщик из этого архива, без ручного вырезания защитных строк.

После успешной установки — новая парольная SSH-сессия, плановая перезагрузка и диагностика из [OPERATIONS](OPERATIONS.md). Нельзя закрывать исходную сессию до проверки нового входа. Сама проверка preflight не гарантирует правильность DNS, ключа, password/PAM, доступность APT/registry/ACME или внешнего firewall.

## Источники и границы

Исходный архив и присланный diagnostic output — источники для причины. Официальный [ufw(8)](https://manpages.debian.org/bookworm/ufw/ufw.8.en.html) подтверждает назначение `status`, `show added` и разрушающее относительно пользовательских настроек поведение `reset`. Чужие правила не удаляются ради прохождения preflight.

Текущий raw-файл GitHub не удалось независимо скачать/hash-проверить; публикация 2.0.2 не выполнялась. Итоговые контрольные суммы и локальные проверки относятся к файлам этой поставки, а не к произвольной будущей ветке `main`.
