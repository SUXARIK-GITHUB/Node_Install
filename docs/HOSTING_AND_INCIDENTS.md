# 🌐 Хостеры, собственный Selfsteal и недоступность ноды

Актуализация: **30 сентября 2026**. Этот документ относится к **VLESS RAW REALITY**. XHTTP и другие транспорты не внедряются.

## Статус присланной информации

Пользователь передал два сообщения: о предполагаемом начале адресной фильтрации `/32` с **20 сентября 2026** и о запрете сторонних SNI/dest неназванным хостером с требованием привести настройки в соответствие **до 1 октября 2026**.

Это полезные сигналы для эксплуатации, но имени хостера, ссылки на оферту и однозначного URL указанного DPI//Checker нет. Поиск не позволил подтвердить первоисточник именно этих сообщений. Они не выдаются за установленное правило всех хостеров, юридическое заключение или доказанный механизм фильтрации вашего IP. Оферта конкретного поставщика имеет значение отдельно от технической работоспособности.

## Что применено к нашему проекту

```text
VLESS клиент
  │  RAW/TCP + REALITY, публичный IPv4 ноды:443
  ▼
Xray / RemnaNode
  │  target=/dev/shm/nginx.sock, PROXY v1
  │  внутри контейнера смонтирован только свой socket-каталог
  ▼
Nginx на хосте
  └─ сайт и действующий сертификат вашего домена
```

Роль SNI выполняет **домен самой ноды**, контролируемый владельцем проекта. `target`/старый `dest` — локальный Unix socket собственного Nginx, а не домен/IP банка, государственного ресурса, чужого CDN или иного внешнего сайта. Публичная DNS A-запись должна указывать на фактически назначенный адрес VPS; сертификат, `serverNames`, клиентский SNI и настройки Host должны совпадать с этим доменом. Параметры REALITY: [официальная документация Xray](https://xtls.github.io/en/config/transports/reality.html).

Адрес для подключения и SNI — разные поля: клиент может подключаться к IPv4, передавая SNI вашего домена. Не заменяйте собственный SNI на посторонний hostname. Внутренний derived SNI служебного API RemnaNode — отдельный механизм проверки канала панели, не сайт маскировки REALITY; его нельзя вручную заменить публичным доменом в локальном probe и ожидать сохранения API-совместимости.

Проверка `profile-check` проверяет только предоставленный raw Xray JSON. Панель может отправить другой профиль, а Host — переопределить клиентский SNI. Поэтому проверять следует **генерируемый шаблон, назначенный профиль, Host и конечную клиентскую конфигурацию**. Рабочие ключи и выгрузки нельзя публиковать. Сертификат/DNS не являются универсальным подтверждением юридического владения или разрешения хостера на услугу.

## Почему не закрыты все порты, кроме 443

| Порт | Назначение | Политика проекта |
|---|---|---|
| Существующий SSH, обычно 22/TCP | Администрирование | Парольный вход со всех IP, без постоянного allowlist. Fail2ban временно ограничивает неудачные попытки только на SSH-портах |
| 80/TCP на IPv4 ноды | ACME HTTP-01 и HTTP redirect | Нужен для автоматического выпуска/продления сертификата. Установщик не переводится на DNS-01 с дополнительным API-токеном |
| 443/TCP на IPv4 ноды | VLESS RAW REALITY / Selfsteal | Публичный клиентский вход |
| 2222/TCP, либо сохранённый Node Port | Служебный API | Только с публичного исходящего IPv4 backend панели |

HTTP-01 использует порт 80: [Let's Encrypt](https://letsencrypt.org/docs/challenge-types/). Node Port — API, не клиентский порт: [Remnawave](https://docs.rw/install/remnawave-node/). У host networking и опубликованных bridge-портов разное взаимодействие с firewall: [Docker](https://docs.docker.com/engine/network/packet-filtering-firewalls/).

Требование «только 443» не совместимо с текущими условиями без изменения способа SSH/ACME и архитектуры. Оно не выполняется скрыто ценой потери административного доступа. Внешний firewall/security group хостера должен разрешать ту же минимально необходимую матрицу, включая API с адреса панели.

## Что можно и нельзя заключить из симптомов

**Недоступен ping.** Это не доказательство блокировки TCP или самого сервера: ICMP может фильтроваться отдельно. Нужны отдельные TCP/TLS-пробы.

**SSH не работает напрямую, но работает через другую сеть/VPN.** Это признак зависимости от пути/источника, а не однозначное доказательство `/32`. Возможны Fail2ban на исходном IP, source-based provider firewall, локальная сеть клиента, маршрутизация и внешняя фильтрация. Не отключайте Fail2ban/UFW до проверки.

**Передача обрывается после 16–20 KiB.** Число байт само по себе не сообщает длину фильтруемого префикса. Размер подсети (`/32`, `/24`) и механизм обрыва потока — независимые признаки. Подсеть тоже может блокироваться до TCP handshake; один IP может подвергаться частичной протокольной фильтрации. Возможны MTU/маршрутные/серверные причины. Это инженерный вывод о недостаточности наблюдений, не установление конкретной причины.

**Красная или зелёная карта checker.** Без методики, URL, используемых адресов, времени, DNS и направления теста нельзя трактовать цвет как доказательство границ CIDR. Специализированный [open-source TCP 16–20 checker](https://github.com/hyperion-cs/dpi-checkers) — пример проверки конкретной гипотезы, а не удостоверение `/32` для вашей ноды; он не отождествляется с названием из сообщения.

Если установлен полный drop трафика до конкретного IPv4 по нужному пути, изменение Nginx, SNI, BBR, MTU или сайта **не заставляет уже отброшенный пакет дойти**. Это условный вывод из места отказа. Selfsteal не обещает доступность заблокированного адреса и не является гарантией отсутствия детектирования.

## Порядок диагностики без изменений сервера

Сначала зафиксируйте точное время/часовой пояс, конкретный IPv4, порт, сеть/оператора клиента и проверяемый протокол. Не сравнивайте разные IP, разный DNS и разные моменты времени как один эксперимент.

На самой ноде через сохранённый SSH или консоль:

```bash
sudo vkarmani-node-check --local
sudo systemctl --failed --no-pager
sudo ss -H -4 -lnt
sudo ufw status numbered
sudo fail2ban-client status sshd
ip -4 address show
ip -4 route show
```

Это не единая команда «починки»: прочитайте каждую ошибку. Вывод смотрите локально; перед передачей редактируйте IP, домены и чувствительные фрагменты. `--local` не проверяет внешний путь от панели или клиента, а UFW parser не заменяет аудит всех nft/iptables hooks.

Проверьте **свой** адрес из проблемной сети, другой независимой сети и backend панели. API 2222 тестируется только с backend: отказ с чужого IP — ожидаемый результат. SSH проверяется на сохранённом порту, TLS/сайт — с правильным собственным SNI. Факт локального listener не заменяет внешний handshake.

При необходимости согласованного packet capture снимайте только короткую выборку handshake/заголовков для своего узла и тестового адреса. Не публикуйте дамп пользовательского трафика. SYN отсутствует на VPS — возможен отказ до хоста; SYN пришёл без SYN-ACK — проверять локальный firewall/listener/маршрут; SYN-ACK ушёл, ACK не вернулся — исследовать обратный путь. Ни один из этих случаев сам по себе не называет конкретного участника фильтрации.

Сравнение с другим IP выполняйте только на собственном адресе или с разрешения владельца. **Сканирование случайных соседей по четвёртому октету не включено** ни в код, ни в регламент. Даже несколько успешных соседних проб не доказывают отсутствие любых других правил фильтрации.

## Когда обсуждать смену IP

Сначала отделите отказ ноды от внешней маршрутизации/фильтрации и согласуйте случай с хостером. При подтверждённой недоступности текущего адреса обсуждается новый **разрешённый к использованию** IPv4, а не автоматическая ротация вслепую. Новый адрес тоже не имеет гарантии будущей доступности.

Смена IP требует согласованного изменения адреса у хостера/в системе, DNS A, локальной сохранённой конфигурации, привязок Nginx/UFW, настроек ноды/Host в панели, клиентского адреса и проверки ACME. Сертификат привязан к домену, а не обязательно к прежнему IP, однако следующая HTTP-01-проверка должна достигать нового адреса. Не надо без причины генерировать заново REALITY keys или SECRET_KEY.

Новый `install.sh` не является IP-migration tool и не переписывает эти параметры на живом узле. Нужны backup/snapshot, согласованный план, canary и проверка rollback с учётом того, сохранится ли доступ к старому адресу.

## Секреты и сторонние тестеры

`SECRET_KEY` ноды и приватный REALITY key **никогда** не передавайте внешнему checker. Административный API token также не нужен для проверки сетевой доступности. VLESS-ссылка содержит доступ пользователя и не должна считаться публичным диагностическим материалом: для согласованного внешнего теста используйте отдельную ограниченную тестовую учётную запись, отзываемую после проверки. Не загружайте рабочую подписку со всеми нодами.

## Что проверить у конкретного хостера до тиражирования

Поддерживаемая ОС/полноценная VM/свой управляемый kernel/GRUB; непосредственно назначенный IPv4 вместо NAT; доступность DNS/NTP/APT/Registry/ACME; внешняя матрица портов; CPU steal/лимиты bandwidth и допустимый workload; консоль и восстановление snapshot; условия оферты для **собственного** Selfsteal. Отсутствие одной из предпосылок — причина остановить внедрение, а не отключать preflight установщика.

## Provider complaint / suspend incident — 2.5.0

Не смешивайте provider incident с сетевой цензурой. Зафиксируйте один из классов: outbound SMTP/spam; port scanning/malware; copyright/P2P complaint; credential compromise; DDoS/attack traffic; excessive PPS/connections; provider-specific prohibited service; false positive/IP reputation; censorship/path failure.

Безопасный порядок: сохранить console/snapshot/evidence; не удалять контейнеры/логи до понимания причины; проверить Panel Torrent reports/Plugin state и локальные container/resource signals; проверить unexpected public listeners; проверить признаки root compromise без публикации секретов. При реальном compromise локальному checker на скомпрометированном root не доверять — rebuild clean VPS и rotate затронутые credentials. Не отвечать на suspend отключением UFW/Fail2ban, `nft flush ruleset` или открытием новых портов.

Не включать packet-content logging пользователей и не собирать лишние персональные данные. Если провайдер требует mitigation, она должна соответствовать ToS и конкретной доказанной причине инцидента.
