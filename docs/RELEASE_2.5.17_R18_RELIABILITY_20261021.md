# VKARMANI Node Install 2.5.17 r18 — исправления маршрутизации и read-only диагностика

Статус: **INCOMPLETE_STAGING_ONLY**, 21.10.2026. Этот выпуск создан из полной проверенной сборки 2.5.16 r17. **Не является проверенным production-релизом.** Действующие ноды, панель, сеть хостов и GitHub не мигрируются автоматически.

## Изменено (новые установки)

1. **IPv4 ввода.** Исправлен ошибочный ранний отказ для `192.0.1.0/24`. Специальный `192.0.0.0/24` по-прежнему запрещён ранним валидатором. Полная проверка IPv4 после предварительных шагов сохранена, как и требование уникальной DNS A, указывающей на один из назначенных адресов VPS. `/etc/network/interfaces`, Netplan, дополнительные адреса и source routing не изменяются.
2. **Каскад Entry/Exit.** В новых генерируемых профилях правила BLOCK содержат частные сети, IPv6 и две конкретные публичные IPv4 пары Entry/Exit (`/32`). Exit использует `streamSettings.sockopt.domainStrategy: ForceIPv4`; `settings.domainStrategy: UseIPv4` сохранён только как параметр совместимости. На Exit `freedom.finalRules` повторяют защиту. Проверки проверяют необходимое содержимое, порядок и отсутствие fallback у Entry. Существующие `role-bundle` и импортированные профили не переписываются: их контрольные суммы и схема могли отличаться. **Запланированное обновление действующего каскада требует отдельного согласованного процесса на двух VPS с резервной копией и ручной проверкой Remnawave.**
3. **Hybrid Selfsteal / Nginx.** Новые внешние режимы (max.ru, ya.ru, rutube.ru, mail.ru) добавляют в установщике внутри своего Stream-блока отдельный `include /etc/nginx/vkarmani-stream-r7/*.conf;` и пустой каталог. Опциональный `scripts/staging_web_deploy.py tcp-deploy` распознаёт **только** эту строго созданную конфигурацию и добавляет **только** собственный фрагмент; основной `nginx.conf` при этом не переписывается. Чужой Stream, старый Hybrid r14-r17 без этого include, отсутствующий marker и сторонние изменения дают STOP. Откат сверяет контрольную сумму `nginx.conf` и журнал того набора файлов, которые действительно менялись. На локальном Selfsteal прежний путь сохраняется.
4. **Безопасная диагностика `--diagnose-quality`.** Два локальных среза `ss` активных TCP-соединений с локального порта 443 (интервал 1–120 секунд). Возвращаются только агрегированные показатели RTT p50/p90/p99, исторически зарегистрированные ретрансляции и delivery rate. JSON не включает удалённые IP, клиентские порты, UUID, ключи или исходный вывод `ss`. `--strict` возвращает код 2 на REVIEW/NOT_VERIFIED. Не меняет сеть или демоны, не отправляет диагностические пакеты наружу. **Это не измерение загрузки Xray на клиента и не доказательство ТСПУ.** Сеть UDP, QUIC и внутренние потоки VLESS этим срезом не измеряются.

## Использование после получения проверенной версии

```bash
bash ./install.sh --diagnose-node --domain node.example.com
bash ./install.sh --diagnose-resources --seconds 15
bash ./install.sh --diagnose-quality --seconds 15
```

Команда установки новой тестовой Ordinary-ноды остаётся **`bash ./install.sh`**; по умолчанию API TCP/2222 и клиентский TCP/443. Не выполнять установку на готовой ноде. Перед испытанием новой VPS требуется полный snapshot, проверка его восстановления и рабочая аварийная консоль провайдера.

## Что намеренно не изменено

- BBR, `fq`, MTU/MSS, TCP/UDP буферы и тайм-ауты conntrack (нет реальных замеров узких мест).
- `routeOnly=true`, QUIC/UDP 443, TCP keepalive и `policy` Xray — любые массовые изменения требуют A/B с живыми клиентами.
- Docker `network_mode: host`, firewall/UFW, Node Port, API Remnawave, сертификаты, TLS/cipher и режимы RAW/XHTTP на одном порту.
- Автоматические фильтры исключения ASN из RKN Guard: исключать подсети по словам «USER»/«MOBILE» опасно. Факт возможных ложных блокировок требует отдельного аудита и точечных исключений.
- Nginx из nginx.org, PROXY v2, XHTTP/CDN-альтернативы — не внедрялись без матрицы совместимости.
- Панельные IPv4 не меняются автоматически. `--rkn-sync-panel` обновляет только RKN-исключения и не является безопасной миграцией панели на другой IP.

## Проверки и ограничения

Запустить `bash -n install.sh`, `python3 scripts/verify_release.py --root .`, `sha256sum -c SHA256SUMS`, `bash tests/run.sh`. Новые офлайн-контракты находятся в `tests/test_2517_r18_reliability.py`. Полную установку, TCP/443 с реальными клиентами, фактический `rw-core run -test` с новым каскадным профилем и live Nginx Stream на разных VPS **требуется подтвердить отдельно**.

## План безопасного staging и восстановления

1. Использовать **две пустые отдельные тестовые VPS** для каскада; не подключать production Internal Squads. Сделать образы диска обеих машин и проверить возврат к ним.
2. Выполнить стандартную установку, проверить `nginx -t`, `systemctl status nginx`, `docker ps`, локальную диагностику и создание приватных профилей. Никакие ключи/UUID не публиковать.
3. Импортировать профили в тестовую Remnawave, подтвердить доступность нового клиентского подключения, разрешение DNS только на Exit и отсутствие доступа клиентов Entry/Exit к адресам самих нод. Проверить остановку Exit: Entry должен отказывать, а не переходить на прямое соединение.
4. Для Hybrid протестировать два маршрута TLS (свой домен и выбранный внешний SNI), certificate renew, внешний порт 443, HTTP/80 ACME, затем опциональный локальный tcp-deploy и откат.
5. Нагрузочный тест с долгими сессиями, UDP-играми, мобильной сетью, видео и новыми TCP-соединениями. Сопоставить `--diagnose-resources` и `--diagnose-quality` до/во время/после нагрузки. Если есть тайм-ауты или отрицательные результаты, **откатить VPS snapshot**, а не менять сетевую политику вслепую.
6. Не переводить в production, пока GitHub Actions на опубликованном коммите не завершится успешно на всех заявленных ОС и не будет зафиксирован живой протокол приёмки.

Release manifest маркирует проект как staging и **не является криптографической подписью происхождения**. Проверка ZIP SHA-256 должна быть получена независимо от самого архива.
