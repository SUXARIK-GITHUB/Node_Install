## 1. Подтверждённый дефект: тест APT не был полностью изолирован

В `tests/test_210_cleanup.py` перенаправлялся только `Dir::Cache::archives`. Для APT оставались системные `Dir::State::lists` и binary cache. Конфигурация `Dir::Etc::parts "-"` также создавала предупреждение о несуществующем каталоге `/etc/apt/-/`.

На исходнике повторно прошли **349 тестов от root** (17.955 с). Тот же набор от UID 65534 завершил 349 тестов с единственным отказом:

```text
FAIL: test_real_apt_locked_cache_defers_then_cleans
AssertionError: 'WARNING' != 'PASS'
```

Отдельный минимальный опыт настоящим `apt-get clean` от непривилегированного UID дал:

```text
E: Could not open lock file /var/lib/apt/lists/lock - open (13: Permission denied)
E: Unable to lock directory /var/lib/apt/lists/
```

При этом временный `.deb` уже удалился: операция дошла до реальной очистки, но затем завершилась с `rc=100` на другом каталоге. Root мог не заметить выход за пределы fixture. Сам production helper правильно вернул WARNING на permission error — менять его на ложный PASS не нужно.

**Исправлено:** Dir, Dir::Etc/parts/main, Dir::State/lists/status, Dir::Cache/archives/pkgcache/srcpkgcache и Dir::Log направлены в один временный корень с пустыми локальными конфигами. Sandbox user — текущий пользователь теста. Реальные POSIX-блокировки сохранены. Проверяется фактически разрешённая конфигурация через `apt-config shell`, сохранность dpkg fixture, соседнего файла и inode lock. Никаких sudo, NoLocking, удаления lock или ослабления проверок.

Журналы: [исходный non-root набор](evidence/ci_original_unprivileged.txt), [минимальное воспроизведение](evidence/ci_apt_reproduction.txt). Параметры Dir и порядок чтения конфигурации описаны в [официальной man page APT](https://manpages.debian.org/trixie/apt/apt.conf.5.en.html).

## 2. Подтверждённая ошибка порядка workflow; причина удалённого 129 — ещё вывод, не полный лог

В исходном `ubuntu-26-userspace` сначала выполнялся checkout, и лишь затем устанавливался Git. Если в базовом контейнере Git отсутствует, [actions/checkout использует REST-загрузку файлов](https://github.com/actions/checkout#usage). Такой каталог не является Git clone. Установка Git позднее не создаёт `.git` задним числом.

Команда `git diff --check` в отдельном каталоге без `.git` локально воспроизвела **exit 129** с сообщением `Not a git repository`. Это согласуется с опубликованным кодом задания 26.04. Однако без полного удалённого лога нельзя утверждать, что 129 там возник именно на этой команде: теоретически возможны и другие причины.

**Исправлено:** независимая от файлов проекта установка Git, CA и тестовых зависимостей перенесена перед checkout в 26.04-контейнере. После checkout отдельный шаг требует настоящий worktree, выводит commit и проверяет SHA256SUMS. Git diff выполняется отдельным шагом после тестов, дополнительно проверяется неизменность tracked files. Матрица ОС, read-only token и закреплённый checkout action сохранены.

**Не нужно удалять `.git` на компьютере пользователя.** Проблема порядка относится к одноразовому CI-контейнеру, а не доказывает повреждение рабочего clone.

## 3. Дополнительно устранена зависимость тестового Nginx от системных scratch-директорий

Пакетная сборка Nginx может иметь абсолютные defaults `/var/lib/nginx/body`, `proxy`, `fastcgi`, `uwsgi`, `scgi`. Один `-p` не перенаправляет такие абсолютные пути. В исходной локальной сборке это подтверждено `nginx -V`.

Теперь в **тестовом** конфиге все пять temp paths находятся под `TemporaryDirectory`. Production-конфиг Nginx и `install.sh` не менялись. Директории PID, error log, Unix-сокет, сертификаты и сайт также остаются приватными. В успешном root-прогоне сравнение метаданных наблюдаемых `/var/lib/apt/lists`, `/var/cache/apt`, `/var/lib/nginx` и `/var/lib/dpkg/status` до/после не нашло изменений. Это проверка этих путей, не полный аудит каждого системного syscall.

## Как применить без изменения работающей ноды

1. Сохраните копию своей локальной папки репозитория вместе с актуальной `.git` и незакоммиченными файлами. Согласуйте нужные локальные изменения и `main` обычным Fetch/Pull, без Force push или reset.
2. Распакуйте новый полный ZIP в отдельную папку. Перенесите его содержимое в свой clone, включая скрытую `.github`, сохранив действующую `.git`. В архиве `.git` нет. Не удаляйте локальный clone целиком.
3. В GitHub Desktop проверьте Changes. `install.sh`, preview/assets и VPN-параметры не должны измениться относительно исходной 2.1.0. Закоммитьте исправление, например `Fix CI isolation and Ubuntu 26 checkout`, и выполните обычный Push origin.
4. Проверяйте **новый** run на новом commit. Старый run останется красным; повтор старого commit не подхватит новые файлы. Нужны успешные test (ubuntu-22.04), test (ubuntu-24.04) и ubuntu-26-userspace.

GitHub описывает просмотр/перезапуск в [Using workflow run logs](https://docs.github.com/en/actions/monitoring-and-troubleshooting-workflows/using-workflow-run-logs) и [Re-running workflows](https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-workflow-runs/re-running-workflows-and-jobs). Перед удалённой публикацией при доступной Linux dev/CI-среде можно выполнить `bash tests/run.sh`. Собирать тестовое окружение на работающей VPN-ноде ради этого исправления не нужно.

**Rollback:** возврат CI-правок обычным revert соответствующего нового commit или восстановление файлов из сохранённой копии с новым коммитом. Force push не нужен. Перезагрузка/backup БД/firewall-rollback/повторный install на VPS к этому исправлению не относятся. Нода из этого workflow не развёртывается и не перенастраивается.
