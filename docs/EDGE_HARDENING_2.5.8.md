# VKarmani Node 2.5.8 — проверка публичной поверхности после рекомендаций от 14.10.2026

**Статус: непубликованный staging-кандидат.** Изменение относится к новой выделенной ordinary-ноде. Никакого массового обновления действующих VPS, инбаундов панели, каскада, SSH-политики или установленного Docker/Nginx без отдельной проверенной миграции здесь нет.

## Основание и границы

14 октября 2026 передано предупреждение о массовой блокировке узлов и рекомендуемая конфигурация: собственный Selfsteal на 443/TCP, HTTP 301 на 80/TCP, исключение явно TLS-вложенных транспортов, управляющий порт RemnaNode только от IPv4 панели, TLS 1.2/1.3 и HSTS. Это **требования к этой доработке**, а не утверждение, что каждая нода с ними будет доступна при IP/ASN-блокировке.

Технические основания:

- Nginx HSTS и наследование `add_header`: https://blog.nginx.org/blog/http-strict-transport-security-hsts-and-nginx
- Nginx `add_header ... always`: https://nginx.org/en/docs/http/ngx_http_headers_module.html
- VLESS Vision доступен при TCP+TLS/REALITY (а XHTTP не является совместимой заменой RAW): https://xtls.github.io/en/config/inbounds/vless.html
- REALITY, fallback и его безопасность: https://xtls.github.io/en/config/transports/reality.html
- Node Port — только для панели: https://github.com/remnawave/panel/blob/main/docs/install/remnawave-node.md

Внешняя рассылка не была использована как доказательство эффективности против любых блокировок. Закрытые Telegram/Discord-источники не проверялись.

## Что делает 2.5.8 при *новой* установке

| Проверка/механизм | Реальное поведение |
|---|---|
| `80/tcp` | Nginx принимает на выбранном IPv4. Собственный Host → 301 на строго заданный `https://DOMAIN/` с сохранением URI; ACME HTTP-01 обслуживается отдельно; неизвестный Host → 404 |
| `443/tcp` | Внешний IPv4:443 принимает Xray RAW+REALITY. Авторизованный VLESS/XTLS Vision обрабатывается Xray, не HTTP. Неподтверждённое REALITY-подключение может быть перенаправлено к собственному Nginx через PROXY v1 на Unix socket; прямого публичного прослушивания этого сокета нет |
| HTTPS сайта | Nginx использует отдельный собственный сертификат узла и разрешает TLS 1.2 и 1.3, HTTP/1.1 и HTTP/2 |
| HSTS | Только в ответах HTTPS *именованного сайта*: `Strict-Transport-Security: max-age=300`. Без `includeSubDomains` и `preload`. Срабатывает также для ошибочных HTTP-ответов на этом TLS-хосте (`always`) |
| Node Port | По умолчанию 2222/TCP; host network; политика UFW `deny incoming` плюс разрешения от зарегистрированных публичных IPv4 панели; нет массового открытия 2222; IP могут отличаться на каждой установке |
| Дополнительные транспорты | RAW/Vision остаётся основным. XHTTP является альтернативным профилем и **не становится автоматически Vision**. Одновременная SNI-маршрутизация разных транспортов не устанавливается скрытно |
| Проверки | Локальная проверка Unix socket тестирует верные сертификат, TLS 1.2/1.3, тело сайта и HSTS; диагностическая проверка при запущенном Xray проверяет оба точных TLS-режима по внешнему IPv4:443 и ожидаемый контент |

**Важно:** конфигурация Nginx с `ssl_protocols TLSv1.2 TLSv1.3` не означает, что *публичный Xray fallback* гарантированно обслуживает оба варианта: последний участок подтверждается только настоящими клиентскими проверками с `curl/openssl` на работающей тестовой VPS. В `--require-xray` и postboot неподтверждённый TLS1.2/1.3/HSTS фиксируется как **FAIL**, не PASS.

## Безопасная внешняя диагностика (без внесения изменений)

Запускайте на контролируемой staging VPS после установки и применения корректного профиля в Remnawave. Указывайте настоящие адреса вашей ноды, не домен панели.

```bash
DOMAIN=node.example.test
IP=192.0.2.10

sudo nginx -t
sudo ufw status verbose
sudo ss -lntp
sudo bash install.sh --check --require-xray

# 80/TCP: ровно 301 и правильный Location, не переходим по редиректу.
curl -4 --noproxy '*' --max-redirs 0 -sSI \
  --resolve "$DOMAIN:80:$IP" "http://$DOMAIN/"

# 443/TCP: строго принудительные версии протокола, сертификат и HSTS.
curl -4 --noproxy '*' --http1.1 --tlsv1.2 --tls-max 1.2 \
  --resolve "$DOMAIN:443:$IP" -sSI "https://$DOMAIN/"
curl -4 --noproxy '*' --http1.1 --tlsv1.3 --tls-max 1.3 \
  --resolve "$DOMAIN:443:$IP" -sSI "https://$DOMAIN/"
```

IP и DOMAIN — **учебные примеры**, перед запуском замените. `curl` должен проверять TLS, без `-k`/`--insecure`. Для 443 ответ должен содержать **один** `Strict-Transport-Security: max-age=300` и настоящий 200/404 страницы. `curl -I` не проверяет содержимое HTML, поэтому `--check --require-xray` дополнительно сравнивает тело с локальной страницей.

Данные проверки на самом сервере — **локальная проверка**, не измерение с разных российских провайдеров. Внешний firewall/security-group хостера диагностируется отдельно. Выполните отдельную проверку Node Port из сети панели (разрешено) и с постороннего IPv4 (тайм-аут/REJECT); без этого **нельзя объявлять порт защищённым**. Для проверки доступности со стороны клиента и ASN нужны независимые внешние сети.

## Почему не меняются другие важные компоненты

- **Никаких автоматических inbound/Host/profile-переписей.** Изменение XHTTP или включение Vision в неподдерживаемый транспорт может разорвать действующие подключения.
- **Не включается SNI-разводка в Nginx stream автоматически.** Установщик генерирует *альтернативы* RAW и XHTTP, не два одновременно работающих inbound на 443. Для реального мультиплекса требуются отдельная конфигурация Xray/Nginx с проверкой PROXY protocol, SNI, SSL-preread и независимые домены, иначе это несовместимая миграция.
- **Нет новой глобальной политики HSTS для всех поддоменов.** Начальный `max-age=300` можно увеличить после проверки сертификата, редиректа, восстановления и совместимости; откат не удаляет мгновенно уже закэшированную политику на клиентах.
- **Не модифицируются чужие firewall-правила и действующие хосты.** У новой установки UFW изначально создаётся на выделенной VPS; на существующем production нельзя запускать первичную установку вместо узкого upgrade.
- **Не отключается RKN Guard**, не меняется его собственный lifecycle и обновление списков. Фильтрация нежелательных источников не доказывает обход DPI/IP-блокировки.

## Приёмка и ограничения

Применимо только после snapshot, проверки восстановления и доступа к консоли провайдера. На отдельной VPS: fresh install → `nginx -t` → `--check --require-xray` → внешний curl TLS1.2+TLS1.3 → внешний allow/deny тест Node Port → клиент с RAW/Vision → reboot → повтор проверок → мониторинг ошибок.

В текущем офлайн-кандидате на реальном локальном Nginx с временной CA проверены TLS 1.2, TLS 1.3, content, заголовок HSTS на 200/404/405, отрицательные варианты и отказ при несовпадении сертификата. **Не проверены:** настоящий Xray, публичный доступ из РФ, Remnawave панель, внешняя UFW-политика, обновление действующих узлов, XHTTP-клиент и независимая двухсерверная цепочка. При их отсутствии статус — **staging only**.

## Возврат

Для staging — восстановление snapshot. Для локального изменения HSTS на контролируемой копии Nginx: сохранить рабочий файл до изменения, проверить `nginx -t` перед и после; вернуть ровно его прежнюю проверенную копию, снова `nginx -t` и reload. Скрипт 2.5.8 **не содержит команды миграции HSTS на старые установки** и автоматически их не правит; команда `--update-cover` предназначена для содержимого сайта, не для Nginx-конфигурации. Кэш HSTS после отката может жить до 300 секунд.
