# VKARMANI Node Install 2.5.14 r15 — корректная команда GitHub

Дата: 2026-10-21 · состояние: `INCOMPLETE_STAGING_ONLY` · происхождение: локальная полная ZIP-сборка на базе r14. **Не публиковалось в GitHub автоматически.**

## Цель и объём

Релиз поднимает установленный номер `INSTALLER_VERSION` с `2.5.13` до `2.5.14`, выравнивает версию в окончании установки, постустановочных gate'ах, шаблонах оператора, стадиях обновления сайта, тестах, сборочном манифесте и документации. Предыдущая версия `2.5.13` **не удалена** из проверяемого списка исторических завершённых нод: обновление диагностик/обслуживания не должно ложно отклонять старую ноду.

Основное поведение Ordinary/Cascade, REALITY RAW/XHTTP, TLS Selfsteal, Docker, сети, DNS, firewall, панели и каскада из r14 **не менялось**. Функциональность переопределения Node Port новым Ordinary-установщиком остаётся в коде, но в базовой инструкции более не показана и не задействуется. **По умолчанию Node API `2222/tcp`, клиентский REALITY `443/tcp`, Certbot HTTP `80/tcp`.**

## Установка из GitHub — только после публикации r15

`README.md` теперь содержит раздел «Установка с GitHub · 2.5.14 r15 (после публикации)». Команда:

1. требует `root`, проверяет, что рабочая папка не существует, клонирует `main` из указанного GitHub;
2. сверяет неизменяемый заранее записанный SHA-256 **файла `install.sh` новой версии**;
3. проверяет `SHA256SUMS` по всем файлам репозитория и содержимое `BUILD_MANIFEST.json` через `scripts/verify_release.py`;
4. сверяет пару `(version, build_id)` с `('2.5.14', '20261021-r15-github-install')` и staging status;
5. проверяет Bash-синтаксис, `--version == 2.5.14`, и лишь затем запускает `bash ./install.sh` **без параметров**.

Пока GitHub `main` содержит 2.5.13 r12 (последний проверенный коммит `197cd273f7954a84e8445ea1d333224304777eac`), п. 2 обязан остановить выполнение. README намеренно **не утверждает**, что r15 уже опубликована. Проверки из рабочего дерева и внутренние хеши не доказывают происхождение репозитория; при выпуске необходимо сверить фактический коммит и провести CI. Не редактировать pinned SHA256 «наугад», а пересчитать его после окончательной сборки.

Сборка по ZIP доступна до публикации и содержит полный исходный проект, включая `docs/` и `tests/`, с локальным release manifest и контрольными суммами. ZIP SHA-256 надо проверять по независимому доверенному каналу.

## Совместимость установки и финализации

- `install.sh --version` выводит `2.5.14`.
- На свежей VPS в `install-version` и `INSTALL_COMPLETE` должен оказаться один и тот же номер `2.5.14`. Без успешно проверенной финальной стадии статус завершения не должен появиться.
- Генерируемый `finalize_install.py` побайтно соответствует версии в `integrations/finalize_install.py`; `VERSION='2.5.14'`. Финализация не допускает маркер или checkpoint другой версии, не меняет ОС повторно.
- `installed_contract_class`, RKN action gates, image update, `--prepare-xhttp`, `staging_web_deploy` и maintenance поддерживают прежние ревизии, но отдельно поддерживают `2.5.14`.
- Новые версии после `2.5.14` остаются fail-closed до явного обновления allowlist.

## Обязательные испытания / операционный порядок

1. Сверить финальный SHA256 ZIP и внутренний release manifest. Для README Git-команды отдельно сверить опубликованный SHA256 `install.sh` и `build_id`.
2. Проверить работу на полностью чистой staging VPS с **проверенным snapshot диска и независимой консолью**. Не ставить поверх существующей ноды, каскада или активных конфигов.
3. Убедиться, что выбирается соответствующая роль, режим Selfsteal и значения портов `2222/443`; передать точный Node Port в Remnawave Panel.
4. Пройти `nginx -t`, TLS по реальному 443, ACME renew, TCP/UDP клиент, UFW allowlist Node API, reboot/`--check` и при необходимости `--finish-install` по записанному checkpoint.
5. Для гибридного режима отдельно проверить Nginx Stream socket/SNI, PROXY v1 между Xray и Nginx, правильный чужой TLS target, сохранность собственного HTTPS и отсутствие чужих слушателей 443.
6. Проверить каскад в паре Entry/Exit со snapshots обеих VPS и контролируемой негативной проверкой outage/fail-closed; не выполнять это на production.
7. При сбое: **rollback полного снимка VPS провайдера**, проверка SSH и возврат исходных DNS/панельных объектов. Локальные резервные копии отдельных компонентов не эквивалентны полному rollback ОС.

## Ограничения

Ни публикация в GitHub, ни GitHub Actions для r15, ни развёртывание на реальной VPS в этой сборке не выполнялись. `INCOMPLETE_STAGING_ONLY` неизменен. Офлайн-тесты не подтверждают клиентский трафик, стабильность внешнего TLS target, работу Nginx Stream на конкретном дистрибутиве, изменения в ТСПУ или устойчивость к сетевой фильтрации. Все server-/panel-/data-операции требуют отдельной безопасной процедуры.
