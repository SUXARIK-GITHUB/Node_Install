# Node Install 2.5.18 r43 — измерение сетевого пути и контроль клиентской совместимости

**Дата:** 2026-11-07  
**Статус:** `INCOMPLETE_STAGING_ONLY`  
**Основа:** полный проверенный ZIP r42.

## Назначение и границы

Это выпуск **только для диагностики скрытности и возможных утечек**. Сохраняет существующие RAW+REALITY/Vision, XHTTP-шаблон, Selfsteal, HTTPS-сайт, режимы SNI, RemnaNode, каскад, Docker, Nginx, UFW, SSH, ключи, DNS-настройки и меню без изменения поведения. Не выполняет обновления ядра или образа, не подключается к панели и не переключает пользователей. Выходные отчёты ограничены кодами проверок и обезличенной статистикой.

Цель — различать **наблюдаемые признаки сетевой проблемы**, а не объявлять любое соединение, которое не удалось, «блокировкой РКН». Даже два разных результата из разных сетей не доказывают участие ТСПУ: причиной может быть DNS, маршрутизация, доступность сайта, firewall, конфигурация клиента или перегрузка.

## Функции r43

| Компонент | Возможности | Что НЕ доказывает |
|---|---|---|
| `scripts/stealth_external_audit.py` | Опционально 1 TCP-дозвон на TCP/443; 1 ограниченное скачивание **собственного** статического файла по HTTP/2 | Не идентифицирует DPI, ТСПУ или REALITY-клиента |
| `scripts/network_path_review.py` | Сравнение обезличенных отчётов контрольной и исследуемой сетей | Не устанавливает причинность и не знает принадлежность IP без заявления оператора |
| `integrations/client_route_audit.py` | Статическая проверка Xray JSON на `freedom` по умолчанию, явные `direct`-правила, внешнюю привязку прокси, баланcировщики | Не измеряет TUN, VPN kill switch, ОС, IPv6, DNS и UDP |
| `scripts/reality_client_matrix.py` | Упорядочивает результаты **реальных испытаний оператора** по версии ядра, fingerprint, XHTTP/RAW, PQ/hybrid key share, исходящему IP | Не проводит испытания само и не гарантирует аналогичный результат на другом провайдере |
| `scripts/stealth_report_compare.py` | Учёт новых полей `tcp443`, `large_http2_asset`, `downloaded_bytes` | Не сравнивает произвольные захваты/PCAP |

### 1. Сравнение сетевых путей — только OWN VPS

Подготовьте **один** доступный только вам тестовый домен и публичный IPv4. Для проверки длинного ответа разместите на собственной **staging**-нoде отдельный публичный статический файл размером **от 32 до 256 КиБ** (например `/assets/canary.bin`), не содержащий приватных данных. Встроенное размещение такого файла не предусмотрено; не трогайте production-сайт для диагностики. На сервере должно быть настроено настоящее HTTP/2, TLS 1.3 и корректный сертификат.

На двух принадлежащих вам или явно разрешённых точках наблюдения выполните **одинаковую** команду. Используйте настоящий FQDN/IP ноды вместо плейсхолдеров и сохраните результаты в разных локальных файлах:

```bash
umask 077
python3 scripts/stealth_external_audit.py \
  --domain OWN_NODE_FQDN --ip OWN_PUBLIC_IPV4 \
  --confirm-owned-endpoint --tcp443 --http2-actual \
  --large-static-path /assets/canary.bin > own-path-control.json
```

Запустите такую же команду из исследуемой сети, результат сохраните как `own-path-affected.json`. **Не** запускайте на посторонних IP или доменах. В `--large-static-path` допустим только безопасный путь внутри своего HTTPS-сайта (без query, redirect, percent-encoding, `..`). `curl` запускается с `-q`, без системных прокси и редиректов, с лимитом 262144 байта, ограниченными таймаутами; содержимое и заголовки ответа не сохраняются. Результат `PASS` в скачивании означает только `HTTP/2 200` и получение как минимум 32768 байт. Это не вывод о сопротивлении ТСПУ.

После проверок **при отсутствии изменений домена, сайта, IP, версии TLS, сервера и времени тестирования** сравните файлы офлайн:

```bash
python3 scripts/network_path_review.py \
  --control own-path-control.json --affected own-path-affected.json \
  --confirm-same-owned-endpoint --strict
```

Отчёт выделяет `DNS_RESOLUTION_DIFFERS`, `TCP443_REACHABILITY_DIFFERS`, `TLS13_HANDSHAKE_OR_HTTPS_DIFFERS`, `HTTP2_APPLICATION_RESPONSE_DIFFERS`, `LARGE_HTTPS_RESPONSE_DIFFERS` и другие разницы. При отсутствии обязательных контролей выводится `INSUFFICIENT`. Никакой классификатор не утверждает, что различия вызваны ТСПУ/РКН. Если подключение не работает, до замены TLS-параметров отдельно проверьте исправность VPS, nginx, сертификата и доступность у самого хостера.

Проверка Node API через `--node-api-port N` из r42 остаётся отдельной: запускать **с внешнего IP, не внесённого в allowlist панели**, и отдельно проверить доступность с IP панели. Не путайте TCP timeout с доказанным firewall deny.

### 2. Проверка клиентских маршрутов

На **своём** компьютере подготовьте экспорт Xray JSON (не URI и не скриншот). Файл содержит секреты, поэтому храните только локально, с правами `0600`, не публикуйте в чате, Git, issue, telemetry или QA-логах.

```bash
chmod 600 /PRIVATE/PATH/client-xray.json
python3 integrations/client_route_audit.py \
  --client-config /PRIVATE/PATH/client-xray.json --strict
```

- `DEFAULT_OUTBOUND_IS_DIRECT` — первый outbound `freedom`, возможен прямой выход.
- `EXPLICIT_DIRECT_ROUTING_PRESENT_REVIEW_EACH_EXCEPTION` — маршрут на `freedom`, для некоторых приложений может быть разрешён осознанно, но всякое исключение требует отдельной проверки.
- `LOCAL_PROXY_LISTENER_NOT_RESTRICTED_TO_LOOPBACK` — публично/широко привязанный SOCKS/HTTP listener; проверить firewall/loopback.
- `BALANCER_RULES_REQUIRE_RUNTIME_VERIFICATION` — статический анализ не разрешил выбранный маршрут.
- `STATIC_REVIEW` — критически очевидных ошибок не найдено, **это не означает отсутствия утечек**.

Сверьте **реальный** внешний IPv4/IPv6 клиента, DNS и TCP/UDP-пакеты при включённом VPN, смене Wi-Fi/LTE, отказе Exit и обрыве туннеля. Отсутствие `direct` в конфиге Xray не доказывает, что другое приложение или ОС не отправляет данные напрямую.

### 3. Проверка XHTTP/Remnawave на staging

Текущий инструмент `integrations/xhttp_profile.py` формирует отдельный серверный импортный шаблон с `network=xhttp`, `mode=auto`, `flow=""`, без изменения live-ноды. Перед выпуском клиенту существующий скрипт `integrations/xhttp_subscription_audit.py` должен подтвердить соответствие **реального приватного экспорта клиента из подписки** серверному XHTTP-шаблону:

```bash
python3 integrations/xhttp_subscription_audit.py \
  --server /PRIVATE/PATH/profile-xhttp.json \
  --client /PRIVATE/PATH/own-client-export.json --strict
```

Рабочий end-to-end **не может быть выполнен здесь без вашей панели и тестовой ноды**. Для приёмки вручную обязательно выполните цепочку:

1. В Remnawave на **staging** создать Config Profile с одним проверенным XHTTP Inbound, привязать к тестовой Node.
2. Создать Host именно для этого Inbound. Проверить его адрес/порт, SNI и дополнительные overrides.
3. Активировать Inbound для тестового Internal Squad и тестового пользователя.
4. Получить действительную подписку и сравнить экспортированный **от клиента** профиль со своим серверным шаблоном.
5. Проверить реальное подключение, собственный внешний IP, DNS/IPv6/UDP, смену сетей, переподключение и поведение при отказе VPN.
6. Если любая проверка не прошла — не активировать XHTTP для действующих пользователей; оставить RAW+REALITY и локальный rollback.

Официальная документация: https://docs.rw/learn-en/config-profiles/ и https://docs.rw/learn-en/hosts/ .

### 4. Матрица версий REALITY и клиентов

Файл доказательств `0600` должен содержать **только метаданные выполненных вами испытаний**, без URI, UUID, SNI, домена, адреса, прокси-токенов и ключей:

```json
{
  "schema": 1,
  "server_core": "26.10.31",
  "trials": [
    {
      "app": "xray",
      "client_core": "26.10.31",
      "fingerprint": "chrome",
      "transport": "raw",
      "key_share": "UNKNOWN",
      "attempts": 1,
      "successes": 0,
      "egress": "NOT_MEASURED"
    }
  ]
}
```

Это **пример схемы данных, а НЕ результаты испытаний**. Вписывайте версии и числа только после фактических собственных тестов. `key_share=PRESENT` разрешается указывать только после отдельной проверки ClientHello. `egress=EXPECTED_VPN_IP` — только после проверки реального внешнего адреса; иначе `NOT_MEASURED`. CLI:

```bash
chmod 600 /PRIVATE/PATH/own-trials.json
python3 scripts/reality_client_matrix.py --evidence /PRIVATE/PATH/own-trials.json --strict
```

Матрица учитывает возможную несовместимость сервера Xray >= 26.9.8 с клиентами без требуемого гибридного key share (см. [XTLS/Xray-core #7259](https://github.com/XTLS/Xray-core/issues/7259)). `randomized` отмечается для повторной проверки после перезапусков из-за задокументированной уязвимости генерации ClientHello/HRR в отдельных версиях (см. [#6714](https://github.com/XTLS/Xray-core/issues/6714)). Не закрепляйте намеренно уязвимую устаревшую версию сервера ради совместимости fingerprint. Не меняйте всем клиентам fingerprint и не отправляйте в отчёт ключи или URL подписок.

## Критерии приёмки и откат

- **Офлайн**: пройти `bash -n`, `python compile`, все тесты, `verify_release`, SHA-256 и ZIP roundtrip. Не допускать потери файлов или ослабления защитных проверок r30–r42.
- **Staging**: показать контроль и исследуемую сеть, не только один запрос; подтверждённое TCP/TLS/H2 поведение, стабильную работу REALITY, проверенную цепочку XHTTP `Profile -> Node -> Host -> Squad -> subscription -> client`, реальный внешний IP и отсутствие DNS/IPv6/UDP direct-утечек при сбое.
- **Перед production**: snapshot с подтверждением восстановления, аварийная консоль, тест на отдельных клиентах и версиях, затем постепенный rollout. Если есть отличие — остановиться, не менять автоматически `SNI`, порт, TLS, транспорт или маршруты.
- **Rollback**: r43 diagnostic tools read-only, для них достаточно перестать запускать скрипты. Для ручных изменений на staging откатить тестовые Hosts/Profiles и восстановить собственный snapshot; live VPS этим выпуском не изменялись.

**Не реализовано и не должно считаться выполненным:** live тест ТСПУ из РФ, реальный REALITY ClientHello, session tickets/post-handshake, автоматизированная проверка подписок панели без доступа к панели, экспериментальные XMUX/QUIC/FinalMask или автоматический переход RAW→XHTTP. Их нельзя подтвердить офлайн и нельзя включать в production без реальных измерений.
