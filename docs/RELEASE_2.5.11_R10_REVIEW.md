## Наиболее важная найденная эксплуатационная проблема

У Ubuntu 26.04 нижний порог был 1536 MiB, так что любая новая VPS с 1 GiB останавливалась в preflight. На остальных системах 900 MiB позволяли пройти preflight, но swap создавался после многочисленных операций APT, изменения firewall/SSH и других подсистем; на малой RAM это риск OOM/прерванной установки. Смена порога сама по себе недостаточна.

### Исправление: низкая память до первого APT

- Порог 900 MiB `MemTotal` унифицирован для Ubuntu 22.04/24.04/26.04 и Debian 12/13, обе архитектуры — только поддерживаемые amd64/arm64.
- Для хостов с фактической RAM меньше 1536 MiB **до каких-либо APT-операций** проверяется наличие минимум 1 GiB *активной* swap-памяти.
- Если swap отсутствует, на чистой выделенной VPS выполняются fail-closed проверки: ext4/XFS для корневой ФС; нормальный `/etc/fstab`; инструменты `dd`, `mkswap`, `blkid`, `swapon`, `stat`, `findmnt`, `ln`; отсутствие постороннего `/swapfile-vkarmani`; свободное место минимум 6144 MiB по текущему предзапусковому контракту. После проверенной резервной копии `/etc/fstab` создаётся полноценный 1GiB swapfile с `0600`, валидацией сигнатуры и атомарной публикацией через hardlink, активацией и идемпотентной записью в fstab. Никакие чужие swap-разделы/файлы не форматируются.
- Во время installation stage перед Docker ещё раз контролируется активный swap, а версия 2.5.11 в acceptance-контракте проверяет достаточный swap после штатного reboot.
- При неготовой ФС (например, Btrfs), нехватке места или постороннем файле установка прекращается **до APT**. Если не удалось включить swap, пользовательский доступ/файлы не удаляются; требуется ручной разбор ошибок и snapshots. Прерывание в середине swap-фазы может оставить `.tmp` — повторный запуск откажется его перезаписывать до проверки оператором.

**Не доказано:** что конкретный хостер разрешит `swapon` и выдаст достаточные RAM/IOPS, что Ubuntu 26.04 и RemnaNode/Xray/Docker успешно устанавливаются с нуля и проходят 24-часовую нагрузку при 1 vCPU / 1 GiB. Для доказательства требуется чистая staging VPS 1 vCPU/1 GiB каждой поддерживаемой ОС, консоль провайдера, ручная приёмка и проверка реального клиентского трафика. Swap увеличивает устойчивость, но не заменяет RAM.

## Генератор сайтов и шесть тем

- `scripts/cover_variants.py`, исходные шесть HTML/CSS пар и старые визуальные настройки оставлены неизменными (не было подтверждённой ошибки в разметке, требующей редизайна).
- Для основного генератора прогнаны браузерные проверки на 4 вариантах и 9 ширинах (36 кейсов), без JavaScript ошибок, сетевых запросов и горизонтального переполнения.
- Для шести статических тем прогнаны 42 браузерных проверки при 7 ширинах; **из-за блокировки localhost/file:// окружением** HTML и CSS вставлялись только в память браузера, а CSP удалялась **только во временной тестовой копии**. Исходные файлы, CSP и отсутствие внешних скриптов проверены отдельно, ни один файл темы не менялся.
- Регрессионные unit-тесты публикации всех шести тем/хешированного CSS, проверки local Selfsteal, неизменности Nginx, восстановления первоначальных прав, отказа при сторонних правках, повреждённых backup и прерванных транзакциях сохранены.
- Проверку `nginx -t` и HTTP/TLS на реальном сервере необходимо выполнять отдельно, статические/isolated прогоны не подтверждают доставку REALITY через публичный IPv4.

## Selfsteal, TLS, маршруты и эксплуатация

- Сохранены REALITY fallback на `/dev/shm/nginx.sock` и PROXY v1, оригинальный Nginx-конфиг, TLS-проверки, local/private socket, строгая политика публикации, тайм-ауты и fallback-ограничения; новые визуальные шаблоны не навязывались.
- Текущий установщик использует системный Nginx: переход на nginx.org потребовал бы отдельной проверки stream-модуля, пакетов и rollback. Смена поставщика пакета не производилась.
- Существующие fix r8/r9 (лишний Docker `--host`, шаблон `assets/style-<hash>.css`, r7 ownership, конфликт legacy cover/r7 journal, ordinary routing) сохранены.
- Версия 2.5.11 согласована с признанными контрактами finalizer/maintenance/RKN/acceptance и инструментами сборки архива. В README удалена команда запуска старого опубликованного `r7e`, который имеет известную ошибку Docker CLI; SHA исторического исходника всё ещё можно верифицировать read-only.
- Встроенные версии Python и исходные standalone-файлы должны совпадать побайтово; это проверяют тесты.

## Планы тестирования и приёмки

**Offline / контейнер тестовой среды:** `bash -n`, AST parse Python, JSON decode, все Python unittest, негативные проверки изолированных транзакций, isolated Nginx с временными сертификатами, release SHA256, readonly source vs clean extracted archive, generator browser matrix (см. зафиксированные выше ограничения). Конкретное число и результаты итоговых тестов указать по фактическому финальному логу, а не предполагать здесь заранее.

**На staging VPS:** создать snapshot и проверить аварийную консоль и восстановление; удостовериться в <=1 GiB RAM и 1 vCPU, свободном месте >=6 GiB, ext4/XFS или готовом swap; сделать полную установку, check preboot/postboot, `swapon --show`, `grep -F /swapfile-vkarmani /etc/fstab`, `free -m`, `docker compose ... config`, `docker ps`, `nginx -t`, TLS GET cover и проверку исходящего IPv4, UFW/API/SSH; затем deploy всех 6 тем и rollback; провал подключения Exit и отсутствие DIRECT на Entry; сделать rollback VPS snapshot, не вручную удаляя отдельные ресурсы. Нужны тесты реальных подписок, доступности панели, DNS/UDP и ночных таймеров.

**Риски:** 1 vCPU / 1 GiB + swap может существенно деградировать по задержкам; нехватка disk/IOPS приведёт к остановке. Не считать это гарантией достаточности ресурсов для произвольной нагрузки или другого провайдера. Старые установленные production-ноды этим пакетом автоматически не мигрируются; не заменять ими действующие файлы, базу/конфиг, Docker/NGINX или прежние inbound. Нет данных о реальном live acceptance.
