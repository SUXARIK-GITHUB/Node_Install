## Исходный базис и принцип изменений

База: ранее подготовленный полный архив `2.5.11 r10`, GitHub `main` на начало работы содержал коммит `a1327c0379533b0b5926b06a9d713460bd1e5bbe`. Не изменялись секреты, действующие инбаунды, Panel, каскадные ключи, Node API порт, Docker volumes, интерфейсы либо DNS. В манифесте сохранён исходный source_commit для аудита происхождения; эта отметка не означает, что r11 уже опубликован на GitHub.

## Инструкции GitHub и ZIP

Старый блок `r7e` с известным дефектом Docker CLI убран. Первый блок README содержит последовательный исполняемый Bash-блок: запрет запуска без root, отказ перезаписывать уже существующий каталог, клонирование GitHub `main`, строгую проверку SHA-256 `install.sh` и всех файлов, release-verify, Bash syntax, version и установку с reboot по умолчанию. **До публикации r11 SHA-проверка намеренно отклоняет r10 из main**. После публикации нужно сверить коммит с ожидаемой версией и контрольную сумму через независимый канал, а не доверять одному README в клоне. ## Три приватных результата ordinary-установки

1. `/root/reality-keys.txt` — REALITY параметры, в том числе PrivateKey.
2. `/root/vkarmani-raw-profile.json` — готовый RAW + REALITY + XTLS Vision Config Profile.
3. `/root/vkarmani-xhttp-profile.json` — готовая **альтернатива** XHTTP + REALITY, без Vision, полученная из core-проверенного `/etc/vkarmani-node/profile-xhttp.json`.

Результаты `root:root`, `0600`, содержат приватные ключи и **не должны** размещаться в публичном Git или чатах. Встроенная проверка XHTTP выполняется настоящим ядром из установленного `remnanode` контейнера с временной приватной конфигурацией; она тестирует совместимость JSON, **не доступность от клиента**. Проверяются права/тип файлов, ссылка, число ссылок, размер, формат JSON, отсутствие повторов свойств, структура/flow, idempotency и совпадение байтов финальных копий. Изменённая копия не перезаписывается; ошибки — fail-closed до INSTALL_COMPLETE. Для каскада сохраняются ранее реализованные отдельные профили, XHTTP-экспорт не навязывается.

**Совместимость:** Нельзя обещать «любое ядро и любую версию». XHTTP требует клиентской реализации XHTTP и поддержки используемых параметров REALITY; RAW+Vision имеет отдельные условия. Обе конфигурации **не должны** быть активны одновременно на 443. В панели нужно назначить ровно один профиль, корректный Host, SNI, public key/short ID и squad; проверить действующим клиентом на разных платформах.

`cover-variants/01-atelier` … `06-foundry` получили индивидуальные визуальные темы, собственные inline-SVG иллюстрации, 4 якорных пункта навигации, 3 статьи, раздел идей, нативный FAQ на `<details>`, анимации без JS с `prefers-reduced-motion`, адаптивные сетки. Тематические тексты явно демонстрационные, чтобы не выдавать выдуманные публикации за факты. Нет внешних API, CDN, cookie, пользовательского ввода, сторонних скриптов. Подключение `style.css` сохранено для существующего R7 механизма, который публикует хешированный CSS `assets/style-<hash>.css` с transactional rollback.

Внутренний генератор основного сайта в `install.sh` дополнен навигацией, секциями и редакционной структурой. Сохранены его прошлые контракты: уникальная генерация сайта в зависимости от seed, лимиты содержимого, строгая CSP, локальная раздача Selfsteal и автономная схема.

## Selfsteal, Nginx, обратное проксирование и соединения

Сохранены внешний TCP 443/Xray, REALITY `target=/dev/shm/nginx.sock`, PROXY v1, локальный UNIX сокет Nginx, самостоятельная обработка публичного HTTP/80, TLS/certbot, проверки Nginx и rollback. Нет внешнего `proxy_pass` или добавленного прокси-контейнера. Добавлены заголовки `X-Frame-Options: DENY`, `Cross-Origin-Resource-Policy: same-origin`, `Permissions-Policy` (камера, микрофон, геолокация отключены). Нужны `nginx -t`, живой HTTPS/HTTP2 и проверка отсутствия HTTP header regressions на новой VPS.

Производительность зависит от CPU steal, диска, ядра Xray/RemnaNode, сети провайдера, MTU и реальных маршрутов. Без измерения p50/p95 RTT и throughput нет основания менять TCP BBR, congestion control, буферы, MTU, kernel sysctl, Xray routing или способы TLS fingerprint: такие изменения могут ухудшить соединение или раскрыть сервер. Невозможно гарантировать, что сеть/провайдер не определят назначение трафика.

## RKN/TSPU и источники

На дату аудита подходящий источник исследования включает официальную документацию Xray (REALITY/VLESS/XHTTP), GitHub XTLS, Nginx по PROXY protocol и публичные технические обсуждения, в том числе Habr и сообщества. Описания механизмов фильтрации и успеха обхода существенно зависят от места, оператора, даты, версии и не заменяют тест из **реальной** сети пользователя. В r11 **не добавлялись** нестабильные «антиблокировочные трюки» или внешние обновляемые бинарники: осталась подтверждённая инфраструктура `RKN Guard` из базовой версии. Перед изменением сетевой схемы нужно проверять независимые тесты и возможность отката.

## VPS 1 vCPU / 1 GiB и production-гейты

r10 подготовил механизм проверки 900 MiB MemTotal, >=6 GiB свободного места, активации 1 GiB swap **до первого APT** при RAM менее 1536 MiB (ext4/XFS либо свой существующий swap), отказ перезаписывать чужие файлы и проверки после reboot. r11 сохраняет эти механизмы. Swap **не** гарантирует достаточный CPU/RAM/IOPS; VPS 1 GiB и доступность XHTTP core нуждаются в отдельной проверке.

Обязательная процедура staging:

1. Зафиксировать GitHub коммит и точный SHA-256, сделать проверенный snapshot и обеспечить аварийную консоль; использовать только новую VPS.
2. Запустить verifier, все офлайн тесты, синтаксический анализ, проверить источник зависимостей.
3. На стенде Ubuntu 22.04, 24.04, 26.04, Debian 12/13 проверить 1 vCPU/1 GiB, swap, установку ordinary, TLS, XHTTP-core, файлы `0600`, Nginx, SSH и UFW.
4. После reboot проверить systemd timers/maintenance, Docker, TLS, Selfsteal, запись логов; подтвердить, что три приватных файла не менялись.
5. В Remnawave импортировать **по одному** RAW и XHTTP профили, проверить активные клиенты, слабую сеть/UDP/DNS и Xray трафик. Проверить 6 site-deploy/rollback и каскадные Entry→Exit outage/recovery в отдельном стенде.
6. Замерить RTT/loss/jitter/throughput и CPU/RAM/IOPS в холостом состоянии и под нагрузкой, затем выполнить восстановление snapshot.

**Пока не выполнено:** запуск установщика на реальной VPS, полная приемка всех поддерживаемых ОС на 1 GiB, Remnawave Panel, маршруты клиентов и внешние блокировки. Не накатывать staging архив поверх действующих нод. Не создавать ложный статус `PRODUCTION_READY` или `INSTALL_COMPLETE` вручную.

## Отчет об испытаниях

Проведены локальные проверки в изолированной копии исходников: **69 тестовых модулей / 854 теста / 854 PASS** (от root), Bash syntax, Python AST, JSON parse; среди модулей — fake-host `Nginx`, TLS/PROXY v1, XHTTP, finalizer с отказами, APT solver на локальном `file://`, RKN Guard, UFW, SSH, IPv4-only и ресурсные контракты. В Chromium выполнены **80/80 визуальных сценариев** (шесть сайтов + четыре seed динамического генератора, восемь viewport). Из-за запрета браузерного доступа к localhost/file:// HTML/CSS в этих сценариях вставлялись в память браузера, CSP убиралась **только из тестовой временной копии**. Исходные CSP, отсутствие внешних зависимостей, HTML/CSS и семантика проверены отдельными тестами.

Окончательный архив должен повторно пройти release verify/SHA256 и 854 теста на чистой распаковке (см. финальный отчёт выполнения). Это не подтверждает фактическую установку, работу с Remnawave или VPS 1 GiB. Испытания VPS и реальной панели — **NOT RUN**.
