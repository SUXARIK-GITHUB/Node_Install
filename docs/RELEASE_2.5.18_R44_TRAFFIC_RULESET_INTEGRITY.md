# Node Install 2.5.18 r44 — nftables integrity и ограничения staging

**Дата:** 7 ноября 2026 г.  
**Статус:** `INCOMPLETE_STAGING_ONLY`. **Ни на один production-сервер изменения не применены.**

## Что было сломано

В r39–r43 `integrations/traffic_limits.py` проверял только наличие именованных счётчиков и цепочек nftables. В ситуации, когда правила `limit/quota/drop` отсутствовали, `status` мог печатать `TRAFFIC_LIMITS=ACTIVE`, а `apply` — `ALREADY_ACTIVE`. Это воспроизводится на синтетическом ответе nftables без прав доступа к реальному firewall.

## Что изменено

`integrations/traffic_limits.py` считывает `nft -j -n list table inet vkarmani_node_traffic` и строго сравнивает структуру с приватным `traffic-limits.json`:

- одна принадлежащая проекту таблица `inet`, только ожидаемые цепочки, счётчики, опциональные квоты и правила;
- `input` и `output` с правильными priority=10, policy=accept и типом filter;
- правильный default-route интерфейс для каждой стороны и направленные SSH/Node API исключения;
- порядок: исключение сервисных TCP-портов → подсчёт → превышение квоты/drop → превышение скорости/drop (если включены);
- точный размер quota, направление `over`, размер скорости в байтах в секунду, запрет неожиданных burst, `drop` и отсутствие посторонних правил;
- действительные значения счётчиков и значения квоты для отчёта/снимка.

При несовпадении: `SafeStop('FOREIGN_OR_MODIFIED_NFT_TABLE')` и код 2 из CLI; **без записи usage snapshot, удаления или переустановки таблицы**. `reset` по-прежнему требует явного `--confirm-new-period`. Если таблицы нет — `status` сообщает `NOT_ACTIVE`, а `apply` устанавливает правила только после проверки конфигурации и синтаксиса.

Старые лимиты, ключи, контуры Remnawave и интерфейс не мигрируются. **Изолированный ZIP не обновляет ранее установленную службу на VPS**: для существующей ноды обновление требует отдельной согласованной процедуры и backup.

## Как проверить на чистой тестовой VPS

1. Снимок у хостера, проверенная rescue/console, отдельная staging-VPS без пользователей; сохраните текущие конфиги (`nft -j -n list ruleset`), текущие `traffic-limits.json`, `traffic-used.json`, сервисы и таймеры на внешнем защищённом носителе. Не публикуйте приватные JSON в чат.
2. Установите из полного архивного дерева с проверкой `SHA256SUMS`, манифеста и версий. Включите **необязательные** лимиты отдельно от остальных настроек.
3. В тестовом окружении выполните **только чтение**:

   ```bash
   sudo nft -j -n list table inet vkarmani_node_traffic
   sudo python3 -I -B /usr/local/lib/vkarmani-node/traffic_limits.py status
   sudo systemctl status vkarmani-traffic-limits.service --no-pager
   sudo systemctl status vkarmani-traffic-snapshot.timer --no-pager
   ```

4. Проверьте IPv4 ingress/egress на выбранном default-route интерфейсе, отдельно SSH и Node API. Для замера квот используйте контролируемую нагрузку с малыми тестовыми значениями **без производственного трафика**, наблюдайте `nft` counters и snapshot. Убедитесь, что в лимиты не включается forwarded/Docker traffic, если он не проходит через `input/output` хоста.
5. В **одноразовой тестовой VPS**, после snapshot и только с аварийной консолью, можно испортить *собственную выделенную* nft-таблицу для проверки отказа. На рабочих серверах этого не делайте. Ожидаемый результат: `status`/`apply`/`reset` выдают STOP, не создают ложный `ACTIVE`, не пересоздают таблицу и не сбрасывают счётчики. Верните сервер из snapshot или из заранее проверенной копии.
6. Проверьте перезагрузку staging, snapshot/timer, восстановление после искусственного обрыва связи. Настоящий throughput/latency тест и поведение billing провайдера не подтверждаются unit-тестами.

**Риски:** Строгий проверяющий может остановиться на новом/неожиданном JSON-формате nftables (это безопасный STOP, а не повреждение таблицы). Нужен пробный прогон на фактической версии `nft`/Ubuntu. Контракт: нельзя утверждать `ACTIVE` для непроверенной конфигурации. Отдельно измеряются burst/policing, политика провайдера и перезагрузка.

## Незакрытые пункты прежнего аудита

- REALITY TLS ClientHello/post-handshake, DPI и ТСПУ — **не проверены в реальной сети**; удалённый DPI нельзя эмулировать одним unit-тестом.
- XHTTP → Remnawave Panel / Hosts / Internal Squad → подписка → реальный клиент — **требуется end-to-end испытание** с нужной панелью.
- DNS, IPv6, UDP/QUIC, реальный клиентский egress и fail-closed Entry/Exit — **нужна тестовая VPS и клиентские packet traces**.
- Настоящие SSH/UFW/Nginx/Docker/systemd установка, reboot и rollback — **нужна отдельная VPS и snapshot**.
- Автоматическая «полная деинсталляция» ОС не реализована намеренно: восстановление из проверенного snapshot безопаснее, чем удаление общесистемных служб. GitHub Actions невозможно подтвердить без публикации r44 в GitHub.

Все изменения r44 ограничены контролем nftables, тестами, релизными metadata и документацией. Результат офлайн-тестирования фиксируется отдельно, после сборки ZIP и чистой распаковки.
