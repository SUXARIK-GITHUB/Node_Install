## 2. Проверка ограничений трафика

`integrations/traffic_limits.py` **не превращён в `tc` shaping**: остаётся opt-in nftables policing с drop пакетов сверх скорости, правила живут в собственной таблице `inet vkarmani_node_traffic`. Не меняются UFW, iptables, внешние nft-таблицы, systemd units, существующие приватные файлы, параметр SSH и управление Docker.

Добавлены две fail-safe проверки:

1. `status` и `snapshot` перед выдачей успешного результата сверяют **текущий** основной IPv4-интерфейс и текущие исключения SSH/Node API с частным сохранённым конфигом. Когда сменился NIC либо порт, возвращается `TRAFFIC_LIMITS=STOP NETWORK_OR_SSH_PORTS_CHANGED_REFUSE`, а не ложный `ACTIVE`. Аналогичный контроль уже выполнялся при `apply/reset`; теперь вызов централизован.
2. Поскольку таблица `inet` обрабатывает IPv4 и IPv6 на выбранном интерфейсе, `network_identity` дополнительно считывает `ip -j -6 route show default`. Если для IPv6 основной выход — другой интерфейс, новая активация останавливается сообщением `UNSUPPORTED_DIFFERENT_IPV6_EGRESS_INTERFACE`: без этого направление могло не ограничиваться. При отсутствии IPv6 default route или совпадении интерфейса проверка проходит.

`validate_config()` теперь не допускает неупорядоченных или повторяющихся номеров защищённых портов. Изолированные тесты моделируют VLAN/NIC drift, IPv6 через отдельный NIC, дефекты JSON, изменения портов, отсутствие записи usage при отказе, квоты, скорости и порядок nft-правил без обращения к firewall хоста.

### Фактическая семантика счётчиков и важные ограничения

- Заданные `in_mbps` и `out_mbps` переводятся из **бит/с** в байт/с по формуле `Mbps × 125000`. Отдельные значения `*_gib` переводятся из GiB в байты (`GiB × 1024³`). Поле `0` выключает соответствующий предел.
- В пределах INPUT/OUTPUT своего NIC сначала принимаются исключения управляющих TCP-портов, затем выполняется named counter, затем quota и затем rate/drop. **Счётчики и quota учитывают и часть пакетов, которые будут отброшены последующим rate/drop**. Это учёт обработанных/попытанных байтов на точке фильтрации, **не гарантированный показатель оплаченного провайдером ingress/egress**.
- Квота не сбрасывается автоматически: `reset --confirm-new-period` — только осознанно с новым расчётным периодом. При жёстком power-off последние ~60 секунд с момента снимка могут не сохраниться. Защищённые SSH/Node API порты в эти счётчики не включены.
- Пользовательский `FORWARD`, Docker bridge, policy routing через другие NIC, внешние балансировщики и провайдерские накладные расходы не учитываются. `inet` правила на одном NIC не являются универсальным ограничителем всех возможных маршрутов. Не заявляется гарантированная скорость на живой линии: DROP может вызвать packet loss.
- Нет live-подтверждения синтаксиса `nft -c` на целевых Ubuntu/kernel, реальной скорости, квоты, восстановления после power loss, IPv6 multi-homing. Симулированные unit-tests этого **не заменяют**.

### Безопасная процедура проверки только на новой staging VPS

Перед проверкой: сделать snapshot сервера у провайдера, убедиться в доступности rescue-консоли, сохранить приватную конфигурацию и firewall ruleset **в защищённый backup** (не выкладывать в чат). Убедиться в актуальном password-only SSH, уникальном пароле и Fail2ban. Использовать отдельную тестовую ноду без клиентов.

Команды **только для чтения, не активируют правила**:

```bash
ip -j -4 route show default
ip -j -6 route show default
sudo nft -j -n list table inet vkarmani_node_traffic
sudo systemctl status vkarmani-traffic-limits.service --no-pager
sudo systemctl status vkarmani-traffic-snapshot.timer --no-pager
sudo bash ./install.sh --traffic-limits status
sudo ss -tlnp
```

Если таблицы nft нет, команда просмотра ожидаемо завершится ошибкой: это не повод менять firewall вслепую. Измерить реальный ingress/egress **на отдельной staging VPS**, отдельно сравнить системные значения с метриками провайдера, убедиться в сохранении SSH-сессии и доступности Panel Node API. Никогда не запускать `nft flush ruleset`, ручное удаление таблицы или «сброс» всех правил ради диагностики.

**Rollback на живой VPS:** сначала использовать проверенный snapshot провайдера и backup; не удалять или перезаписывать nft/UFW во время удалённой SSH-сессии. Откат к предыдущему ZIP — только откат исходников, не автоматический rollback состояния VPS. Для замены установленного `traffic_limits.py` необходим отдельный проверенный план обновления с резервной копией установленного helper и проверкой сопутствующих systemd units: штатный установщик **отказывается перезаписывать отличающийся helper**.
