# ⏱️ Исправление конфликта Chrony / systemd-timesyncd — 2.0.3

Дата: 2026-09-30. Область: ранняя стадия установки ноды. Не инструкция по изменению панели, базы данных, клиентского транспорта или полной миграции действующей VPS.

## 1. Что подтверждает присланный журнал

Установщик 2.0.2 был скачан с GitHub и прошёл проверку SHA256. UFW-preflight прошёл; все три значения приняты, публичный IPv4 выбран по DNS и интерфейсу, секрет сохранён с правами 0600. Bootstrap APT действительно установил/обновил базовые пакеты. Следующая компонентная транзакция только построила план и завершилась:

```text
The following packages will be REMOVED:
  systemd-timesyncd
E: Packages need to be removed but remove is disabled.
INSTALL_FAILED rc=100 line=2761
```

Первопричина в коде 2.0.2: общий массив APT содержал `--no-remove`, а список компонентов безусловно требовал `chrony`. На этой ОС его установка конфликтовала с уже установленным `systemd-timesyncd`. Защита от удаления отработала правильно; неверным был выбор обязательного пакета установщиком.

Это **не ошибка SECRET_KEY, домена, RAW/REALITY, Nginx или Docker**. В показанном запуске компонентная транзакция не была применена; однако базовые пакеты, закрытые файлы параметров и служебные markers уже созданы. Нельзя описывать состояние как «ничего не изменено» или как завершённую установку. Reboot в журнале не запланирован.

Ошибка не выявлялась прежними 226 тестами: они не запускали разрешение зависимостей компонентной транзакции с уже установленным виртуальным `time-daemon`. Теперь это отдельная регрессия, а не просто тест наличия слова `chrony` в шаблоне.

## 2. Как работает выбор времени в 2.0.3

| Состояние dpkg | Решение |
|---|---|
| Установлен systemd-timesyncd | Сохранить его; не запрашивать Chrony и не удалять timesyncd |
| Установлен Chrony | Использовать его; прежняя конфигурационная ветка Chrony |
| Нет обоих и нет чужого time-daemon | Установить Chrony без удаления других пакетов |
| Есть неизвестный провайдер time-daemon, два клиента или неполный пакет | Остановиться с диагностикой, без попытки замены/удаления |

Выбор основан на структурированном выводе `dpkg-query` (`binary:Package`, `Status`, `Provides`), а не на языке APT-лога или предположении «любая Ubuntu использует timesyncd». Учитываются held-пакеты, arch suffix и config-file remnants. Наличие пакета не выдаётся за работающую синхронизацию.

Перед компонентной транзакцией выполняется `apt-get --simulate ... --no-remove`. На фактическом `apt-get install` **тоже остаётся `--no-remove`**. Симуляция не резервирует состояние dpkg до следующего вызова; если план изменится и потребуется удаление, реальная операция всё равно должна отказать. Разрешений `--allow-*`, автоматического `apt remove`, `autoremove` и очистки чужого firewall не добавлено.

### Timesyncd

Источники времени ОС/хостера сохраняются: `timesyncd.conf`, per-link/DHCP и netplan не переписываются. Отдельный файл `/etc/systemd/system/systemd-timesyncd.service.d/90-vkarmani-ipv4.conf` ограничивает службу `AF_UNIX AF_INET`. После daemon-reload и запуска проверяется фактическое значение `RestrictAddressFamilies`; неподтверждённый результат считается ошибкой. Masked unit не разблокируется автоматически.

Готовность означает одновременно: служба активна, `NTPSynchronized=yes`, `ServerAddress` — IPv4, существует штатный regular runtime-marker `/run/systemd/timesync/synchronized`. Сам файл без состояния службы и ядра не считается достаточным. Проверка не измеряет точность синхронизации на этой VPS; timesyncd реализует SNTP и не объявляется функционально равным Chrony.

### Chrony

Сохранены прежние источники/ограничения конфигурационной ветки установщика и `chronyd -4`. Проверяются `chronyc -n waitsync 1 0.1 0.0 1` и `Leap status: Normal`. Ожидание обоих клиентов использует общий монотонный deadline 120 секунд; отдельная дочерняя команда ограничена остатком времени и максимумом 5 секунд. Таймаут не превращается в PASS.

После успеха выбранная служба записывается атомарно в закрытый `/etc/vkarmani-node/time-provider` (0600, fsync файла и каталога). Acceptance и postboot используют именно эту службу. Если сохранённая и установленная службы разошлись, выдаётся `TIME_PROVIDER_DRIFT`.

## 3. Продолжение ровно этого незавершённого запуска 2.0.2

Ранее общий guard запрещал любой переход между версиями незавершённой установки. Удалять его или вручную подменять `/var/lib/vkarmani-node/install-version` небезопасно: под одинаковым marker могут оказаться частично разные файлы.

Теперь под общим installer lock разрешено только узнаваемое раннее состояние. Read-only gate проверяет:

- private regular файлы и каталоги состояния, `owned-installation`, версию 2.0.2, точный `rc=100 line=2761` и формат времени ошибки;
- SHA256 старого встроенного `node_helper.py`: `d12e637c5a91106b2e7df53f65c84c62dcaca64c5d8d3f29f41639b994082c58`;
- сохранённые конфигурацию/секрет и указатель исходной закрытой копии с непустым manifest; содержимое секретного ключа позже повторно проверяет штатный validator, без печати;
- отсутствие завершения, сетевого rollback, image state, compose, управляемых конфигов сети, Nginx, journald, Docker repository и других признаков поздних этапов.

Проверка manifest в gate подтверждает наличие/безопасность указателя, **не доказательство полного восстановления из исходного backup**. Перед заменой версии создаётся ещё одна закрытая копия параметров, ключа, helpers, старых version/failure markers, time configs и остальных штатных путей. Её файловый SHA256 manifest проверяется; только затем marker атомарно переходит на 2.0.3. Первый backup pointer не заменяется.

Сбой до завершения копирования сохраняется в `RESUME_FAILED`, не уничтожая узнаваемый старый `INSTALL_FAILED`. После подтверждённой копии и смены marker дальнейшие ошибки относятся к 2.0.3; продолжать нужно этой версией, а не вручную возвращать 2.0.2. Это не атомарная транзакция всей ОС и не защита от произвольного вмешательства другого root-процесса.

Сохранённые три значения повторно не спрашиваются. Ключи не заменяются, серверный IPv4 не спрашивается четвёртым пунктом. Первичная чистая установка по-прежнему требует ровно три значения. Законченная установка 2.0.0/2.0.1/2.0.2 новым файлом не мигрируется; она запускает свои установленные проверки, как раньше.

## 4. Запуск исправленного файла

Перед продолжением: snapshot текущего частичного состояния, проверенная консоль хостера и сохранённая исходная SSH-сессия. Snapshot — внешнее действие владельца VPS; установщик не подтверждает его создание за вас. Не откатывайте bootstrap-пакеты наугад и не удаляйте UFW/state.

Загрузите отдельно поставленный `install_2.0.3.sh` через SFTP в `/root/install_2.0.3.sh`. Проверка и запуск на конкретной ноде инцидента:

```bash
sudo bash <<'INSTALL'
set -Eeuo pipefail
set +x
umask 077
EXPECTED_HOST='astra-404539554-preset1.astravps.co'
[[ $(hostname) == "$EXPECTED_HOST" ]] || {
    echo "STOP: этот блок предназначен для $EXPECTED_HOST." >&2
    exit 1
}
src='/root/install_2.0.3.sh'
[[ -f "$src" && ! -L "$src" ]] || {
    echo "STOP: загрузите исправленный файл в $src." >&2
    exit 1
}
work=$(mktemp -d /root/vkarmani-install.XXXXXXXX)
install -m 0700 -- "$src" "$work/install.sh"
cd -- "$work"
if ! printf '%s  install.sh\n' \
    '22b9e50d736e6332d3ad3973d6e23b56ba7f4338a161ab2f118e226ef392c216' \
    | sha256sum --check; then
    echo 'STOP: SHA256 не совпал. Установщик не запущен.' >&2
    exit 1
fi
bash -n install.sh
[[ $(bash install.sh --version) == 2.0.3 ]] || {
    echo 'STOP: неверная версия установщика.' >&2
    exit 1
}
exec bash install.sh
INSTALL
```

Ожидаемые промежуточные признаки **при соответствии состояния gate**:

```text
RESUME_2.0.2_PACKAGE_STAGE=ELIGIBLE; configuration and secret will be reused
RESUME_FROM=2.0.2 BACKUP=/var/lib/vkarmani-node/backups/...
TIME_PROVIDER=systemd-timesyncd; системные NTP-пакеты не заменяются.
```

Они означают прохождение конкретных этапов, не завершение всей установки. Любой новый STOP нужно разбирать по полному выводу без секретов; обход guards и удаление markers запрещены. Код не управляет внешним firewall, NTP/DNS провайдера, панелью или snapshot.

GitHub из среды подготовки не обновлялся. Старый bootstrap с hash 2.0.2 не установит исправленный файл. Для запуска с GitHub сначала опубликуйте согласованные `install.sh`, README и SHA256SUMS 2.0.3. При обновлении локального clone сохраните его действующую `.git`; новая рабочая поставка намеренно не включает старую Git-базу. Она сохранена отдельно в metadata backup.

## 5. Проверки и остаточный риск

Всего 304 теста: 226 сохранённых и 78 новых. Пять используют настоящий APT 3.0.3 на отдельном локальном `file://`-индексе с синтетическими package records; там воспроизведены исходный отказ 100, планы с timesyncd/Chrony/отсутствующим daemon и сохранение запрета на посторонние удаления. Системные APT state/sources не менялись, пакеты не устанавливались, модель не содержит полного дерева зависимостей Ubuntu Noble.

NTP-команды/systemd-состояние проверены на подставленных ответах и ошибках, не на запущенной службе. Resume gate проверен на закрытых временных fixtures, включая реальный payload старого helper, отказ на изменениях и неизменность входных файлов. Порядок этапов main проверен по коду; полный main/resume на VPS не запускался. Подробности: [TEST_REPORT](TEST_REPORT.md).

После успешного полного завершения сначала проверьте вторую парольную SSH-сессию, не закрывая старую. Затем плановая перезагрузка и `sudo vkarmani-node-check`; после профиля/Host в панели — `sudo vkarmani-node-check --require-xray` и настоящий RAW REALITY-клиент. Эти проверки не выполнены автоматически из среды подготовки.

Образный `rollback-image` не исправляет пакетный/NTP этап и не восстанавливает всю VPS. Автоматического удаления установленной службы нет; возвращение всей частично изменённой ОС выполняется из проверенного snapshot либо по отдельному плану фактического состояния. Прежние конфиги и markers должны оставаться в backup, а не перезаписываться старым архивом.
