# Node Install 2.5.18 r39 — NTP-проверка при перезапуске службы

**Статус:** `INCOMPLETE_STAGING_ONLY`. Исправление будущих установок; не выполнять команды восстановления на рабочей VPS без backup и доступа к аварийной консоли.

## Наблюдаемый сбой на Ubuntu 24.04

При реальном первом запуске r38 `NTP_SYNC=PASS` зарегистрирован на раннем шаге. Позднее обновления ОС и сетевые изменения сопровождались несколькими перезапусками `systemd-timesyncd`. Около 17:09 журнал записал успешную первоначальную синхронизацию текущего процесса. Около 17:18 финализация завершилась `NTP_SYNC_TIMEOUT: TIMESYNCD_NO_ACCEPTED_NTP_REPLY` и сохранила checkpoint; затем администратор подтвердил `NTPSynchronized=yes`, нормальный `Leap`, положительное число пакетов и работу службы.

Журнал **не сохранил** значение `NTPMessage.Ignored` на момент отказа, поэтому точную причину одного отдельного пакета установить невозможно. В исходном коде обнаружен класс ложных отказов: все сообщения с `Ignored=yes` безусловно отбрасывались, хотя `Ignored` описывает *последний* NTP-пакет, а не обязательно отсутствие ранее принятой синхронизации.

## Изменение только в встроенном time_helper.py

Для NTP-ответа с `Ignored=no` требования не меняются. При `Ignored=yes` (временный spike) допускается завершить проверку **только при одновременном выполнении** всех условий:

1. `systemd-timesyncd.service` запущена (`active/running`), идентификатор инвокации корректен и не меняется во время проверки.
2. `NTPSynchronized=yes`, NTP-сервер — IPv4, NTPMessage корректно распарсено: положительный счётчик пакетов, допустимые режим/stratum/leap.
3. Существующий `/run/systemd/timesync/synchronized` — обычный файл владельца `root` либо системного пользователя `systemd-timesync`, не допускающий записи другим пользователям.
4. `ExecMainStartTimestampMonotonic` текущего процесса известен, а маркер последней успешной синхронизации по времени относится **к этому процессу**, не к предыдущему. Время сравнивается консервативно: не допускаются маркеры в будущем, старше 2 часов или возникшие до/в момент запуска службы.
5. По-прежнему обязательны две последовательные устойчивые выборки с тем же IPv4 источника и идентификатором инвокации. Общий лимит ожидания не продлевается.

Если доказательств недостаточно, установка **останавливается**, сохраняя checkpoint. Код не меняет часы, NTP-источники, сетевые правила или сервисы.

## Текущие незавершённые установки r38

**Не заменяйте** `/usr/local/lib/vkarmani-node/time_helper.py` и `vkarmani-node-check` на r39 вручную: их SHA-256 входят в `finalization/checkpoint.json`. Замена ломает защиту финализатора и сама по себе не является официально поддерживаемой миграцией.

Для прочтения состояния без изменения конфигурации:

```bash
sudo timedatectl status
sudo timedatectl timesync-status
sudo python3 /usr/local/lib/vkarmani-node/time_helper.py wait --seconds 35 --stable-samples 2
```

Если последняя проверка напечатала `NTP_SYNC=PASS` и есть рабочий snapshot/аварийная консоль хостера, **только для штатно подготовленного checkpoint той же r38** допустим штатный `--finish-install` из **того же сохранённого исходного каталога r38**. Команда продолжает финализацию (включая RKN/UFW), поэтому не является read-only. При повторяющемся NTP-отказе не следует создавать INSTALL_COMPLETE или редактировать checkpoint вручную: нужно разбирать реальный вывод текущего time-helper и сохранённые значения NTPMessage.

Новая r39 **не обещает автоматически исправить уже сохранённый r38-checkpoint**. Этот релиз устраняет воспроизводимую ошибку логики **в новых установках**.

## Проверка

Автономные тесты: нормальный NTP-пакет, последний проигнорированный spike после подтверждённого sync в **той же** инвокации, устаревший/будущий маркер, чужой владелец, легитимный системный владелец, небезопасные права, неверный пакет/источник, смена идентификатора службы и общий дедлайн. Отдельная проверка на реальной Ubuntu 24.04 и полный install/reboot ещё необходимы.
