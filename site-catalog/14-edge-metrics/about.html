About Edge Metrics: An illustrated technical notebook about requests, latency and operational telemetry

Edge Metrics

An illustrated technical notebook about requests, latency and operational telemetry

Compare percentiles and outliers instead of hiding the slowest requests in an average.

No sign-in, external scripts or third-party analytics.

Four paths for further study

Choose the subject most relevant to your question. Each item leads to an article and a practical exercise.

  1. Tracing a request

    Sketch the stages of a page request from browser to storage and give every stage a shared trace identifier. Annotate where timing can be lost or counted twice.

  2. Latency distributions

    Lay out ten illustrative response times with one slow outlier, then compare median and upper percentiles without claiming the small sample represents production.

  3. Quiet dashboards

    Design a dashboard with one panel for demand, one for errors and one for latency. Beside each, write the operational decision that panel is meant to support.

  4. Useful alerts

    Draft an alert description with a symptom, a duration and a safe first investigation step. Distinguish an isolated spike from a persistent user-visible failure.

Method and limits

The following is an independent reading exercise, not a report of fieldwork.

Take a deliberately illustrative set of response times in milliseconds: 80, 82, 85, 91, 95, 98, 102, 105, 109 and 900. The median is 96.5 ms, while the slowest request takes 900 ms. Their arithmetic mean is 174.7 ms. Each statistic answers a different question, and ten observations are not enough to predict a production percentile.

An alert description should state the symptom, minimum duration, affected population and a first check. For example, a sustained rise in failed requests may justify investigation; one isolated slow browser request rarely does. Every threshold is local to the system being observed.

Averages conceal a surprisingly large range of request experiences. A dashboard should separate errors, ordinary latency and long-tail delays, then explain what each panel can and cannot prove. A new alert is useful only if its threshold has an owner and a clear response; a colored graph without a decision attached often produces noise.
