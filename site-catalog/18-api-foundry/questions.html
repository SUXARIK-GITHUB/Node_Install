Questions

Answers on request validation, useful errors and related reading from Interface Foundry.

Request validation: When should malformed input be rejected?

Reject malformed input at the boundary with a clear explanation.

Useful errors: What belongs in a useful error message?

A clear error response pairs a stable code with a human-readable explanation. Do not expose stack traces, connection strings or internal file locations to clients.

Versioned endpoints: How can a versioned endpoint remain compatible?

Draw a compatibility matrix for an old client and a new field. Show what happens when the field is absent, ignored or rejected before calling an interface stable.

What should I check in this material: First observation?

Imagine POST /notes receiving a JSON object with a required title and optional labels. Decide explicitly whether an empty title is rejected, whether an unknown property is ignored, and which fields are returned after creation. Document success and validation failure with separate examples; do not make clients infer the contract from a stack trace. What should I check in this material: Second observation?

For repeatable submissions, accept an idempotency key and compare it with the original request body. A repeat with the same key and body should not create a second object. A different body with the same key needs a documented conflict response. The key is not a substitute for authentication or transaction safety. What are the limits of this exercise?

Idempotency is about the effect of an operation, not simply receiving the same status code twice. Describe what happens when a client retries after losing the response, and who owns the record of the original request. Clear error categories help callers distinguish invalid input from temporary unavailability without guessing from a message string.
