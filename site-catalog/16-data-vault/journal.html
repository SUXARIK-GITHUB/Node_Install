A readable backup

A backup is useful only when its format and contents remain readable.

An archive should include names, sizes and a documented format that can be read without the original application. Keep the encryption recovery method separately from the backup media.

Open an old sample archive without changing its contents and write down the file list, format and tool required to read it. Note anything a future maintainer would need to know.

02 / Technology

Restoration day

Try restoring selected files into a clean directory before you need them.

Choose a small but representative set of files and restore them into an empty directory. A successful job log cannot tell you whether permissions or links survived extraction.

Restore a few harmless sample documents into a new directory and compare their names, sizes and readability with the source. Never rehearse over a live working folder.

03 / Technology

Checksums in practice

Compare recorded checksums with restored files rather than trusting a success message.

Checksums detect changed bytes, but do not prove that a database dump is logically restorable. Compare hashes and also open a restored sample with its intended tool.

Hash a deliberately created example file, copy it and compare the recorded digest. Then change one character to illustrate why the checksum is only an integrity signal.

Versioned archives

Keep several dated restore points so one mistake does not erase the past.

A rotation needs several independent restore points because silent corruption can propagate. Document when older copies expire and how you know a full backup actually completed.

Prepare a rotation table with several dated archives, retention reasons and a separate restore destination. Explain which versions would survive one accidental deletion.

What to look for: A restoration test, not merely a backup log

An archive that can be listed is not necessarily one that can be restored. A meaningful recovery rehearsal verifies filenames, permissions, encoding and the application that will read the result. Keep a separate note of any encryption key or software dependency: a flawless checksum is of little use when the only recovery key was lost with the original machine.

Field guide

A restoration test, not merely a backup log

An archive is not a useful backup just because its creation program returned success. A repeatable recovery path needs an independent copy, an empty destination and a way to verify that the restored data can actually be used.

Method

  1. Prepare a small test set: a normal document, a directory of nested files and a name with non-ASCII characters. Record archive format, approximate size, checksum and the process for locating any encryption key.
  2. Restore to a separate empty directory, not onto the originals. Compare file contents, names and permissions. For a database dump, additionally load a disposable database and query a small representative sample.
  3. Assume the original computer no longer exists. List the software, keys, access rights and instructions required to recover the files. A plan that depends on one unavailable device is incomplete.

Limits and safety

Do not use production secrets or a live database for this exercise. A matching checksum does not prove that a system or its permissions can be restored.
