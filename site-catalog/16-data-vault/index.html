Inside the edition

  1. A readable backup

    An archive should include names, sizes and a documented format that can be read without the original application. Keep the encryption recovery method separately from the backup media.

  2. Restoration day

    Choose a small but representative set of files and restore them into an empty directory. A successful job log cannot tell you whether permissions or links survived extraction.

  3. Checksums in practice

    Checksums detect changed bytes, but do not prove that a database dump is logically restorable. Compare hashes and also open a restored sample with its intended tool.

  4. Versioned archives

    A rotation needs several independent restore points because silent corruption can propagate. Document when older copies expire and how you know a full backup actually completed.

Start here: A restoration test, not merely a backup log

An archive is not a useful backup just because its creation program returned success. A repeatable recovery path needs an independent copy, an empty destination and a way to verify that the restored data can actually be used.

  1. Prepare a small test set: a normal document, a directory of nested files and a name with non-ASCII characters. Record archive format, approximate size, checksum and the process for locating any encryption key.

  2. Restore to a separate empty directory, not onto the originals. Compare file contents, names and permissions. For a database dump, additionally load a disposable database and query a small representative sample.

What to notice: Archive checksum: Detects changed bytes during storage and transfer.; Extraction test: Checks that the format is readable and directories survive.; Application test: Verifies that restored information is useful, not just present.
