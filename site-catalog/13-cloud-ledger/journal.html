Example and analysis

Release handoff: a small example

Consider an application made of a web process, an API and a data store. Draw three boxes and arrows for the calls, then describe one customer task: saving a draft. If the store is unavailable, the web page can still load, but saving must fail visibly rather than displaying a false confirmation. The diagram becomes useful only when it names the affected user action.

A release record can include the artifact digest, configuration version, database compatibility requirement and an exact rollback condition. Record who verifies the result, but do not publish real credentials or secrets. A green startup log alone is not sufficient: verify a read, a write and recovery from a deliberately failed request in a separate test environment.

For recovery exercises, restore a backup into a fresh destination, check its schema and selected records, then test that the application can read it. Keep recovery time and permissible data loss as different questions. No sample values on this page represent measurements from a real service.

Reliability budget

Count the services that can fail before declaring a reliability target.

An availability target needs a named service boundary: decide whether a failure means a slow page, a rejected request or an unavailable dependency. A budget is only meaningful against that definition.

Draw a dependency map for a fictional three-service application, then mark which customer-facing action fails if each service is unavailable. Keep the assumptions next to the diagram.

02 / Technology

Immutable releases

Make a release artifact immutable and keep its rollback steps alongside it.

A release becomes reproducible when the artifact, configuration and migrations are versioned together. Store the previous build and test the reversal before exposing the new one.

Write a release checklist using a fixed artifact identifier, one change record and a rollback condition. Explain how a second operator would recognize the previous version.

03 / Technology

Regions and latency

Compare routes and response times from several regions rather than guessing.

A second region is not automatically faster; routing, cold starts and distance to databases can dominate. Compare a small set of identical requests from each location and record the distribution.

Compare the same hypothetical request from a nearby and a distant region, separating transmission time, server processing and measurement uncertainty. Label rather than invent results.

04 / Technology

Recovery drills

Rehearse recovery from a missing host with a copy of the configuration.

A restoration drill should begin with a missing machine, not an assumed healthy cluster. Record which secrets, persistent volumes and DNS changes are necessary before users can return.

Build a recovery rehearsal sheet listing configuration, backup location, credentials handoff and a clean target machine. A restore is only complete when it can be checked independently.

What to look for: Release handoff: a small example

A recovery plan is easier to trust when it states what data is recoverable, which dependencies must already exist, and which failure it cannot handle. A deployment can be immutable while its configuration remains fragile. Compare the documented recovery sequence against a disposable environment; a green release indicator alone is not evidence of restoration.
