Questions

Answers on reliability budget, immutable releases and related reading from Northbound Cloud.

Reliability budget: What should count toward a reliability target?

Count the services that can fail before declaring a reliability target.

Immutable releases: How can a release remain recoverable?

A release becomes reproducible when the artifact, configuration and migrations are versioned together. Store the previous build and test the reversal before exposing the new one.

Regions and latency: Which measurements make regional latency comparable?

Compare the same hypothetical request from a nearby and a distant region, separating transmission time, server processing and measurement uncertainty. Label rather than invent results.

What should I check in this material: First observation?

Consider an application made of a web process, an API and a data store. Draw three boxes and arrows for the calls, then describe one customer task: saving a draft. If the store is unavailable, the web page can still load, but saving must fail visibly rather than displaying a false confirmation. What should I check in this material: Second observation?

A release record can include the artifact digest, configuration version, database compatibility requirement and an exact rollback condition. Record who verifies the result, but do not publish real credentials or secrets. A green startup log alone is not sufficient: verify a read, a write and recovery from a deliberately failed request in a separate test environment. What are the limits of this exercise?

A recovery plan is easier to trust when it states what data is recoverable, which dependencies must already exist, and which failure it cannot handle. A deployment can be immutable while its configuration remains fragile. Compare the documented recovery sequence against a disposable environment; a green release indicator alone is not evidence of restoration.
