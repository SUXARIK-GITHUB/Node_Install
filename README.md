# 🛠️ Remnawave Node · 1.3.5

**VLESS + RAW + REALITY · Nginx Selfsteal · IPv4-only**

Самодостаточный `install.sh`: для запуска не нужны файлы из `tools/` и `tests/`. Исправление подготовлено на основе архива 1.3.4. Скрипт настраивает ноду, но не создаёт и не изменяет объекты панели.

> **Для уже установленной ноды используйте `--repair-connection`, а не полную установку.** Локальный `PASS` не доказывает подключение панели. Полное развёртывание на реальной VPS и действующее соединение пользователя в среде разработки не проверены.

## 🔧 Исправить подключение существующей ноды

Скопируйте **новый `install.sh` из этого архива** на ноду, например в `/root/install.sh`. Сначала сделайте снимок VPS. На **ноде**, от root:

```bash
cd /root
bash install.sh --repair-connection --refresh-image
```

Этот режим предназначен только для завершённой установки **VKarmani 1.3.x**. Он сохраняет `SECRET_KEY`, REALITY-ключи, домен, профиль и список IPv4 панели. Не выполняет APT, reboot, изменения Nginx, SSH, sysctl, маршрутов или MTU. **RemnaNode пересоздаётся: действующие VPN-соединения прервутся.**

С `--refresh-image` сначала загружается официальный `remnawave/node:latest`, затем закрепляется его digest. Без этого флага сохраняется установленный образ:

```bash
bash install.sh --repair-connection
```

Перед изменениями создаётся root-only резервная копия в `/var/lib/vkarmani-node/backups/connection-1.3.5-*`. При ошибке после начала изменений выполняется попытка возврата управляемых файлов и запуска прежнего контейнера. Это не гарантирует здоровье прежней установки и не заменяет снимок VPS. Добавленные узкие разрешения UFW для сохранённых IP панели при откате остаются. Старый образ удерживается тегом `remnawave/node:vkarmani-connection-rollback`.

Исправление нормализует host networking и `restart: always`, устраняет затенение сохранённых `SECRET_KEY`/`NODE_PORT` через `environment`, пересоздаёт контейнер, проверяет его реальные переменные, обновляет служебный SNI в TLS-проверке. Docker остаётся владельцем автозапуска; лишний активный oneshot systemd больше не оставляется. Порт управления разрешается **только с сохранённых IPv4 панели**, а не для всего интернета. Внешний firewall хостера не меняется.

## 🩺 Две разные проверки

### На ноде: локальная готовность

```bash
bash /root/install.sh --diagnose-node
```

Проверка использует временные диагностические файлы, удаляемые после завершения. Конфигурация и состояние сервисов не меняются. Проверяются сертификат, CA, точное совпадение серверного сертификата с сохранённым ключом, служебный SNI, обычный и фрагментированный ClientHello, запущенный контейнер и его порт/ключ.

```text
NODE_MANAGEMENT_LOCAL=PASS
PANEL_CONNECTION=NOT_VERIFIED
```

Это означает только локальную готовность, **не** успешное подключение панели.

### На сервере панели: действительный mTLS + JWT запрос

Скопируйте **тот же `install.sh`** на сервер панели. Не запускайте там полную установку. Выполните:

```bash
bash /root/install.sh --diagnose-panel NODE_ADDRESS 2222
```

`NODE_ADDRESS` — IP или доменное имя из карточки ноды, без `https://`, пути и порта. При нескольких backend-контейнерах укажите нужный явно:

```bash
bash /root/install.sh --diagnose-panel NODE_ADDRESS 2222 remnawave
```

Автоматически выбирается только один работающий официальный контейнер `remnawave/backend` или `ghcr.io/remnawave/backend`. Внутри него выполняются чтение таблиц `keygen`/`nodes` в **read-only транзакции** и запрос `GET /node/xray/healthcheck`. Панельный клиентский сертификат и ключ, JWT-ключ берутся из её собственной БД только в память процесса. Приватный ключ CA не читается. Сертификаты, токен, строки подключения и приватные ключи не печатаются, не выгружаются в файлы и не передаются в аргументах процессов.

Проверяются TLS 1.3, CA и авторизация. Имя серверного сертификата не сравнивается с публичным доменом: у RemnaNode служебная идентичность, а не сертификат сайта; проверка подписи/цепочки/срока действия остаётся включённой. Дополнительный SNI вычисляется из ключевого материала.

Успех выглядит так:

```text
PANEL_NODE_API=PASS stage=HTTP code=AUTHENTICATED_HEALTHCHECK HTTP=200
PANEL_MTLS=PASS PANEL_JWT=PASS
AUTHENTICATED_DIRECT_API=PASS
```

Это подтверждает авторизованный **прямой** доступ из выбранного backend-контейнера. Не подтверждает состояние всех worker-контейнеров, применённый Xray-профиль, трафик клиентов или маршрут через настроенный node proxy. При наличии proxy диагностика явно предупреждает, что тестирует прямой путь.

При TLS-ошибке выполняется дополнительный диагностический запрос с группой X25519. Его успех при неуспехе основного запроса показывает различие поведения TLS/пути, **но не доказывает MTU-проблему** и ничего не меняет в работающих сервисах.

Коды завершения: `0` — соответствующая проверка прошла; `1` — проверенный отказ; `2` — проверка не выполнена полностью (например, неоднозначный контейнер, несовместимая схема БД или нет Prisma). Для repair код `0` означает применение ремонта и локальную проверку, не внешнее подключение.

Расшифровка результатов — [CONNECTION-REPAIR.md](CONNECTION-REPAIR.md).

## 🚀 Первая установка на чистую VPS

Полный установщик сохраняет ограничения исходной версии: Ubuntu **22.04/24.04** или Debian **12/13**, systemd, GRUB, amd64/arm64, от 900 MiB RAM и 6 GiB свободного места. Новые версии ОС этим релизом не объявляются проверенными. Режим ремонта существующей собственной установки не требует переустановки ОС.

Домен: одна A-запись на локальный публичный IPv4 VPS, без AAAA и CDN proxy. Исходящий IPv4 панели должен быть разрешён на Node Port в локальном и внешнем firewall. Нужны снимок VPS и консоль хостера.

```bash
sudo bash install.sh
```

Три значения: `SECRET_KEY → исходящий IPv4 панели → домен ноды`. IPv4 самой ноды выбирается по DNS среди адресов её интерфейсов.

Полная установка обновляет пакеты ОС, устанавливает Docker/Nginx/Certbot, настраивает UFW, Fail2ban для SSH, Chrony, BBR/fq, отключение IPv6 и периодическую перезагрузку в понедельник в 04:00 МСК. **После полной установки предусмотрена разовая автоматическая перезагрузка**; `--no-reboot` отменяет только её. Для ремонта канала управления полную установку не повторять.

Команду загрузки с GitHub используйте только после публикации именно этой версии и проверки `--help`; скачивание `main` до обновления репозитория не доставит 1.3.5.

## 🔗 Два отдельных канала

```text
Панель → IPv4 ноды:2222 → API RemnaNode (mTLS + JWT)
Клиент → домен ноды:443 → Xray RAW/REALITY → /dev/shm/nginx.sock → Nginx
```

Nginx не занимает публичный `443` и не обслуживает API `2222`. REALITY использует `target: /dev/shm/nginx.sock`, `xver: 1`. XHTTP не добавлен, Vision принудительно не включён.

В панели отдельно нужны карточка Node с правильным адресом и Node Port, включённое состояние, назначенный Config Profile и активные inbound. Для выдачи подключения пользователю также настраиваются Host и группы доступа. Локальный шаблон и памятка:

```text
/etc/vkarmani-node/profile.json
/etc/vkarmani-node/PANEL-SETUP.txt
```

`profile.json` содержит приватный REALITY-ключ. Не публикуйте его. Отсутствие слушателя Xray на `443` нельзя автоматически считать причиной недоступности API на `2222`.

## Прежние режимы сохранены

```bash
bash install.sh --repair-network  # Только исправление network-helper для sysctl/IPv6.
bash install.sh --repair-node     # Прежний комплексный ремонт наших служб; не первый выбор для API.
vkarmani-node-check               # Общая локальная проверка после установки.
vkarmani-node-tls-check --all-local
```
