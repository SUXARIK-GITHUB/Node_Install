# Подключение панели к ноде: 1.3.5

## Последовательность для существующей установки

1. Снимок VPS. Скопировать новый `install.sh` на ноду и сервер панели.
2. На ноде: `bash /root/install.sh --repair-connection --refresh-image`.
3. На ноде: `bash /root/install.sh --diagnose-node`.
4. На панели: `bash /root/install.sh --diagnose-panel NODE_ADDRESS 2222`.
5. Проверить в интерфейсе панели её собственный статус ноды и применение нужного профиля. Не путать успешный API-запрос с проверкой всего VPN.

При другой папке замените `/root/install.sh` фактическим путём. Режим ремонта требует маркеры завершённой собственной установки 1.3.x. Если установка не завершилась или файлы явно противоречат друг другу, он останавливается, а не переписывает неизвестное состояние.

## Расшифровка

| Результат | Что это означает и что проверять |
|---|---|
| `NODE_MANAGEMENT_LOCAL=FAIL` | Сначала локальный контейнер, фактические переменные, сертификат, локальный TLS. Панель пока не проверена. |
| `RUNTIME_SECRET_KEY_MATCH=FAIL` | Контейнер использует не сохранённый ключ. Repair убирает затенение переменной и пересоздаёт контейнер. Не публиковать значения ключей. |
| `RUNTIME_NODE_PORT_MATCH=FAIL` | Порт работающего контейнера отличается от сохранённого. Нужно также совпадение Node Port в панели. |
| `NODE_VERSION=UNKNOWN` | Версия не извлечена из доступной части стартового журнала; это не утверждение о старом образе. Digest выводится отдельно. |
| `stage=TCP code=ECONNREFUSED` | Адрес/порт недоступен на уровне TCP: нет слушателя, отказ firewall или неверная цель. |
| `stage=TCP code=DEADLINE_EXCEEDED` | TCP не установился: проверить адрес, маршрут, внешний firewall и фактический исходящий IPv4 backend. Это не однозначное доказательство конкретного firewall. |
| `stage=TLS ...` | TCP установился, но TLS не завершён. Проверить SNI, CA, срок сертификатов, образ, путь и сетевые ограничения. |
| `stage=TLS_SERVER_VERIFIED ...` | Клиент проверил сервер, но полноценный авторизованный HTTP-ответ ещё не получен. Сам по себе этот этап не доказывает mTLS. |
| `HTTP=401/403` | Получен HTTP-ответ через TLS; авторизация не принята. Проверить JWT-материал, часы, версии. |
| Разные `CA_SHA256` на ноде и панели | Сохранённый ключ ноды и выбранная панель содержат разные CA. Это не лечится открытием порта. Нужна сверка экземпляра панели и ключа; скрипт не подменяет ключ автоматически. |
| `PANEL_NODE_API=PASS` | Прямой запрос из выбранного backend прошёл mTLS и JWT к healthcheck API. |
| API проходит, панель всё ещё offline | Смотреть worker/очередь, адрес и порт карточки, её enabled/disabled, профиль и inbound, совместимость runtime панели. Прямой тест не проверяет путь через node proxy. |
| `NODE_CARD=NO_EXACT_ADDRESS_MATCH` | В БД нет карточки с ровно таким адресом; возможна карточка с DNS-именем вместо IP. Запустить с адресом из неё. |
| `PANEL_CHECK=INCOMPLETE` | Нет результата теста; не трактовать как недоступность ноды. Проверить выбранный контейнер и поддерживаемую схему БД. |

Совпадение CA само по себе ещё не доказывает совпадение JWT-ключа и успешную авторизацию; для этого нужен действительный запрос. `SECRET_KEY` нельзя просто сравнивать с заново скопированным ключом посимвольно: панель может выпускать другой сертификат ноды при сохранении того же CA/JWT.

## Что не делать наугад

Не отключать UFW, mTLS, проверку CA и не открывать `2222` всему интернету. Не менять MTU/MSS, ядро и sysctl только потому, что TCP открыт, а TLS не отвечает. Не подставлять домен сайта-заглушки как обязательный API SNI. Не повторять полную установку ради диагностики уже установленного сервера. Не передавать секреты в аргументах команд и не присылать полный `docker inspect` или `docker compose config`.

## Резервная копия

Каталог `/var/lib/vkarmani-node/backups/connection-1.3.5-*` содержит `files.txt` с соответствием индексов `0.before`, `1.before` и т. д. исходным путям. В нём также сохраняются `config.json.before`, `remnanode.env.before`, закрытые технические журналы и результат локального TLS-теста. Каталог содержит секреты и имеет права 0700. Его нельзя публиковать или целиком отправлять в чат.

При неудаче автоматического отката используйте снимок VPS либо вручную восстановите перечисленные управляемые файлы из этого каталога и старый образ. Не запускайте `docker image prune -a`, пока нужна возможность отката. Скрипт не удаляет чужие контейнеры или образы.

## Область проверки

У нас нет результата запуска этого исправления на конкретных серверах пользователя. Ошибка неправильного SNI воспроизведена на локальном TLS-стенде; реальная причина внешнего таймаута остаётся гипотезой до результата двух проверок. Для диагностики достаточно их очищенного вывода, а не приватных файлов.
